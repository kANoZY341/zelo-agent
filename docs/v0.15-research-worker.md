# Zelo Core v0.15 — Research Worker

## Status

Fourth bounded implementation slice of v0.15 Capability and skills ecosystem.

Prerequisites are merged:

- Capability Registry — PR #55;
- Skill Registry — PR #56;
- Generic Worker Registry — PR #57.

## Goal

Move the already-proven read-only `research_run` path behind Zelo's shared
Supervisor and Worker Registry while preserving its existing evidence, tool and
authority boundaries.

The key rule is:

> Research becomes a Worker without becoming more powerful.

This slice changes routing identity and auditability, not the allowed research
surface.
## Trusted worker contract

The built-in Research Worker is:

- worker ID: `research_core`;
- role: `research`;
- capability: `research`;
- authority: `workspace-read`;
- realized authority profile: `workspace-read-no-network-v1`;
- backend: the existing `ResearchRuntime`.

The `research` CapabilitySpec moves to version 2 and permits both `agent` and
`worker` subjects.

The default Research AgentSpec moves to version 2 and declares:

- role `research`;
- WorkerRequirement capability `research`;
- the existing `research_run` task kind;
- the existing evidence-retrieval skill/procedure;
- the same read-only tool allowlist.

No title or capability metadata grants runtime authority by itself.
## Persisted execution identity

Migration `0026_research_worker_selection` adds nullable `tasks.research_spec`.

For every newly submitted `research_run`, Core:

1. selects the current model through Model Gateway;
2. asks Supervisor for a worker matching the required Research role/capability;
3. persists the exact `WorkerSelectionSnapshot`;
4. includes model and worker selection in the task action hash;
5. records routing/selection audit events.

For Agent Factory execution, the Supervisor request is taken from the bound
Research AgentSpec WorkerRequirement.

Retry performs a fresh trusted worker selection and increments the task action
version.

### Upgrade behavior

Tasks created before this slice have no `research_spec`. If such a Research task
is still pending when v0.15 starts, claim fails closed with
`research_worker_selection_invalid` before model/tool execution. An operator
retry performs a fresh trusted selection and rebinds the task.

The default Research AgentSpec also moves from v1 to v2 because worker
requirements are part of trusted agent identity. Persisted v1 Research
AgentInstances therefore remain historical records but fail exact current
registry matching; new Research execution should use a v2 instance rather than
silently widening an old snapshot.

## Claim-time fail-closed gate

Before a Research task becomes RUNNING, Core validates:

- the persisted selection parses as a WorkerSelectionSnapshot;
- the selected worker still exists in the trusted registry;
- Supervisor still considers the snapshot exact/current;
- the worker remains enabled;
- role and capability requirements still match;
- Agent Factory Research tasks still match their exact WorkerRequirement;
- the task action hash still matches model + worker + agent execution identity.

If any check fails, the task is cancelled with
`research_worker_selection_invalid` before model or tool execution.
## Runner behavior

Runner resolves the selected worker ID from the Research Worker Registry and
invokes that exact registered backend.

The backend remains the existing `ResearchRuntime`, so all prior safeguards
remain:

- `local_general` model profile only;
- bounded model steps and tool calls;
- read-only ToolPolicy;
- `repo_status`, `list_workspace_files`, and `read_workspace_file` only;
- source hashing and citation validation;
- untrusted retrieved text never becomes instruction authority;
- no write, browser, shell, API or computer-control path.

The legacy direct ResearchRuntime constructor slot is retained only for isolated
tests/legacy construction; production claimed tasks carry an exact selection.
## Non-goals

This slice does not add:

- public web search or arbitrary HTTP;
- browser automation;
- computer/desktop control;
- Python or shell execution;
- write-capable filesystem access;
- API credentials or external service credentials;
- new task kinds;
- new Research tools;
- dynamic/model-authored WorkerDescriptors;
- new approval, scheduler, merge or release authority.

## Verification

Required gates:

1. exact worker snapshot persists on Research tasks;
2. action identity includes the Research Worker selection;
3. retry reselects the current trusted worker;
4. stale registry identity fails closed at claim time;
5. Runner resolves the exact selected backend;
6. Research AgentSpec activation requires the Research Worker;
7. capability subject/version tests cover Research worker compatibility;
8. migration upgrade/rollback guarantees remain green;
9. existing Research evidence/citation tests remain green;
10. diff check, Ruff lint and Ruff format;
11. full pytest;
12. adversarial review and exact-head GitHub CI.
