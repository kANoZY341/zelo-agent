# v0.17 — Conservative, provider-reported company token evidence

This stage adds a truthful **operator-only read of already persisted token
metadata** after real Research Worker attempts. It does NOT call a model,
estimate missing usage, create a new provider connection, reserve spend, grant
permissions, or change Task/Agent/Worker runtime behavior.

## Source and scope

`GET /projects/{project_id}/youtube-company-token-observation` uses the
existing owner bearer-token protection. Under a read-only SQLite transaction,
it finds Research `TaskAttempt` records started within the past 24 UTC hours,
joined to immutable Task Project identity and the four exact trusted YouTube
company role IDs:

- `youtube` (VP)
- `youtube_content` (Director)
- `youtube_research` (Manager)
- `youtube_script_writer` (Specialist)

The report counts attempts across all four roles, Campaigns, retries and
retired/replaced AgentInstances within one Project. No other Project,
baseline Research Worker, standalone `youtube_topic_researcher`, third-party
agent or non-Research Task contributes. The source is bounded to at most
256 attempt rows per Project/24h; if historical/invalid database state
contains more, refuse with a specific error instead of showing
silently-truncated, misleading totals.

## Strict accounting rules

ResearchRuntime already persists an array of per-ModelRequest token usage
returned by the model provider in a **successful** `ResearchRunResult`.
The observer counts such an attempt as fully reported only if ALL expected
steps have valid, nonnegative bounded integer values for
`prompt_tokens`, `completion_tokens` and `total_tokens`, numbered
consecutively, with `prompt+completion=total` on *every* step. It checks
the declared `model_steps` count and a nonempty bounded model ID.
It rejects nulls, booleans, negatives, missing fields, overflowing values,
step mismatches, inconsistent totals and malformed payloads.

The view distinguishes:

- `attempted_research_workers` — all started attempts;
- `completed_research_workers` — persisted successful attempts;
- `fully_reported_successes` — successes containing complete bounded
  provider-reported token metadata;
- `unmetered_attempts` — ALL other attempts, including failures and
  provider results that omit some or all token metadata;
- `provider_reported_prompt_tokens`,
  `provider_reported_completion_tokens` and
  `provider_reported_total_tokens` — **only the complete observations**.

**Unknown is not zero.** No missing/invalid/unreported attempt contributes a
fake zero-usage observation, and none is silently counted toward a financial
hard-spend ceiling. This is *partial historical information* and the provider
metrics are **not independently attested**.

The output contains explicit immutable flags:
`provider_metrics_are_unverified=true`,
`does_not_assume_unmetered_attempts_are_zero=true`,
`does_not_include_failed_or_cancelled_model_work=true`,
`no_money_or_cost_guarantee=true`, and
`no_new_execution_or_approval_authority=true`.

## Important remaining safety boundary

Model providers may not report tokens at all, may undercount prompts, or may
fail after spending tokens without persisting a successful result. These
aggregates cannot prove completeness or causal billing accuracy, particularly
for errors and cancellations. **Do not use this endpoint as an authorization
token, hard budget, billing record or proof that failures cost zero tokens.**

A future full Campaign spending system needs trusted per-model usage
attestation, pre-dispatch reservation/caps for unknown consumption, failure
usage recovery and a separately approved provider price schedule. No remote
YouTube credentials, publishing, browser/shell/computer, Agent self-hiring or
auto-scheduling is added here. Zelo Company remains disabled unless the human
Managing Director explicitly enables its exact audited Registry digest.
