# v0.15 — Open Code Review: synthetic finding calibration

This slice makes the selected first community import **measurable on fixed
cases**, instead of assuming that source-grounded comments are correct because
their JSON and line anchors validate. It is deliberately an offline human-
submitted grader, **not** automatic review or a new Coding Specialist Worker.

## Authenticated operator routes

- `GET /integration-candidates/community/open-code-review/calibration/cases`
- `POST /integration-candidates/community/open-code-review/calibration/evaluate`

The suite exposes four small Zelo-authored hypothetical code/evidence snippets:
an unchecked user-supplied file path, an off-by-one page slice, a proven
server-owned fixed-file allowlist, and a storage call with unknown middleware.
The expected answer for the first two is one exact path/added-line/
category/severity finding; the safe and insufficient-context cases expect
no *asserted* issue. The expected labels are withheld by the GET response,
but **not secret** (they remain visible in Zelo's source).

The suite has an exact SHA-256 identity incorporating the pinned
`alibaba/open-code-review` commit, fixed evidence, expected case labels,
and allowed synthetic line anchors. Before supplying a suite or scoring any
answer, the full curated upstream source manifest and attribution must verify
successfully. Missing/tampered pinned sources return a generic 503.

## Submission and measurement

The POST takes one strict candidate label, the exact suite SHA-256 and four
`{case_id, raw_review_json}` entries in canonical order. Each
`raw_review_json` is the reviewer JSON text following the already-existing
`zelo-ocr-line-review-input-v1` schema, bounded to 4,096 characters. The
entire request is bounded to 32,768 bytes; extra keys, duplicate JSON object
keys, non-JSON, stale suite hashes, omitted/reordered cases and widened
permissions fail closed.

All candidate finding text remains **untrusted**. The existing Open Code
Review binder enforces comment fields, content bounds, categories, severities,
path safety, exact allowed added lines, canonical order and duplicate
detection. Invalid reviewer JSON or out-of-scope evidence is counted as an
`invalid` case rather than silently being counted as a clean negative.

A SHA-256-bound result records, for each fixture and in total:

- **Matched findings:** exact expected path, start/end line, category, severity
- **Unexpected findings:** well-formed comments without an expected match
- **Missed findings:** expected labels with no matching valid comment
- **Invalid reviews:** malformed, duplicated, out-of-range or off-scope outputs
- **Clean negatives:** valid, empty reviews for fixtures with no proven issue

The grader does **not** independently interpret a model's free-text explanation
or prove that its semantic claim is correct: a comment with the matching
category/line can still be wrong. Labels come from four Zelo-authored
scenarios, not historical real PRs or a statistically representative
benchmark. Synthetic base/head labels are **not genuine Git SHA
provenance**, and the scorer makes that limitation explicit. No model was
invoked during baseline tests; real model comparisons need separately
captured candidate output and reviewer/operator judgments.

## Strict non-authority

The service does not run any model, import upstream executable code, register
a Reviewer Worker, touch Git, create or modify Task/Approval/Audit/Memory/Agent
rows, publish PR comments, auto-fix files, merge code, promote a Skill, or
authorize tools, Space or filesystem access. Candidate `scores` are
evaluation evidence, never an authorization ticket. The existing independent
review and CI policies remain the sole gates for developer work.
