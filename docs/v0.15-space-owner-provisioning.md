# v0.15 — Owner creates a populated Space through Core

## Purpose and boundary

The existing owner registration API requires a pre-existing filesystem root.
This additional endpoint lets the authenticated operator create a **new**
private resource and seed it with bounded UTF-8 text through normal Core HTTP.
It reuses the existing immutable Space resource registry, not a second storage
or permissions system. No Agent/Worker/Tool can invoke this owner operation.

The alternative was a general upload/write API over arbitrary paths. This
implementation deliberately does not add that interface: creation accepts
only logical Project/Space/resource identity and flat, supported filenames.
Existing Computer/Space read and list execution remains separately controlled.

## Request and normal workflow

`POST /agents/{instance_id}/space-resources/provision` requires the normal
operator authentication. The instance must be active, bound to its current
trusted registry, and belong to an active Project. Its trusted Space/file
profile must permit the selected logical Space. No caller-supplied host path,
Project override, credential source, overwrite flag or executable upload exists.

```json
{
  "space_id": "workroom",
  "resource_id": "documents",
  "operations": ["list", "read"],
  "files": [
    {"name": "notes.txt", "text": "Owner-provided project evidence."},
    {"name": "checklist.md", "text": "Review the evidence before acting."}
  ]
}
```

A successful request returns HTTP **201** and the existing Space resource
receipt. Core creates private directories (0700) and private files (0600),
then records the attested root. The record identifies a resource root, not an
immutable historical digest of every seeded file's contents.

The operator must still create an operation-specific Space intent and confirm
it with the returned `resource_record_id`, separately grant Computer file
permission, and submit a Task bound to the returned activation. Provisioning
alone never creates an intent, activation, Computer, Task or model context.
The normal `files_list`/`files_read` Task routes and revocation controls are
unchanged. See [Computer Specialist startup](v0.15-computer-specialist-startup.md).

After a Computer restart or human handback, inspect
`GET /agents/{id}/computer`. If `control.resume_snapshot_required` is true,
Space file Tasks remain refused until an explicitly permitted `browser_snapshot`
Task obtains a fresh observation. Do not edit that flag or automatically widen
browser permission. A refused file Task may be retried through the existing
`POST /tasks/{task_id}/retry` after the snapshot requirement is satisfied.

## Bounds and error behavior

At most 16 flat files may be seeded. Each text file is limited to 65,536 UTF-8
bytes, with 262,144 total bytes per creation. An empty resource is allowed.
Filenames use the gateway's existing canonical text-file contract; nested
paths, unsupported extensions, duplicate names and malformed Unicode refuse.
The existing per-Project resource limit applies before filesystem creation.

HTTP 401 denotes missing/invalid operator authentication; 422 invalid input;
403 an unapproved Space/file profile; and 409 inactive/stale state, existing
resource identity/root, quota exhaustion or unsafe/incomplete creation.
Validation errors on this document-input endpoint return a fixed message,
not the supplied document text. Existing routes retain their error contracts.
Storage/server failures may instead return HTTP 500; a failed response never
proves that no files were created. Inspect the preserved reservation/data before
recovery, rather than automatically retrying or inferring a grant.

Directory traversal uses pinned descriptors and refuses symlinks, unsafe
ownership/modes and replacement of the attested root. Files are prepared in a
randomly named private staging directory. Their complete name set, identities,
private modes and supplied bytes are checked together before and after atomic
publication. Linux `renameat2(RENAME_NOREPLACE)` publishes the completed root
without replacing even an empty existing destination. Unsupported atomic rename
refuses; there is no ordinary replacing-rename fallback. See the
[Linux rename contract](https://man7.org/linux/man-pages/man2/rename.2.html).

A small, exclusive `.provision-{resource_id}` reservation in the owner Space
directory records the prepared directory name. It is retained on success or
failure; it is recovery metadata, not a resource/Agent grant. A repeated request
is **not** an automatic overwrite or idempotent replay. Concurrent identical
requests have at most one winner.

## Failure, retry and recovery

Filesystem writes and a SQLite commit are not a single atomic transaction.
On incomplete creation, files remain in the private staging directory, without
a published resource. A database failure after successful filesystem publication
can leave a completed root without its registry record. Both outcomes preserve
all created data and the reservation; neither triggers automatic deletion,
adoption or another creation attempt with the same identity.

The owner must inspect the reservation and preserved data. Existing complete
canonical roots may use the separate registration workflow after review; staged
or partial data is not automatically registered or moved. A failed response
never means an Agent grant was made. These checks are not a security boundary
against unrestricted code executing as the same operating-system account as
Core; such a process can also alter Core memory or storage directly.

The registry mutation is serialized with existing Core authority checks.
No schema migration or production configuration change is required. Rolling
back this endpoint preserves all existing Space roots, registry records and
history; standard registration and read/list workflows remain available.

## Acceptance evidence

Tests exercise normal Core startup and owner HTTP, actual private filesystem
creation, explicit confirmation, normal Runner list/read, revocation, restart
persistence, invalid inputs, concurrent creation, changed-root refusal and
interrupted-write data preservation. Review regressions reproduce attempted
adoption of a replaced published root and replacement/modification/addition of
earlier seed files while a later file is written. Additional checks cover an
empty destination appearing at publish time, unavailable atomic publication and
a database commit failure. Controlled Computer backends are used in deterministic
regression tests; separate native host qualification is required before describing
the complete real-backend route as verified.

This is an owner resource-initialization feature, not Agent file-write,
general Space delegation, Browser/Memory/Terminal authority or full v0.15
completion. The original milestone and independent release gates remain open.
