# v0.15 — Operator-only single-attempt learned-Skill merge candidate

**Status:** implementation candidate; **default DISABLED**, no Core HTTP
route, model Tool, scheduler callback, Agent authority or automated publisher.
The entire user-facing v0.15 release remains **HOLD** under issue #166.

This is a separately reviewed precursor to real governed learned-Skill
publication. It is *not* permission to begin production merging. The existing
generic protected learned-procedure merge refusal remains unchanged.

## Activation is not automatic

`Settings.skill_publication_external_merge_enabled` defaults to
`false`. This standalone Python service is deliberately **not constructed
or reachable by application startup, Task dispatch, API routes or model Tools**.
Only a trusted local operator integration could instantiate it with a
configured GitHub publisher, explicit approved Skill proposal/claim and the
confirmation string:

`MERGE_EXACT_APPROVED_SKILL_ONCE_WITHOUT_RETRY`

Merely enabling the setting, storing a decision/fence, or obtaining read-only
provider evidence does not execute any action.

## Preconditions and exact identities

The service requires a valid existing, successful `promotion_run` Core Task
and its **latest** successful TaskAttempt plus latest `approved` Approval.
Its recorded exact PromotionRequest, Task action version/hash, approved
result and immutable GitHub PR/head/base must match the supplied, separately
operator-reviewed `MergeRequest`.

It also requires:

- The immutable accepted Skill proposal and one exact exclusive claim,
  unchanged predecessor, current AgentSpec/registry, reviewed content SHA-256.
- One immutable owner review decision, an immutable `reserved_no_send`
  fence, and the matching complete merge request fingerprint.
- Current trusted GitHub publisher binary/config identity and the exact
  approved repository; live provider PR/CI and immutable base/head Git tree
  comparisons, regular file mode `100644` and exact bounded Skill artifact
  SHA-256. These checks are all **GET** before any durable attempt.
- A fresh GET of the real GitHub `main` branch-protection policy must show
  **strict up-to-date required status checks** bound to the configured trusted
  GitHub Actions app ID, administrator enforcement, no force pushes/deletions
  and no explicit review-bypass allowances. **Missing/403/unreadable or
  unqualified protection refuses before any merge attempt record or PUT.**
  A caller-supplied opt-in flag alone cannot authorize a GitHub write.
- A fresh local Core Task/approval, registry/spec, Skill and fence verification
  under one SQLite `BEGIN IMMEDIATE` writer before inserting the record.

## At most one externally visible PUT

Migration 0046 adds three append-only tables:

1. `skill_publication_merge_attempts`: unique by fence, claim and PR. The
   **send-outcome-unresolved** row is **committed before** any GitHub PUT.
   It permanently declares `send_may_have_occurred=true`,
   `automatic_retry_allowed=false`, `runtime_authority=false`. Every
   retry is refused before any new remote request, **even if a crash occurred
   after DB commit and before the original PUT could be sent**.
2. `skill_publication_merge_receipts`: inserted only after receiving an
   affirmative provider merge response with a valid SHA, followed by a
   read-only verification that the GitHub PR is merged/closed with exact head
   identity, the merged commit has the original reviewed base SHA as its
   **single** parent, and its immutable Git tree has the approved regular
   file and blob OID. The receipt never activates a Skill or grants a Tool.
3. `skill_publication_merge_failures`: a separate one-row-per-attempt
   **terminal** diagnostic with a stable phase (PUT request/response,
   provider PR, commit, Git tree, receipt persistence), one allowlisted reason,
   the same claim/attempt ID and explicit `automatic_retry_allowed=false`.
   Raw exception text, GitHub bodies and tokens are never persisted. If
   SQLite is unavailable during incident recording, the committed attempt
   still prevents all automatic retries, and the error remains phase-coded.

All three tables have database uniqueness/constraints and SQLite triggers
that reject UPDATE, DELETE and `INSERT OR REPLACE`, including on duplicate
identities.

The protected merge request uses GitHub's `sha` head precondition and
`merge_method=squash`; the caller cannot change title, message, branch or
reviewed artifact under a different decision.

A timeout, lost provider response, unexpected base advancement, malformed
GitHub response or failed after-write verification **leaves the original
send-outcome-unresolved row intact** and refuses re-execution. Such a result
requires a distinct read-only incident reconciliation; it is not evidence
that the merge succeeded or that the operator's Skill was activated.

## Security limits and outstanding release gates

- **No live GitHub merge test is authorized by this candidate.** Tests use a
  ScriptedTransport recording GET/PUT calls, verifying exactly one PUT
  maximum and durable behavior under timeouts.
- GitHub's merge endpoint can condition on reviewed **head** SHA but cannot
  atomically pin the target branch base SHA during the network race. A
  concurrently advanced base can therefore cause an unexpected merge;
  post-merge verification will refuse the receipt, but cannot undo an
  externally sent action. Production enablement requires an independent
  repository protection/serialization decision and external qualification.
  On 12 October 2026, Zelo's private-repo GitHub protection/rulesets REST
  reads returned HTTP **403** (feature requires Pro/public), meaning the
  new protected-main preflight refuses every attempted send even if the local
  feature flag is manually enabled. There is no automatic plan upgrade or
  repository-visibility change.
- An affirmative PUT response and verified commit establish stronger
  provenance than read-only topology alone, but crash/response-loss recovery
  **does not** prove which actor merged a remote PR. Never automatically
  promote a Skill from a historical GET observation.
- This candidate still lacks a separately qualified Skill-specific Merge Task
  kind, run-time send identity, complete approval/cancellation audits and
  full deployment proof. It is not a v0.15 release gate PASS by itself.
- Existing generic Skill publication merger stays **fail closed**. Media's
  four consumed native-reader proof attempts remain terminal, and UI PR #61
  remains parked.
