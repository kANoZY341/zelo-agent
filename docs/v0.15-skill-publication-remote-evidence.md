# v0.15 — Fresh, read-only GitHub evidence for claimed Skill publication

**Status:** v0.15 release-closeout development candidate, **not** a publication executor.

This slice builds on the exact, operator-selected immutable local claim and
`SkillPublicationMergePreviewService` from the separately reviewed claim work.
It does **not** change Zelo's generic protected learned-procedure merge refusal,
activate a learned skill, or enable a Tool, Task, Worker or GitHub write.

## What changes

`SkillPublicationRemoteEvidenceService.verify(claim_id, merge_request, principal)`
reuses the existing `PromotionCIVerifier`, trusted publisher identity, and
read-only `GitHubTransport` to check that the already-reviewed learned-skill
artifact still belongs to the right live PR at the same exact base/head SHA.

The sequence is intentionally bounded:

1. Authenticate the trusted Core operator in the claim/preflight services,
   reconstruct the accepted Agent/Skill/review/previous promoted revision,
   validate the exclusive claim, and verify that exactly one correct
   `100644` added procedure artifact is the entire reviewed change.
2. Confirm publisher executable, repo identity, configured GitHub host and
   trusted CI verifier identity. A caller cannot select a different publisher.
3. Use the existing CI verifier: GET the exact open PR, check its head repo,
   branch, SHA and base branch/SHA, then fetch the bounded provider check-runs
   and require all configured check names, app IDs and slugs to be successful.
4. Compare the fresh provider-backed CI snapshots *exactly* with the
   operator's frozen MergeRequest evidence (apart from observation timestamp).
   A missing, failed, replaced or reordered check identity is refused.
5. GET the PR **again** and refuse if draft, closed/merged, moved, forked,
   renamed or rebased. Repeat the local Core claim/preflight before returning
   anything, refusing Agent pause/revocation/retirement, changed registry or
   promoted predecessor during the external reads.

The final strict response contains hashes of the exact complete merge request
and freshly verified CI, a current observation timestamp and literal flags:
`no_write_ever_issued_to_github=true`,
`current_observation_not_merge_authority=true`,
`no_publication_or_execution_authority=true`,
`runtime_skill_activation_authority=false`.

## Separate source-byte verification

The `SkillPublicationBlobEvidenceService` performs an additional
read-only provider file listing, Git blob byte/SHA-256 comparison and final
PR check. See `docs/v0.15-skill-publication-blob-evidence.md`. It does not
verify remote Git tree mode and does not provide merge authorization.

## Security and limits

The only provider requests made by this slice are **GET**. No POST, PUT, git
write, publication, approval creation, new Task kind or automatic retry exists.
All tests use a deterministic scripted provider; no real GitHub branch or PR
is touched by the new function tests.

A passing observation can become stale immediately afterward; it is **not**
an approval token or a durable right to run a future merge. Even the two
exact PR snapshots are not a substitute for an approval-bound writer-side
precondition checked immediately before the actual side effect.

## Subsequent owner-selection candidate

The separate append-only operator decision stage records the Managing
Director's approval of this exact claim/PR/head/CI observation **for later
review**. It is documented at
`docs/v0.15-skill-publication-operator-decision.md`; it never converts a
read-only observation into external merge authority.

Next distinct gates for a real learned-skill publication mechanism are:

1. Authenticated operator approval of the exact retained merge request and
   reviewed proposal/claim, including immutable external decision evidence.
2. Durable before-side-effect claim transition and timeout/ambiguous-response
   fence, with **no automatic second GitHub merge attempt**.
3. Exact remote merge receipt reconciliation against immutable approved action
   and GitHub merged commit; follow through to existing promotion-link ledger
   only after all authority checks pass. Runtime activation remains separate.
4. Independent exact-head code review, full CI and post-main regression
   evidence, followed by the remaining v0.15 release gates in issue #166.
