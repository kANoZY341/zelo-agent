# v0.15 — Deny inherited Space file grants before Task work

This is a narrowly scoped Core authority hardening for the existing
operator-confirmed Space `files_read` capability. It **does not** enable
delegated Space use or grant any additional permissions.

## Policy and enforcement

The previously qualified file gateway rejected any
`AgentExecutionBinding.delegation` at the actual file-use point. Core now
applies the same default denial earlier inside the shared
`TaskService._check_space_approval` gate, called on **submit, retry and claim**
before a Space-bound Computer Worker task can be dispatched.

A delegated execution snapshot that otherwise looks valid cannot inherit the
parent's Space activation or cause a resource lookup to begin. It returns the
stable `computer_space_activation_invalid` refusal. The existing per-Agent
file permission, exact live Project/AgentSpec/registry identity, owner
activation, cancellation, revocation and real-use file gateway checks remain
in place. No raw files, host paths, model prompts or credentials are exposed.

The negative regression takes a persisted valid nondelegated Computer Task,
derives a schema-valid delegated identity for that Task, and asserts early
refusal **before any attested-resource lookup or backend file read**. The
existing positive task/real gateway tests continue to prove a valid owner
can read one bounded UTF-8 file through the mediated path.

## Remains unqualified

This **does not** complete issue #131. Delegated Space access, other resource
kinds, cross-Space inheritance, Browser, Memory, Terminal, Shell, write access
and general Tool grants stay disabled until independently specified,
operator-approved and enforced at every use point. Specialist profile read-only
projections are not execution tickets; UI PR #61 remains parked.

v0.15 release is HOLD under issue #166. No REA runtime activation or fifth
Media native-reader proof is granted by this change.
