# v0.17 — Real Company operational status and readiness evidence

The **operator-only** GET
`/projects/{project_id}/youtube-company-status` reports *actual persisted*
YouTube Company state. It is distinct from Harness blueprint/Archify diagrams
and inactive design-review receipts. The response aggregates the real four
AgentInstances, Organization assignments, active parent Delegations and
Campaign resource reservations that Zelo's execution authority already uses.
It does not create or activate an Agent, Campaign, Tool, Space grant, or Task.

## What you see

Each of the four expected trusted roles is returned in fixed hierarchical
order, with its exact Role ID/level, reporting parent, project-bound
AgentInstance ID (if present), active Org assignment/unit ID, incoming
Delegation/Campaign IDs, reserved budget expiry, and two Task counters:

- `project_role_research_tasks_24h`: number of created Research Tasks bound
  to that Project and exact Role ID in the previous 24 UTC hours;
- `project_role_active_tasks`: all currently pending,
  awaiting-approval or running Research Tasks bound to the same Project/Role.

The status identifies why a company is not yet fully assembled:
`not_created`, `ambiguous_instances`, `registry_disabled`, `paused`,
`project_inactive`, `identity_stale`,
`assignment_missing_or_ambiguous`, `assignment_invalid`,
`parent_chain_incomplete`, `delegation_missing_or_ambiguous`,
`delegation_invalid`, or `campaign_or_reservation_invalid`.
An explicitly approved, properly assigned VP with CEO reporting is
`root_assigned`. A correctly bound descendant with its current and
inherited hierarchy intact is `delegated_chain_intact`.

A full company shows the four consecutive states:
`root_assigned` → `delegated_chain_intact` × 3. The summary reports
`unambiguous_active_role_instance_count`,
`roles_with_consistent_chain_evidence` and
`all_four_reporting_chains_consistent` only when the exact trusted
Company registry is selected, the Project is active and all role-level
evidence is consistent. Partial or revoked hierarchies are shown honestly;
the UI cannot infer readiness from a mere role name.

The endpoint reads from one explicit, deferred SQLite WAL **read
transaction**. This is essential: the default SQLAlchemy `Database.read()`
Session by itself does not start a physical SQLite read transaction under
Python 3.12's driver semantics. Zelo explicitly issues a read-only `BEGIN`
before the initial Project SELECT, pinning the same snapshot across all
four roles/Task counters while leaving concurrent writers functional.
An independent reviewer reproduced the previous inconsistent-read risk;
a regression now revokes a VP→Director Delegation from another connection
mid-status assembly, proving the first report sees one complete pre-revocation
snapshot and the next report sees the fully revoked chain. No arbitrary
active instance, assignment or delegation is selected when duplicates
exist; ambiguity fails closed in the observed status. Role snapshots must
match exact immutable trusted `AgentSpec` content and the **current**
whole-registry version, including the Org hierarchy, parent unit types,
delegation depth/max-depth, common Campaign and unexpired owner-bound
resource proof. A retired instance is not silently revived or selected.

The response is strict, frozen and versioned. Its immutable flags explicitly
state the scope: real Project state rather than draft design; **not an
operator approval, execution permission, hiring authorization, financial
budget or spend guarantee**. Strict validation also rejects changed role
order, mismatched evidence counts, non-reviewed registry identity and
forged authority flags.

## Authorization remains with Core

`all_four_reporting_chains_consistent` is **evidence, not authorization**.
The real TaskService, AgentChildCreationService, and model Tool Gateway
separately revalidate the full AgentSpec, Project, org/reporting chain,
Campaign status, budget reservations, ancestor revocations, per-role Worker
availability and capacity **at the moment of each actual action**.

The observation might become stale immediately after reading. No token
metrics are attested and no price/currency amount is inferred. The
separate 24-attempt Team budget and partial provider-reported token evidence
retain their own exact source and limitations. Use these views together,
but never add missing token readings as zero.

## Qualification

Tests use real Core persisted database records and the existing four-role
Company fixture—not guessed sample data—and verify:
- Empty/disabled Project; default registry unchanged;
- Exact VP→Director→Manager→Specialist with owner-bound budgets;
- Partial VP→Director progress and uncreated positions;
- Revoking the top VP→Director Delegation and cascading status;
- Simulated expiry and paused Project; actual state cannot masquerade as live;
- Per-role bounded Research Task counts without counting another Role;
- Authenticated HTTP status response without any database mutation;
- Strict rejection of forged authority flags and changed role order/evidence;
- Missing Project and naive clock refusal.

The full relevant tests, independent exact-head Astra Medium review and
normal serial GitHub exact-head/post-merge CI gates remain prerequisites to
merge. UI PR #61 stays parked, REA inactive and native-reader qualification
budget remains exhausted.
