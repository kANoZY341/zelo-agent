# v0.15 — Specialist Dot Space access status (read-only)

This is a Core-owned **operator inspection projection**, not an OpenDots
permission engine. It extends the existing Specialist profile without
changing its instructions, memory namespace, learned skills or Tool grants.
It depends on the separate, reviewed Space file Task authority chain
(PRs #145–#147).

## New operator-only route

`GET /agents/{agent_instance_id}/specialist-profile/space-access`

Returns at most 128 newest owner confirmation records for the exact
AgentInstance. The response includes only logical Space/resource IDs,
confirmation/intent/resource record IDs, expiry, bounded status/reason and
boolean availability. It never returns filesystem root paths, source files,
content snippets, model prompts or credentials.

A route is labelled `eligible_for_scoped_file_task` **only when the
projection observes** all of:

- Current trusted registered AgentSpec, active AgentInstance and Project;
- An unexpired, unrevoked, exact, intact owner Space confirmation bound to
  the correct intent, registry, spec, project, Space and resource;
- Existing, attested pre-provisioned directory root and the same
  ownership/mode constraints as the bounded descriptor-relative gateway;
- AgentSpec explicitly allowing `computer_run`, `computer_read` and file
  computer access;
- Owner-enabled `files` permission for that AgentInstance;
- No unresolved Core-managed human takeover for that AgentInstance;
- Configured persistent Computer backend.

It reports denial reasons for owner revocation, expiry, resource retirement,
changed roots, unsafe file-directory modes, inactive/stale agent/project,
missing Agent capability, disabled Computer file permission, unconfigured
backend or failed grant-integrity verification. Old/invalid historical
confirmations remain visible as *denied* instead of being resurrected.

## Operation-specific file grants

The view now includes `declared_operations` taken from the verified Core
intent and reports `eligible_operation=list` when a confirmation
allows only listing. An independent `read` confirmation remains labelled
`read`. Dual-operation intents expose both declared operations, while
`eligible_for_scoped_file_task` retains its existing meaning: **a snapshot
of prerequisites**, not general permission or an invitation to skip
use-point revalidation. A list-only grant must never be displayed as a
read grant. Malformed or stale intent evidence is projected as denied,
not as an effective operation.

## Owner takeover and handback

The view reuses the same durable `human_takeover_unreleased` check as Task
admission and file execution. While owner takeover is requested, active or
ambiguous, a route otherwise eligible for reading/listing reports
`reason=computer_human_control_active` and
`eligible_for_scoped_file_task=false`. Failed takeover or handback does not
clear that state. Successful explicit handback clears this particular denial;
revocation, expiry, disabled permissions and other denials still apply.

This is an additive denial reason; the response shape is unchanged. The
inspection makes no backend call, opens no file content and creates no Task,
grant or control event. It reflects the Core owner-event ledger, not an
out-of-band backend control change. A positive local projection is not a live
backend readiness guarantee: the real read gateway still enforces the existing
fresh-snapshot requirement after handback/restart and all use-point checks.

The regression reproduces three prior false-positive views through normal
Core HTTP while Task submission already correctly refused access. It also
covers pending pre-acknowledgement takeover, Agent isolation, revocation
precedence, restart persistence and unauthenticated access. This corrects the
operator's status, not a previously observed execution-authority bypass.

## Critical distinction

This response is a moment-in-time **human-readable status**, **never**
an authorization ticket. A background model, Worker, Tool or Task cannot
submit this response to gain execution privileges. Only the Core task route
independently revalidates permission at submission, retry, claim and actual
use. A positive projection does not schedule work, open a file, approve
delegation or copy any material into Zelo Mind or Memory.

The original `GET .../specialist-profile` keeps its existing
`effective_space_access=[]` and `effective_worker_or_tool_grants=[]`:
its legacy v1 declaration-only semantics are unchanged. The new operator
status view does not imply an unrestricted Space grant or any Browser,
Terminal, Shell, Memory, write, or generic Tool authority.

## Verification and future scope

`tests/test_agent_space_status.py` checks confirmed and denied states,
revocation of activation *and* intent, expiry, project/agent changes,
changed inode, unsafe directory mode, no backend, owner file-permission
revoke, empty/cross-agent profiles, authentication, no filesystem path
disclosure, and lack of Task/audit writes. This remains independent of
the parked UI PR #61; React Computer Panel/visual status comes later.
