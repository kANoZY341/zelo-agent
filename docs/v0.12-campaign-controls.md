# v0.12 — Campaign execution controls

This slice continues v0.12 after durable Project, Goal, Campaign, dependency,
event and checkpoint ownership are established.

## Goal

Create the Core authority primitives that a later bounded scheduler can safely
use without inventing a second execution or accounting system:

- campaign-scoped execution leases with fencing generations;
- deterministic recovery of expired leases;
- shared campaign budget limits;
- atomic budget reservations with idempotency;
- commit, release and expiry accounting;
- startup recovery of expired reservations.

The scheduler and autonomous Mind wake cycles remain out of scope.

## Lease invariants

A lease is identified by `(campaign_id, scope)`.

- At most one holder can own a scope at a time.
- Every successful acquisition advances a monotonic generation.
- The holder receives an opaque lease token plus the generation.
- Renew and release require the exact current holder, token and generation.
- A live lease cannot be replaced by another holder.
- Expired leases can be recovered and then reacquired at a higher generation.
- Lease tokens are never written to Campaign events.
- Lease rows are retained after release so generations cannot reset after
  restart.

The generation is the fencing value future schedulers/workers must bind to when
performing lease-protected work.

## Budget invariants

Budgets are campaign-scoped named integer resources. Core does not hard-code a
resource vocabulary in this slice. Future callers can consistently account for
resources such as model tokens, tool calls, developer runs or cost micros.

A configured limit tracks:

- committed/spent units;
- live reserved units;
- currently available units.

New work must reserve units before use. A reservation:

- is idempotent within one Campaign;
- belongs to one named owner;
- has a fixed upper-bound unit count;
- has a bounded expiry;
- may transition exactly once from `reserved` to `committed`, `released` or
  `expired`;
- cannot commit more units than were reserved.

Committed units remain spent. Released or expired reservations return their
unused capacity. Budget limits cannot be lowered below committed plus currently
reserved capacity.

SQLite triggers preserve capacity and durable-history invariants below the
service layer.

## Recovery

Core recovers expired Campaign leases and budget reservations on application
startup before task recovery starts. Recovery is also exposed explicitly per
Campaign.

Recovery only releases expired control state. It does not:

- create or retry tasks;
- claim task dependencies;
- schedule Campaign work;
- spend budget;
- authorize merge/release;
- invoke Zelo Mind.

Those actions remain separate later v0.12 work.

## API surface

Authenticated Core endpoints cover:

- acquire, inspect, renew and release Campaign leases;
- set/get/list Campaign budget limits;
- reserve/list/commit/release budget reservations;
- recover expired Campaign control state.

All durable mutations append Campaign events, so the existing Campaign event
stream remains the operational history rather than creating a second audit
system.

## Explicit non-goals

This slice does not add:

- a scheduler;
- autonomous or recurring Mind wake cycles;
- Research specialist execution;
- automatic failure/cancellation propagation;
- workspace Campaign UI;
- v0.13 memory;
- any new merge or release authority.
