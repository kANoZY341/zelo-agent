# v0.16 — Signed WhatsApp text to inert opaque channel ingress

## Scope

This **offline-only** connector-boundary helper is stacked after the signed
WhatsApp text-shape parser. It signs/verifies using the caller's server-managed
Meta App Secret and pseudonymizes ephemeral provider IDs using an **independent**
Core-managed identity secret of 32–512 bytes. It refuses weak/missing/zero
identity secrets and rejects reusing the Meta App Secret as the pseudonym key.

No secrets are stored in this code. A future service must securely provision,
rotate and protect both secrets and bind the expected Meta App/App Secret
identity to the operator-approved WABA/phone registry. Rotation of the
Core identity key changes opaque identifiers and therefore requires explicit
ledger/account rebinding; this helper does not silently migrate them.

`prepare_unverified_whatsapp_ingress` yields `None` for signed status-only
notifications. For an exactly one-message signed text event it constructs the
existing, immutable `ChannelTextIngress` with:

- `channel="whatsapp"`;
- `account_key`: HMAC-keyed WABA ID **plus** receiving phone number ID;
- `sender_key`: HMAC-keyed claimed WhatsApp sender ID;
- `thread_key`: HMAC-keyed WABA/receiving phone/sender tuple;
- `message_key`: HMAC-keyed claimed Meta provider message ID;
- bounded original text, its UTF-8 SHA-256 fingerprint and claimed UTC timestamp.

The domain separation is inherited from the existing
`derive_opaque_channel_key` implementation and `ChannelTextIngress`
fingerprints. The per-message turn ID fingerprint remains stable across
duplicate webhook retries, account- and thread-scoped, and independent of
mutable message text. A changed text digest under the same provider message
ID is intentionally left for the existing *unverified* replay ledger to
reject; this helper does not access that ledger.

The raw provider IDs do not appear in generated opaque keys. The inbound
and prepared-outbound contract representations also omit text to reduce
accidental disclosure via debugging. The ephemeral text is still included in
explicit serialization; consumers must never log or persist its unredacted
serialization without a separately reviewed data-retention decision.

## Explicit non-authority

This remains **unverified provider data**. HMAC verification does not establish
that Ahmad authorized the WABA, phone number or sender. It does not create
an operator-approved account binding, a provider-account credential record,
a trusted delivery timestamp or a freshness window.

No new webhook/API, external network request, database write, Mind turn,
task/worker/tool authorization, sending, voice, call, durable message body
or runtime learned-skill activation exists. No component is wired to call
this helper automatically.

Later independent gates must bind an operator-approved and revocable WABA/
receiving-phone identity to trusted provider credentials, verify signed event
origin against that registry, enforce durable replay/freshness limits and
perform a separate authority review before Mind admission and outbound
sending. Native Media qualification evidence and UI PR #61 remain untouched.

## Tests

Bounded HMAC verification; independent secret enforcement; stable
account/thread/message pseudonyms; distinct receiving phone/WABA/sender
identity; changed-text digest under identical provider message ID; safe
status-only no-op; no provider/task authority; private text omitted from
default representations. Full exact-head CI and review are required before
any merge.
