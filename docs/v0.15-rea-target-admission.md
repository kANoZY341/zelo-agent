# REA inert target admission

This increment adds an independent operator-only byte snapshot utility. It does
not run REA, change the #119/#121 fixed-fixture proof, register a Worker/Task,
change Agent/Capability/Skill registries, or enable any of the 139 REA tool grants.
It does not touch the Media refusal history or parked UI. It imports only Python
standard-library modules and never imports or executes the vendored source.

## Operator workflow

From the dedicated repository root, prepare these fixed directories yourself:

```sh
mkdir -p workspaces/rea-target-inbox workspaces/rea-target-snapshots
chmod 700 workspaces/rea-target-inbox workspaces/rea-target-snapshots
```

Place one operator-selected application folder (mode 0700) inside the inbox.
The utility accepts a single basename, never an absolute path, environment
setting, API upload, or model selection. Both roots must already exist, belong
to the current OS user, and have mode 0700. Their ancestors must be real,
non-group/world-writable directories owned by the operator or filesystem root
owner; a system-owned sticky ancestor such as `/tmp` is permitted, but neither
fixed root may use that exception. Do not give agents access to these directories.
There are no new environment settings.

```sh
.venv/bin/python -m scripts.admit_rea_target \
  --allow-offline-target-admission example-app
.venv/bin/python -m scripts.admit_rea_target \
  --allow-offline-target-admission --verify SNAPSHOT_ID \
  --receipt-sha256 RECEIPT_SHA256
```

Without the explicit opt-in switch the CLI refuses before filesystem access.
Retain the emitted identity and receipt digest separately from the snapshot.
CLI output contains only bounded aggregate metadata and inert-authority flags;
it omits the selected local folder name, relative file names, and contents.
The private receipt contains relative paths, sizes, SHA-256 digests, source-defined
limits, operator UID and fixed-inbox provenance. It intentionally does not retain
an absolute path or selected folder name. No output is sent to Mind or chat.
This local receipt is not an authenticated operator identity or a Core approval.

## Narrow input contract

Only `.js`, `.mjs`, `.cjs`, `.json`, `.html`, `.css`, and `.map` files are accepted.
Bytes must be UTF-8 text without ASCII control bytes except tab, CR and LF. This
is an inert lexical filter, not artifact parsing or proof of valid/safe JavaScript;
text with those extensions may still be malicious. No archives are unpacked,
syntax parsed, imports loaded, browser opened, native tool launched, or target
executed. The utility performs no network operations and grants no network access.

Names are 1–80 ASCII letters, digits, underscores, dots or hyphens, beginning
with a letter or digit. Hidden entries, symlinks, hardlinks, nonregular files,
foreign-owned content and group/world-writable content are refused. Limits are
128 files, 512 KiB per file, 4 MiB total, five path components including the file,
and 256 total entries including directories. Empty trees and empty directories
are refused; zero-byte files are allowed. Limits are compiled into trusted code,
not caller-controlled CLI options.

## Integrity and threat model

Every path component is opened relative to a retained directory descriptor using
`O_NOFOLLOW`; file reads use nonblocking opens and validate regular type, link
count, owner, size, inode and timestamps before/after reading. Directory names
are streamed with an entry cap. Source contents and metadata are scanned twice,
including after copying, and ancestor links are checked on exit. The source is
never modified. No naive recursive path copy or target-selected host path is used.

The snapshot receives a random identity in the private ignored staging root.
Files/receipt are sealed to 0400 and directories to 0500. Catchable failures clean
only that invocation's exclusive scratch tree using retained directory handles,
including partial writes and late source replacement. Existing staging data is
preserved. OS crashes, SIGKILL, or filesystem failures during cleanup can leave
private scratch data; these are not successful admissions and have no authority.

“Immutable” here means sealed read-only by this utility, with fail-closed integrity
verification. POSIX modes cannot prevent the owning user or root from modifying
or replacing data. The operator, kernel and local filesystem are trusted; a hostile
process running as that operator, hostile mount manipulation, or malicious
filesystem is outside this boundary. Stop writers before admission. The two-pass
checks detect observable races but cannot provide an atomic filesystem snapshot
or guarantee that files did not change and revert between checks. No host-wide
immutable flags or extra privileges are requested.

Verification requires the independently retained receipt SHA-256, reads bounded
bytes, reconstructs the exact canonical receipt from actual staged content, and
rejects changed, missing, extra, oversized, nonregular, linked or unsealed content.
Even a coherent rewrite of receipt and files fails against the original digest.
Verification is point-in-time; it is not an execution lease, signature, or protection
against later writes. The receipt is never trusted as a source of limits or paths.
The aggregate digest hashes canonical sorted path/size/content-digest records.

## Remaining gates

A later separately authorized design must bind receipt identity and content to
Core approval, Space/Agent/Task/Worker authority, revocation and consumption,
source/analyzer identity, execution-time revalidation, sandbox lifecycle and
real analyzer target integration. No consumer of these snapshots exists today.
Copied bytes and a receipt never grant permission to execute. No new runtime
route or native-reader proof attempt is introduced.
