# v0.15 — Promoted-head recording exclusivity

## Scope and authority

A governed skill proposal remains immutable after review. Ahmad's acceptance
is a historical decision, not permission to record multiple promoted heads
for one AgentInstance, source skill, procedure and revision version.

The promotion-link recording path now checks the already-promoted, verified
lineage **inside the serialized Core write transaction**, before inserting
another durable promotion link or recording a success audit event. Only an
initial version 1 or the immediately following version whose predecessor hash
matches the verified latest promoted content may link. A competing/stale head
fails closed with `skill_learning_promoted_head_advanced`. Missing predecessor
history fails closed. An exact retry of an already-linked proposal with the
same verified merge proof remains idempotent.

This closes the *local promotion-proof recording* race for two proposals
accepted before either promotion. The SQLite writer uses BEGIN IMMEDIATE to
serialize read-before-write decisions. If a future storage implementation
changes that contract, it must preserve equivalent write serialization.

## Historical compatibility and boundaries

Historical divergent heads, if already persisted under older code, still
cause the read-only promoted resolver to fail closed as ambiguous; tests
construct this historical condition explicitly. No prior link, reviewed
proposal, receipt, or operator decision is rewritten or deleted.

**This is not an external publication lock.** A GitHub PR may already have
been merged before `record_promotion_link` runs. The generic promotion
publisher and merger do not yet carry a verified learned-skill proposal
identity through their pre-merge authorization path. A future pre-publication
gate must bind that identity, recheck it immediately before external merge,
and reject competing releases there. Do not advertise external exclusivity,
automatic skill activation, or the absence of historical ambiguity.

No worker/tool/agent permissions or runtime skill loading change here.
The existing UI PR remains parked.

## Validation requirements

- Competing accepted v1 proposal is refused at link time after another
  v1 candidate has linked; the accepted record survives and the first
  exact link retry stays idempotent.
- The resolver still refuses constructed historical dual-head data.
- Unchanged v1/v2/v3 promotion lineage and revision resolver tests pass.
- Ruff check, formatting, diff checks and full exact-head CI must pass
  before this branch can merge.
