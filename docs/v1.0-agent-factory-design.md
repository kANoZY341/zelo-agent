# Zelo Core v1.0 — Agent Factory

## Status

Architecture contract for the first v1.0 implementation slice.

v1.0 builds on the merged v0.10 multi-worker runtime. It does not replace the
existing Agent Runtime, Developer Runtime, Worker Registry, Supervisor,
approval system, validation, review, promotion, or release boundaries.

> Models think. Workers work. Agents specialize. Zelo decides.

## Mission

v1.0 introduces persistent, trusted specialist-agent identities that can use
existing Zelo runtimes and delegate work to replaceable workers without becoming
a second authority plane.

The first target is the reusable Agent Factory foundation. Business, YouTube,
Trading, Research, and other specialist agents are registered only after this
foundation is proven.

## Layering

```text
                              ZELO
                               |
                         Agent Factory
                               |
                         Agent Registry
                               |
                  trusted specialist identity
                               |
              +----------------+----------------+
              |                                 |
        Agent Runtime                     Developer Runtime
   bounded model/tool loop          approved coding delegation
              |                                 |
        Tool Registry                 Worker Registry/Supervisor
                                                |
                                Codex / Claude / OpenCode / future
```

Agents and workers are deliberately different concepts.

An agent is a long-lived Zelo specialist definition: purpose, capabilities,
allowed task kinds, tool scope, memory namespace, and delegation requirements.

A worker is an execution harness selected by Zelo for bounded work. Workers do
not become persistent specialists and agents do not inherit worker credentials,
executables, shell authority, GitHub authority, or promotion authority.

## First-slice scope

The first implementation slice adds:

- canonical `AgentDescriptor`;
- immutable, trusted `AgentRegistry`;
- content-derived registry version;
- deterministic `AgentFactory` lookup/instantiation;
- canonical agent capability and delegation metadata;
- isolated memory namespace identity;
- explicit allowed task kinds and tool names;
- explicit worker-role/capability delegation requirements;
- tests proving deterministic ordering, fail-closed duplicate registration,
  canonicalization, immutable registry state, and version invalidation.

This slice does **not** add a new API task kind or database migration. Persisted
execution is added only after the descriptor/snapshot contract is stable.

## Agent descriptor

A trusted descriptor contains only Zelo-owned metadata:

```text
agent_id
role
capabilities
allowed_task_kinds
allowed_tools
memory_namespace
delegation_role
delegation_capabilities
enabled
version
```

All tuple/set-like fields are canonical: sorted, unique, bounded, and validated.
Agent IDs, roles, capabilities, tool names, task kinds, and memory namespaces use
restricted identifier syntax.

The descriptor is immutable once registered.

### Example

```text
agent_id=coding
role=coding
capabilities=[code_planning, code_review, repository_change]
allowed_task_kinds=[agent_run, developer_run]
allowed_tools=[repo_status, list_workspace_files, read_workspace_file]
memory_namespace=agent/coding
delegation_role=developer
delegation_capabilities=[zelo_core_development]
enabled=true
```

The descriptor does not name Codex, Claude Code, OpenCode, or a model. Worker
choice stays with the existing Supervisor and Worker Registry.

## Agent registry

`AgentRegistry` is populated only by trusted application assembly.

Its version is a canonical content fingerprint over:

- registry schema version; and
- every registered descriptor in deterministic `agent_id` order.

Changing any material descriptor field changes the registry version.

The registry provides deterministic listing and exact-ID lookup. Unknown or
disabled agents fail closed at the factory boundary.

The registry does not mutate dynamically from model output, task payloads,
plugins, files, or external services.

## Agent Factory

`AgentFactory` resolves a trusted descriptor by `agent_id` and produces a
bounded runtime binding for later execution.

The first slice returns an immutable binding containing:

- exact descriptor; and
- exact registry version.

Later persisted specialist-agent tasks will bind this snapshot into approval and
audit state. A changed descriptor or registry version must invalidate
compatibility instead of silently changing an existing task's identity.

The factory is not a code generator. It does not install packages, create worker
executables, provision credentials, or dynamically invent permissions.

## Delegation contract

An agent may declare a worker delegation requirement:

```text
delegation_role=developer
delegation_capabilities=[zelo_core_development]
```

This means the agent may ask Zelo to route work through the existing Supervisor.
It does not identify a concrete worker.

The eventual flow is:

```text
Coding Agent
    |
    | requests developer + capability set
    v
Zelo Supervisor
    |
    +--> Codex
    +--> Claude Code
    +--> OpenCode
```

Selection remains deterministic, capacity-aware, authority-bound, and approval-
bound under the v0.10 worker contract.

An approved worker selection is never silently replaced because an agent prefers
another worker.

## Tool contract

`allowed_tools` is an upper bound on which registered Zelo tools a specialist
may request.

The existing `ToolRegistry`, `ToolPolicy`, and `ToolGateway` remain the
execution authority. An agent descriptor never bypasses tool policy.

An empty tool list means the specialist has no tool authority.

Unknown tools in a descriptor are not resolved in the first contract-only slice;
application assembly will later validate registered-agent tool references against
the trusted Tool Registry before enabling execution.

## Memory namespace

Each agent owns one canonical logical memory namespace such as:

```text
agent/coding
agent/business
agent/youtube
agent/trading
```

The namespace is an identity and isolation boundary, not permission to read
arbitrary host files or user data.

The first slice does not implement persistent agent memory. It only makes the
namespace part of trusted agent identity so future memory storage can be
partitioned without changing agent IDs.

Future memory must remain bounded, auditable, and scoped to the registered
namespace. An agent may not choose another agent's namespace at runtime.

## Approval and authority invariants

Agent Factory must preserve these invariants:

1. Zelo remains the only routing and approval authority.
2. Agent descriptors are trusted configuration, never model-authored input.
3. Agents cannot directly select executables, credentials, providers, or concrete
   workers.
4. Worker selection continues through the trusted v0.10 Supervisor.
5. Existing worker authority profiles remain unchanged.
6. Tool access continues through Tool Policy and Tool Gateway.
7. Promotion, merge, release, and GitHub credentials stay outside agents and
   workers.
8. Material descriptor/registry changes invalidate future snapshot compatibility.
9. No hidden autonomous background loop is introduced.
10. No specialist can spawn another specialist unless a later explicit delegation
    contract adds and binds that authority.

## Specialist rollout

After the generic foundation is proven, specialist agents should be introduced
one at a time.

Initial order:

1. Coding Agent — first production proof because Zelo already owns the complete
   developer/reviewer/validation boundary.
2. Business Agent.
3. YouTube Agent.
4. Trading Agent.

Each specialist must declare only the capabilities/tools it actually needs.

## Deferred work

The first Agent Factory slice intentionally does not add:

- Ruflo or another swarm runtime;
- LangGraph or another orchestration framework;
- MCP/A2A ecosystems;
- autonomous agent-to-agent messaging;
- dynamic agent creation from prompts;
- self-modifying descriptors;
- persistent learning;
- cross-agent shared memory;
- new cloud-model credentials;
- unrestricted browser/shell access;
- background scheduling;
- a new database migration.

Those are added only when a concrete specialist requirement justifies them.

## Implementation sequence

1. add this design contract;
2. add canonical agent descriptor/binding contracts;
3. add immutable Agent Registry and Agent Factory;
4. prove registry versioning and deterministic behavior with tests;
5. wire trusted application assembly with a disabled-by-default Coding Agent;
6. add an approval-bound specialist execution snapshot;
7. add persisted specialist execution only if the snapshot contract requires it;
8. integrate Coding Agent with existing Agent Runtime and Developer Runtime;
9. prove agent -> Supervisor -> worker delegation without vendor-specific routing;
10. run full regression/security review before enabling additional specialists.

## First-slice acceptance criteria

The first slice is complete when:

1. descriptors are immutable and reject extra fields;
2. identifiers and bounded collections are validated;
3. canonical ordering/uniqueness is enforced;
4. duplicate `agent_id` registration fails;
5. registry listing is deterministic;
6. registry version changes for any material descriptor change;
7. registry version is independent of registration insertion order;
8. factory lookup fails closed for unknown or disabled agents;
9. returned bindings include exact descriptor and registry version;
10. no worker implementation/vendor appears in the generic agent contract;
11. no database migration or task/API behavior changes;
12. Ruff, format check, and the full pytest suite remain green.
