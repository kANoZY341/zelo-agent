# v0.15 — Core-mediated human computer takeover fence (HOLD)

**Status:** bounded security fix candidate for #131/#166. This is not broad
OpenDots Space qualification, a new permission grant, or release approval.

## Source-observed regression

Before this fix, a claimed `computer_run` Space file read checked the remote
control state once, then performed its local 64-KiB read after another wait.
An owner could complete `AgentComputerService.take` after the read's
`backend.control` response returned the old bot snapshot. The SQLite
revocation check remained valid, so the read could return private content
after human takeover. A deterministic test reproduced that behavior
on the previous source (the test failed because **no refusal occurred**).

## Core-managed remedy

- A trusted owner takeover first commits an append-only
  `take_control_requested` event **before** any remote backend takeover
  request. It also rotates the current Computer permission-version stamp,
  invalidating outstanding Task bindings without widening permissions.
- The pre-network event is serialized by SQLite `BEGIN IMMEDIATE` with
  existing Space read use-point checks. If the Space read wins, its bounded
  file read finishes before the takeover can start. If takeover wins, a
  stale bot-control response cannot override the durable request.
- Task submit/retry/claim and the file gateway deny active, failed or
  ambiguous takeover until the owner records a verified handback.
- A pending remote takeover response cannot be raced by a handback. A
  handback also records a pre-network intent and clears denial only after
  confirmed bot control, not an unknown/human/transitioning response.
- Crashes and remote timeouts fail closed. An owner can use the existing
  handback endpoint to cancel a **waiting** bot-owned OpenBot request through
  the pinned `/control/cancel` contract before the historical fence clears.
  The cancellation's returned holder, requested and transitioning fields
  must confirm bot control; an ambiguous cancellation remains blocked. A
  crashed request still marked `take_control_requested` with no terminal
  event needs separate manual recovery/independent remote-state
  reconciliation; there is **no** automatic retry or bypass.
- Overlapping handbacks are refused while a remote handback is pending.
  Their asynchronous results cannot clear a newer owner takeover.
- Existing descriptor-relative file opening, root inode checks, human
  snapshot readiness, cancellation, permissions, authority binding, audit
  events and default-deny Space behavior remain in place.

## Threat boundary, limitations and release gates

This coordination covers **Zelo Core-mediated owner takeover/release**.
It does **not** attest that an external actor cannot manipulate OpenBot's
control state directly, or create a server-side transition outside Core.
A future production-grade backend lease/epoch protocol and real-host
qualification would be needed to prove that broader boundary.

Space file reads remain narrowly bound to approved, nondelegated,
Task-claimed UTF-8 text files. No browser, shell, memory, write,
cross-Space, inherited Space, general Computer or Tool capability is
created. This fix does not activate REA, change native Media proof quota,
restart a fifth native qualification, unpark UI #61, or release v0.15.

### Validation expected before merge

The regression suite covers stale bot-control replies after owner takeover,
pre-network pending handoffs, refusal of new Space Tasks, failed takeover,
ambiguous handback, overlapping handbacks and incomplete takeover/handback
interleavings. The real `OpenBotComputerBackend` HTTP adapter's partial
take/request failure and owner-initiated cancellation are exercised with
scripted provider responses. This uses the existing pinned OpenBot
`agent-computer/src/control.ts` `cancel(requestId)` implementation,
not an invented HTTP endpoint.
Repository lint/format, exact-head GitHub CI, independent review,
clean merge-tree and post-merge main CI are required.

The authoritative milestone **still remains HOLD** under #166.
