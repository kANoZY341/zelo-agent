# v0.15 — Open Code Review findings in the independent Coding review

## Decision and scope

Issue #132 requires useful Open Code Review integration, not another catalog
preview. Existing Core already owns the independent reviewer selection,
approval-bound Worker identity, isolated candidate snapshot, capacity, result
and promotion checks. The chosen change adds a selectable output format to
that path and reuses the pinned OCR adapter. It does not introduce a second
review service, upstream CLI, model transport, autonomous reviewer or merge API.

The alternative was to launch an independent upstream OCR engine or attach
operator-supplied comments after review. That duplicates source/lifecycle
boundaries and does not prove the existing reviewer inspected the same bytes.
The minimal integration instead checks returned findings against anchors Core
derives from the exact frozen candidate. All imported code remains reference
data; Apache-2.0 attribution and source hashes are unchanged.

## Explicit operator selection

Default `ZELO_DEVELOPER_REVIEW_FORMAT=zelo` preserves the existing report
contract and serialized request. To request OCR-formatted independent review,
set `ZELO_DEVELOPER_REVIEW_FORMAT=open_code_review` in the private environment
for the intended Core process. No live environment file is changed by this PR.

The ordinary developer Task still needs its existing approvals, trusted
independent Worker and validation environment. OCR selection is captured in
the immutable reviewer binding. An independent reviewer must exist; an explicit
OCR selection never silently falls back to unreviewed development. Changing
the selection invalidates pending compatibility and is checked again around
review execution. Model output cannot choose the format or expand authority.

## Execution and provenance

Normal flow: approved developer Task -> existing worker/validation -> Core
frozen candidate snapshot -> sandboxed Git changed-line derivation -> existing
independent reviewer -> OCR format/anchor validation -> existing ReviewerReport
and validated persistent Task result/audit. The typed result contract binds
the OCR evidence, summary hash, normalized findings, approved base and developer
candidate digest together. These checksums detect mismatched records; they are
not cryptographic signatures or authorization against a caller that rewrites
entire records and recomputes their hashes.
No snapshot contents are published to GitHub by this code.

The reviewer receives instructions to produce the pinned OCR JSON contract.
Its paths and line numbers are only claims: Core derives allowed anchors per
changed file, rejects findings outside them, bounds diff/output size, and
validates source provenance through the existing curated-source verifier.
Nondefault Git diff attributes refuse, preventing repository rules from
reclassifying binary content as a clean textual review. Compact inclusive line
ranges keep the prompt bounded; raw anchor sets still validate each finding.
Sparse maps or added context that exceed the instruction budget refuse without
truncation.
Ignored generated files supply no anchors. Unsupported/binary/nonregular,
empty or deletion-only changes refuse OCR review rather than claim a clean
review; the ordinary report mode remains available for separately approved
work requiring different coverage.

The snapshot's Git HEAD is the approved **base**, not a committed candidate.
Both Git SHA fields in the nested line evidence therefore identify that real
base. The enclosing `isolated_candidate_snapshot` evidence records the exact
`candidate_content_sha256` shared with the normal review result. Its diff hash
is the SHA-256 of the canonical ordered per-file patch-hash manifest, not an
invented commit or the hash of a concatenated textual patch. This evidence
must not be presented as the existing committed-Git operator-preview receipt.

The existing Worker preflight, read-only authority, snapshot mutation checks,
capacity limits and cleanup remain active. A malformed/ungrounded response,
source-verification failure or changed review selection fails closed; no
alternate parser accepts it as a successful review. The normalized report
is still evidence, not independent proof of model accuracy, CI success,
operator approval or permission to merge.

## Compatibility and rollback

The default reviewer binding omits the new format field during nested
serialization, preserving historical default request fingerprints and the
old wire shape. An explicitly selected OCR binding emits the field so older
code will refuse that new binding rather than silently reinterpret it.
Existing normal-review requests still parse and execute under default settings.
No database migration is required. Withdrawing the setting does not erase
old results or reactivate pending OCR approvals; they require a compatible,
explicitly approved request.

## Verification boundaries

Regression tests execute real standalone Git checkouts and Core review
snapshot lifecycle, actual no-network Git sandbox commands and validation,
with controlled producer/reviewer outputs. They cover full developer execution,
tracked/untracked anchors, ignored paths, default wire preservation, missing
independent reviewer, selection withdrawal, mutation detection and prohibition
of model-supplied approval/auto-fix fields.

These deterministic tests prove integration behavior, not the semantic quality
of a live model. An independently observed native reviewer run and the existing
fixed-case quality evaluation remain distinct evidence. Full exact-source CI,
review and predecessor/post-merge checks remain mandatory. This change does
not complete ECC publication, other integrations, Media or the entire v0.15
release. It creates no new Worker/Tool/Space grant and does not change UI #61.
