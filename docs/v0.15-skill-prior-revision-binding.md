# v0.15 — Trusted prior-revision binding for learned procedures

## Scope

This is a Core-only, non-executable continuation of the governed skill-learning work:

1. PR #100 adds append-only proposal/review records and inert candidate serialization.
2. PR #103 enables Ahmad-only candidate materialization.
3. PR #104 records historical, append-only evidence of an accepted candidate passing the existing Promotion → CI → Merge path.
4. PR #105 adds a read-only, exact promoted-revision resolver.
5. This slice allows new proposal versions to cite the **exact preceding promoted revision** without activating either revision.

The trusted source remains the operator-reviewed promotion-link ledger, not model claims, free-form memory, an uploaded file or an Agent-authored identity.

## Resolution rules

For a new revision vN where N is 2 or greater, Core resolves v(N−1) from the current AgentInstance, source Skill and procedure. The resolver must validate the entire retained promotion lineage and refuse:

- a missing or unpromoted predecessor;
- an incorrect previous revision digest;
- a version gap or duplicate promoted version;
- a wrong promotion repository;
- a stale or inconsistent promotion link;
- a proposal that widens the allowed capability/task/tool/Space envelope;
- histories exceeding the bounded 64-link limit.

For v1, the prior resolver intentionally returns no predecessor. This preserves revalidation of historical accepted v1 proposals after their own promotion. For v2+, Core selects the **exact prior version**, not whichever version happens to be latest at revalidation time. Thus v2 can remain reviewable/retryable after it is itself promoted, while v3 may cite the reviewed v2.

## Authority boundary

A prior-version proof is **not** a runtime Skill Registry entry or an Agent execution grant.

This slice adds no new API endpoints, Agent task kinds, automatic approvals, Developer or Promotion runs, candidate materialization, filesystem writes, network access, cross-Agent reuse, or active learned-skill loading.

Only the existing Core proposal construction/revalidation path consumes the trusted prior-revision lookup, solely to build or revalidate immutable proposal identity. Ahmad review and normal Developer/Review/Promotion remain independent gates.
