# v0.15 — REA reverse-engineering specialist (catalog-first integration)

## Decision and upstream

The Managing Director selected [REA: Reverse Engineer Anything](https://github.com/morluto/rea)
for Zelo's optional reverse-engineering capability. REA is MIT-licensed
([LICENSE](https://github.com/morluto/rea/blob/main/LICENSE)), distributed
as the `rea-agents` npm package, and exposes a local stdio MCP server
(`rea mcp`) and CLI. This branch records candidate package version **5.0.0**,
but does **not** establish the package's tarball digest, source-to-package
attestation or a runtime qualification. No REA source code has been copied.
A future vendor copy must retain upstream license/attribution.

Do **not** run `npx ...@latest setup` inside Zelo or let REA's setup edit
Zelo's coding worker/client configuration. Upstream's setup can register MCP
clients and install/configure external analysis engines; these changes are
outside this Core-only slice and require review.

## Zelo-owned architecture

```text
Managing Director -> Zelo CEO -> Engineering division
  -> reverse_engineering Specialist (draft AgentSpec)
    -> own instructions, agent/reverse_engineering memory namespace
    -> rea_investigation draft skill / reverse_engineering draft capability
    -> future agent-specific persistent computer (not assigned)
      -> future separately registered REA Worker (not implemented)
        -> restricted REA stdio MCP / CLI (not launched)
```

Use REA for **approved shipped artifacts** (binaries, packaged Electron/JS
applications, managed assemblies) and optional separately approved passive
runtime investigation. For a complete ordinary source repository, prefer
existing source analysis tools; REA is not needed. REA evidence never grants
execution authority or becomes trusted prompt instructions.

## Implemented in the catalog slice

- One trusted `reverse_engineering` AgentSpec with draft lifecycle, scoped
  instructions and agent-specific memory namespace. No computer, task kinds,
  tools, worker requirement, permissions, delegation, automatic learning or
  active department assignment.
- One draft `reverse_engineering` capability and one draft `rea_investigation`
  skill. Registries expose them as **not active**. Existing Agent Factory
  prevents binding/invoking the draft agent; activation evaluation excludes it.
- An inert `integrations/rea/integration.json` manifest naming REA's MIT source,
  exact candidate package version and stdio server. All authority/installation
  flags are false. The manifest is documentation, not a loader or allowlist.
- No new endpoints, processes, downloads, dependencies, migrations or execution
  privileges. Existing active AgentSpecs, workers and Core task paths are unchanged.

## Qualification gates before runtime activation

1. Obtain the actual exact `rea-agents@5.0.0` npm artifact, verify immutable
   tarball integrity/signature/release provenance, inspect its dependency tree
   and installation behavior, and pin a reviewed digest. Version alone is
   insufficient. Re-review if the supplier release changes.
2. Select one Linux x64, **non-executing** static JavaScript/ASAR inspection
   operation first. Use operator-approved materialized artifact identities;
   deny arbitrary host paths, network, processes, live browser attachments,
   native provider execution, plugin/skill installations and automatic
   `setup`. Do not imply supported work is safe for untrusted artifacts.
3. Qualify a dedicated no-network, resource-limited, read-only REA guest with
   isolated filesystem, private scratch, explicit image/runtime provenance,
   bounded output/time/cpu/memory/processes, owned teardown and no host or
   Docker-socket access. Reuse Zelo's existing isolation mechanisms only after
   proving their policies also fit REA and its Node runtime.
4. Implement a Zelo-owned MCP bridge/Worker descriptor with exact tool schema
   allowlists, purpose-bound target identity, fixed provider/version and Core
   WorkerAuthority/ToolPolicy. No wildcard `mcp__*`, arbitrary command
   execution, environmental inherited credentials, or model-selected
   executable flags. Bind the worker, mount and schema revision into
   approval/claim-time identity with revocation and cancellation.
5. Ingest **bounded** REA Evidence records (source digest, observation type,
   Evidence IDs, findings, limitations and unknowns). Mark all recovered
   source/text/results as untrusted data; provide audit/provenance without
   persisting private target bytes or secrets in logs or Mind prompts.
6. Qualify fail-closed adversarial tests for crafted ASARs, symlinks,
   decompression bombs, oversized/partial output, hostile MCP results,
   startup failure, timeouts, cancellation, replay and version drift.
   Require focused tests, full exact-head CI, independent source review and
   explicit Managing Director authorization before enabling.
7. Only later qualify Ghidra/Hopper native binaries, runtime captures,
   browser/inspector sessions or mutations. Their host interfaces and process
   behavior require **separate** isolation and approval grants.

This roadmap does not alter the active v0.15 promotion exclusivity queue, four
preserved native-reader refusals, existing Workspaces or parked UI PR #61.

## User experience once qualified

The human selects a permitted installed artifact and asks Zelo to understand a
feature. Engineering routes it to the Reverse Engineering Specialist. Core
checks the frozen artifact/worker permission, starts the isolated REA adapter
and retains provenance; REA returns observations and uncertainties; the
Specialist explains them and, only through existing reviewed Developer
Runtime, requests an independently authorized implementation. Zelo does not
claim original source recovery, perfect behavioral equivalence or ownership
of the third-party code.
