# v0.15 — Read-only Agent Computer Worker

## Goal

Allow a persistent Zelo Agent to inspect its own persistent computer through the
normal trusted task/runtime path without granting browser mutation, workspace
writes, shell execution, credential entry, host access or host fallback.

This slice builds on:

1. `v0.15-agent-computer-openbot-foundation.md`;
2. `v0.15-agent-computer-control.md`.

## First executable surface

The only Agent Computer actions cleared by this slice are:

```text
browser_snapshot
browser_read
files_list
files_read
```

Not cleared:

```text
navigate
click
type
key
scroll
files_write
exec / shell
human secret entry
credential injection
host filesystem
host shell
host browser
```

Screenshots are also excluded from Agent/model results in this slice. They remain
a future owner-facing Computer Panel surface.

## Authority model

Computer execution does not consume the Agent's domain `worker_requirement`.
A Research/Coding/etc. Agent may retain its normal domain worker and separately
own a persistent computer.

A `computer_run` requires the intersection of all of:

- exact current active AgentInstance identity;
- AgentSpec `allowed_task_kinds` containing `computer_run`;
- registered Agent capability `computer_read`;
- trusted AgentSpec computer profile supporting the requested surface;
- persisted Core computer `enabled=true`;
- persisted Core Browser or Files permission for the requested action;
- an enabled Computer Worker in the Worker Registry;
- exact Supervisor worker-selection identity;
- exact worker-authority-policy fingerprint;
- exact per-Agent permission fingerprint; and
- exact OpenBot adapter/revision/namespace/supervisor identity.

A task is Agent-only. Direct generic `/tasks` submission is denied in Core and
SQLite also rejects `computer_run` without an Agent execution identity.

## Execution identity

`ComputerExecutionSpec` binds:

- AgentInstance UUID;
- exact Computer Worker selection snapshot;
- action;
- bounded relative path where applicable;
- permission-version digest;
- backend-identity digest; and
- timeout.

The specification is immutable within one task action. Retry may rebind it only
through the standard failed/cancelled/interrupted -> pending action-version
transition, after re-reading current permissions and backend identity.

## Revocation / claim boundary

Submission is not sufficient authority.

Immediately before creating a running attempt, TaskService revalidates:

- Agent execution identity;
- Agent registry snapshot;
- Supervisor worker selection;
- worker-authority policy;
- current Core permission row;
- permission digest;
- OpenBot backend identity;
- action/path/timeout binding.

Any mismatch cancels the task with
`computer_execution_spec_invalid` **before a TaskAttempt is created**.

ComputerRuntime checks the same permission/backend binding again immediately
before the OpenBot request and once more after the read returns.

## Human takeover barrier

Read-only Agent work is refused while:

- the human holds control;
- a handoff request is active; or
- control transfer is in progress.

The worker never attempts to override or release human control.

## Result bounds

OpenBot responses are normalized into Zelo-owned typed result models.

Current bounds include:

- browser snapshot: at most 200 elements;
- element refs/roles and workspace paths are identity fields and fail closed if oversized rather than being truncated;
- browser page text: max 6,000 characters;
- workspace text: max 64,000 characters;
- workspace listing: max 500 entries;
- display names/values/titles may be bounded only while setting `truncated=true`;
- upstream booleans/integers/types are validated strictly.

Raw OpenBot response objects are never persisted directly.

## Capability, Skill and Worker Registry

New trusted entries:

```text
Capability: computer_read
  subjects: agent + worker

Skill: computer_observation
  procedure: computer_observation
  task: computer_run

Worker: computer_core
  role: computer
  capability: computer_read
  authority: agent-computer-read
```

The Computer Worker is registered only when the OpenBot backend is actually configured.

Agent Activation policy v3 additionally requires a computer profile,
`computer_read`, and an enabled Computer Worker for any Agent declaring `computer_run`.

## Worker authority

`agent-computer-read-v1` is Core-only metadata whose realized policy says:

- browser mutation: false;
- filesystem write: false;
- shell: false;
- host fallback: false;
- credential injection: false;
- human takeover barrier: true.

The realized semantics are included in the global worker-authority policy
fingerprint. Widening them invalidates existing Supervisor selection snapshots.

## Database migration

Migration `0032_computer_worker_read`:

- adds `computer_run` to the task-kind allowlist;
- adds immutable `tasks.computer_spec`;
- extends the Agent execution task-kind guard;
- rejects inserts/updates that make `computer_run` Agent-less; and
- preserves all prior task and running-attempt triggers.

## Live Zelo-host qualification

A disposable real OpenBot namespace was used with the exact pinned image.

Proof:

```text
create custom computer Agent
-> grant Core Files permission
-> start real persistent OpenBot computer
-> seed qualification/proof.txt
-> submit Agent computer_run(files_read)
-> claim revalidates Agent + Worker + permission + backend identity
-> ComputerRuntime reads through the real OpenBot computer
-> task succeeds with exact marker
-> submit second files_read
-> revoke Files permission
-> claim cancels task
-> error = computer_execution_spec_invalid
-> attempt count = 0
-> submit browser_read and claim it
-> owner takes human control
-> ComputerRuntime refuses the read with computer_human_control_active
-> owner hands control back
-> resume_snapshot_required = true
-> stop computer
-> remove disposable container/profile/workspace/supervisor
```

Marker returned through Zelo:

`ZELO-COMPUTER-READ-PROOF`

The qualification namespace was cleaned completely after the proof. Runner dispatch itself is covered independently by the Computer Worker tests, including successful read execution and failure while human control is active.

## Next gate

must not be enabled merely because read-only computer execution passed.
