# v0.15 — Exact-main-SHA release interlock (HOLD)

**State:** candidate release-safety improvement only. Zelo v0.15.0 is still
**NOT approved, tagged, published or ready to ship**. Last release: v0.14.0.

The existing `release_run` Task workflow already requires a separate
approval, current merge lineage and a GitHub annotated tag bound to the exact
main SHA. Those controls alone do **not** establish the Managing Director's
v0.15 milestone scope, four refused native Media proof disposition, completed
Space/Skill/Worker qualification, independent full-repo audit or operator
final release decision in issue #166.

This slice adds a second, milestone-specific **execution interlock**. By
default, every `v0.15.<patch>` tag, including `-rc` prereleases, refuses
with the stable code `v015_release_scope_approval_required` **before**
creating a Release Task approval or contacting GitHub.

## Trust boundaries

- `TaskService._submit_release` checks the operator-controlled exact
  `main` SHA after validating the existing successful Merge Task but
  **before** invoking GitHub readiness or persisting a new Release Task.
- `TaskService._valid_action` rechecks the pin at **operator approval, retry
  and Task claim**; an already approved Task becomes invalidated/cancelled if
  its release SHA is subsequently revoked, before any Runner dispatch.
- `PromotionReleaseRuntime.verify_ready` independently rechecks the
  same milestone gate **before** any provider GET. `run` always calls
  `verify_ready` before a GitHub POST, so existing/pending approvals do
  not bypass a subsequently revoked or stale release pin.
- The optional host-only setting
  `ZELO_V015_RELEASE_APPROVED_MAIN_SHA` maps to
  `Settings.v015_release_approved_main_sha`. Default is **unset**. It
  accepts exactly 40 lowercase hex characters. A different, malformed,
  absent or stale SHA is refused, even when a generic Merge/Release Task
  was separately approved.
- Matching the host pin **only lifts this interlock**. It is not evidence
  that issue #166's checks passed and it never substitutes for existing
  exact-head GitHub checks, Task approval, operator scope decision,
  external independent review or release governance. **Do not configure
  it until the independent candidate-head audit and explicit Managing
  Director approval have been recorded.**
- Other historical release versions keep their existing authorization
  semantics. No new model Tool, GitHub ability, credential, Worker
  permission or automatic release path is introduced.

## Verification

Tests confirm refusals for v0.15.0, prereleases and patch tags before even
a provider GET; default-deny at Task submission before an approval record;
incorrect/stale pins refused; an exact pin performs existing *read-only*
readiness checks without creating a tag; older tags retain strict main
head checks and exact Task approval.

This is deliberately **not** a release approval artifact. The final
approved `main` SHA can only be decided once the remaining v0.15 Space,
publication, Media, Worker, third-party, CI and independent audit gates are
resolved and the Managing Director explicitly authorizes the milestone.

UI PR #61 and the four exhausted refused Media native-reader proof attempts
remain unchanged. The current work does not request another Media proof or
authorize automatic learned-Skill publication.
