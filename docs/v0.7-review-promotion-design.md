# Zelo Core v0.7 — Review & Promotion Design

Status: design baseline for `feat/v0.7-review-promotion`.

## Goal

v0.7 turns a successful v0.6 Developer Agent result into a separately reviewed and explicitly approved promotion flow. The coding worker never receives GitHub credentials or promotion authority. Zelo owns review, exact-result binding, commit creation, branch push, pull-request creation, CI verification, merge, and release tagging.

## Non-goals

- No autonomous merge without a separate operator approval.
- No autonomous release tag without a separate operator approval.
- No worker access to GitHub credentials.
- No force-push, branch deletion, history rewrite, rebase, or arbitrary remote.
- No promotion from a failed, cancelled, interrupted, boundary-failed, or validation-failed Developer attempt.
- No promotion from an unverified or mutated retained workspace.

## Promotion stages

1. Developer execution approval — existing v0.6 behavior.
2. Review candidate — Zelo computes an immutable candidate manifest and review fingerprint.
3. Promotion approval — binds the exact candidate, base SHA, target repository, target base branch, commit metadata, proposed branch, and PR metadata.
4. Promotion execution — Zelo re-verifies the candidate, creates the trusted commit, pushes the exact branch, and opens the PR.
5. CI verification — Zelo records the exact PR number/head SHA and required check conclusions.
6. Merge approval — binds the exact repository, PR number, base branch, head SHA, merge method, and successful CI snapshot.
7. Merge execution — squash merge only if the PR head/base and CI snapshot still match.
8. Release approval — binds an exact merged `main` SHA and semantic version tag.
9. Tag execution — creates only that approved tag on that exact SHA.

Every later stage fails closed if any earlier bound value changes.

## Trust boundaries

### Worker boundary

Codex/other DeveloperWorker implementations may only modify the isolated developer repository already defined by v0.6. They must never receive:

- GitHub token or `gh` authentication state,
- writable access to the primary checkout,
- writable access to promotion records,
- permission to commit, push, open/merge PRs, or create tags.

### Zelo promotion boundary

Only trusted Zelo code may:

- read the retained developer workspace after execution,
- compute the promotion candidate manifest,
- create the trusted commit,
- authenticate to GitHub,
- push the approved branch,
- create the PR,
- inspect CI,
- merge,
- tag.

External actions always require the matching approval stage.

## Immutable candidate

A successful Developer attempt produces a `PromotionReview` contract. The contract is frozen and persisted as JSON. It contains only bounded, reviewable metadata plus content hashes; it does not contain credentials.

Required identity fields:

- review schema/version,
- developer task ID,
- developer attempt ID,
- source repository identity,
- retained workspace relative path,
- approved base SHA,
- observed HEAD SHA,
- worker implementation/config/version identity,
- validation identity/profile/version,
- sandbox version,
- validation-passed flag,
- changed-file count,
- canonical candidate manifest,
- ignored-artifact inventory summary,
- review fingerprint.

### Candidate manifest

The base commit identifies every unchanged tracked file. The manifest therefore binds every material difference from the base.

Each entry is sorted by bytewise path and records:

- relative path,
- operation: `add`, `modify`, or `delete`,
- object type: regular file or symlink,
- Git-compatible mode,
- byte size for present objects,
- SHA-256 of exact file bytes or exact symlink-target bytes for present objects.

Renames are normalized to delete+add. Paths must be valid repository-relative UTF-8, must not traverse, and must not contain nested Git metadata. Special files are forbidden.

Untracked non-ignored source files are represented as `add` entries. Ignored generated artifacts are not promoted. Their bounded inventory is included in the review metadata so the review records what existed during validation.

## Review fingerprint

`review_fingerprint` is SHA-256 over canonical JSON using sorted keys, fixed separators, ASCII escaping, and no non-finite numbers.

The hashed object includes:

```text
review_version
developer_task_id
developer_attempt_id
source_repository
workspace
base_sha
head_sha
worker_identity
validation_identity
validation_profile
validation_version
sandbox_version
validation_passed
candidate_manifest
ignored_artifact_summary
```

The fingerprint is content identity, not an authorization token.

Before any commit, push, PR, merge, or tag action, Zelo re-computes the relevant identity and compares it with the approved fingerprint/specification. Mismatch invalidates the action.

## Promotion task contract

v0.7 will introduce a separate promotion task rather than extending `developer_run` authority.

Proposed task kind:

`promotion_run`

Submission references a completed Developer attempt and includes bounded operator-controlled metadata:

- developer task ID,
- developer attempt ID,
- target base branch, initially only `main`,
- proposed branch name under a Zelo-owned prefix,
- commit title/message,
- PR title/body.

At submission, Zelo:

1. loads the exact completed attempt,
2. verifies it succeeded and validation passed,
3. verifies the retained workspace is still owned by that attempt,
4. computes `PromotionReview`,
5. builds a frozen `PromotionRequest`,
6. binds the request into the existing action hash,
7. places the task in `awaiting_approval`.

Approval never binds merely to a workspace path. It binds to the immutable review fingerprint and exact external action specification.

## Promotion execution invariants

Immediately before trusted commit creation, Zelo must:

- re-verify workspace ownership,
- re-compute the candidate manifest,
- require the same review fingerprint,
- require HEAD == approved base SHA,
- require no worker-created commits,
- require validation identity unchanged,
- re-run the trusted validation profile against the exact candidate,
- require validation success,
- verify the primary checkout remains unchanged.

Trusted commit creation must not execute repository hooks, filters, textconv, credential helpers, pagers, fsmonitor, includes, or worker-controlled Git config.

The promotion branch must:

- use a deterministic Zelo-owned prefix,
- be created from the approved base SHA,
- contain exactly one trusted promotion commit for the approved candidate,
- never use force push,
- never overwrite an unrelated existing branch.

The initial target repository is the configured Zelo repository only. Arbitrary repository URLs and arbitrary remotes are forbidden.

## PR and CI identity

After push, Zelo opens exactly one PR from the approved promotion branch to the approved base branch and persists:

- repository identity,
- PR number,
- PR URL,
- base branch/SHA,
- head branch/SHA.

CI verification must query GitHub for the exact PR head SHA. A green result for another SHA is not sufficient.

The merge approval binds:

- repository identity,
- PR number,
- base branch,
- exact head SHA,
- merge method = squash,
- required checks and their successful conclusions,
- CI verification timestamp/config version.

If the PR head moves, base changes, checks regress, PR closes, or mergeability changes, the approval is invalid.

## Release identity

Release/tagging is a separate action after merge. The approval binds:

- repository identity,
- exact merged `main` SHA,
- exact semantic version tag,
- tag target type = commit.

Tag creation fails if:

- `main` no longer points at the approved SHA,
- the tag already exists with another target,
- the tag format is invalid,
- the preceding merge record does not identify the approved SHA.

## Persistence

Prefer existing task/attempt/approval/audit primitives.

Add a nullable `promotion_spec` JSON field to `tasks`, analogous to `developer_spec`, for the frozen approved external-action specification. Avoid a new general workflow engine in v0.7.

Persist only bounded review metadata and fingerprints. Do not persist GitHub tokens, raw credential material, or hidden model reasoning.

## Audit events

Expected events include:

- `promotion_review_created`
- `promotion_approval_created`
- `promotion_started`
- `promotion_reverified`
- `promotion_commit_created`
- `promotion_branch_pushed`
- `promotion_pr_created`
- `promotion_ci_verified`
- `promotion_failed`
- `promotion_completed`
- `merge_approval_created`
- `merge_reverified`
- `merge_completed`
- `release_approval_created`
- `release_reverified`
- `release_tag_created`

Audit details contain identifiers, SHAs, bounded names, statuses, and fixed diagnostic codes only.

## Failure and recovery

All external actions must be idempotent or safely discoverable after restart.

Examples:

- If commit creation succeeds but push does not, retry must reuse/verify the exact commit rather than create a different one.
- If push succeeds but PR creation response is lost, retry must discover the exact branch/PR and verify its head before continuing.
- If a PR already exists for the approved exact head/base, reuse it.
- Never infer success solely from a previous audit event; re-read Git/GitHub state.
- Never clean up or delete remote state automatically in v0.7.

## Initial implementation order

1. Frozen review/promotion contracts and canonical candidate-manifest hashing.
2. Tests for path, symlink, binary, deletion, rename normalization, mutation detection, and deterministic fingerprints.
3. `promotion_run` task schema, persistence migration, and approval binding.
4. Reverification + trusted commit creation.
5. Safe branch push + PR creation.
6. Exact-head CI verification.
7. Separate merge approval and squash merge.
8. Separate release approval and tag creation.
9. Recovery/idempotency tests.
10. One controlled end-to-end promotion smoke after the full test suite is green.

## Security acceptance criteria

v0.7 is not releasable unless tests demonstrate:

- worker cannot access promotion credentials,
- worker cannot commit/push/merge/tag,
- workspace mutation after review invalidates promotion,
- approval cannot be replayed against different code/branch/PR/SHA,
- executable Git configuration cannot run,
- symlink/path/nested-Git attacks fail closed,
- validation is rerun before promotion,
- CI is checked for the exact PR head SHA,
- merge requires a separate exact-head approval,
- release tag requires a separate exact-main-SHA approval,
- no force push or arbitrary remote is possible,
- protected primary state and pre-existing untracked files remain unchanged.
