# v0.15 — Governed learned-skill publication *intent* (offline)

## Scope and non-authority

`SkillPublicationIntent` is an immutable, deterministic, **inert** binding
of one live, accepted skill-learning proposal to its trusted review,
AgentInstance, source Skill, procedure, content-addressed artifact, promotion
repository, expected promoted predecessor and exact revision version.
It contains no executable instructions, network calls or available bypass to
the existing generic learned-file publication refusal.

An authorized operator may request
`prepare_skill_publication_intent(store, proposal_id, principal)` in code.
No API route, Task kind, GitHub publisher/merger integration, runtime skill
activation, Worker/Tool grant, filesystem write or durable claim exists.
The helper obtains all fields from existing trusted Core state and does not
accept caller-supplied digests, repository, branches or GitHub PR references.

The intent holds:
- immutable proposal, review, AgentInstance and source Skill identity;
- frozen procedure version and content SHA-256;
- content-addressed artifact path, artifact SHA-256 and bounded byte count;
- configured trusted promotion repository;
- for v1, *no* predecessor; for vN+1, exact verified promoted revision hash
  and trusted promotion-link fingerprint for the immediate predecessor;
- a deterministic SHA-256 fingerprint over every intent field except the
  fingerprint itself;
- `publication_authority=false`, `runtime_authority=false`, and
  `tool_authority=false` as literal, unchangeable fields.

A valid intent is **only an exact preflight snapshot**. It cannot reserve
the promoted scope or permit external GitHub side effects. Two conflicting
previously accepted proposals may both construct distinct valid inert v1
intents until an actual promotion happens. When promotion advances, a
subsequent recheck rejects the stale candidate. A merged or paused candidate
cannot be prepared as a fresh publication intent.

The intent contract itself verifies the fingerprint and exact
`skills/procedures/<skill>/<procedure>/vN-<digest>.json` path. That
is tamper evidence, not evidence that an untrusted constructor has
authorization. Consumers **must** reconstruct from Core's verified store;
accepting a self-computed fingerprint from an external caller as proof
would bypass the intended trust boundary.

## Subsequent local exclusive-claim candidate

The distinct `SkillPublicationClaimService` uses this same read-only intent
contract as its source of trusted identity and stores an immutable,
operator-only, one-slot-at-a-time **local** reservation. See
`docs/v0.15-skill-publication-exclusive-claim.md`. It does not alter this
intent's non-authority and is neither an external GitHub publication claim
nor permission to activate a learned skill. Generic protected-file merge
refusal remains enabled until a separately reviewed publication-specific
path is built.

## Later gates required before any publication

1. Durable, operator-approved, **exclusive** publication reservation that
   serializes competing proposals, includes exact review/agent/skill identity
   and expected promoted predecessor, and supports crash/uncertain-result
   recovery without silently deleting historical claims.
2. A separate learned-skill-specific GitHub publication workflow that
   locks repository, approved PR/head, artifact digest, exact premerge CI,
   approved merge request and reservation identity; reverify immediately
   before a network side effect and bind retries to one identical action.
3. Post-merge reconciliation that confirms remote merged identity and only
   then records an immutable local promotion proof. An ambiguous external
   result must fail closed and preserve investigation evidence.
4. Independent operator decision for any **runtime** skill loading or
   widening of Agent/Worker/Tool authority.

The generic `PromotionMergeRuntime` learned-file refusal from PR #111
remains in force and is not overridden by this contract. This is not a
shortcut around earlier unfinished v0.15 Media qualification. The four
retained native-reader refusals remain consumed, and UI PR #61 stays parked.

## Qualification

- Accepted and current v1 and v2 lineage produce stable identities;
- artifact and review digests are derived from authoritative Core records;
- unreviewed, wrong-operator, unconfigured-repository, already-promoted,
  agent-paused and stale competing candidates refuse;
- forged model fields, repository, path, authority flags or SHA-256 digest
  refuse during strict model validation;
- tests prove two competing valid intents remain non-authoritative;
- no new database migration, external API, Task or live learned-skill
  activation is introduced; full exact-head CI and code review are required
  before any later merge.
