# Zelo Core v0.15 — Python Worker

## Status

Fifth bounded implementation slice of the v0.15 Capability and skills ecosystem.

Merged prerequisites:

- Capability Registry — PR #55;
- Skill Registry — PR #56;
- Generic Worker Registry — PR #57;
- Research Worker — PR #58.

## Goal

Add a real Python Worker for bounded computation without turning Python into a shell,
filesystem, network, credential, or Zelo-authority escape hatch.

The key rule is:

> Python computes; Zelo Core decides and owns every authority boundary.

## Trusted worker contract

The built-in Python Worker is:

- worker ID: `python_core`;
- role: `python`;
- capability: `python_execution`;
- authority: `isolated-compute`;
- realized authority profile: `isolated-compute-no-network-v1`;
- backend: `PythonRuntime`.

No new default AgentSpec or department is introduced in this slice. `python_run` is a
Core worker/task surface; future trusted AgentSpecs may require it through the normal
WorkerRequirement contract without Python itself becoming an organizational agent.
The `python_execution` procedure is represented in the trusted Skill Registry.

No capability, Agent title, submitted payload, or model output may choose a worker,
authority profile, executable, sandbox mount, environment, or resource limit.

## Execution boundary

`python_run` accepts only bounded `code`, optional `stdin`, and a task timeout.
Core wraps that code in a trusted bootstrap and starts the fixed system Python with
`-I -S` inside Bubblewrap.

The sandbox has:

- a fresh network namespace with no network access;
- no Zelo workspace mount, only an empty read-only `/workspace`;
- read-only sandbox root, `/tmp`, `/proc`, and `/dev` mount surfaces;
- no credentials or inherited user configuration;
- only the fixed Python interpreter, standard library and required runtime libraries;
- no shell binary;
- no writable filesystem surface.

The trusted bootstrap also sets memory, CPU, file-size, open-file and process limits
before compiling or executing submitted code.

## Persisted execution identity

Migration `0027_python_worker_selection` adds `tasks.python_spec` and extends the
trusted task-kind constraint with `python_run` while preserving task-table and
running-attempt triggers.

Submission persists the exact `WorkerSelectionSnapshot`; action identity includes that
snapshot. Retry performs a fresh trusted selection. Claim revalidates registry,
authority policy, Agent WorkerRequirement and action hash before creating a RUNNING
attempt. Runner repeats exact selection validation before resolving the backend.

A pre-v0.15/persisted Python task without `python_spec` therefore fails closed at claim.
Operator retry is the only path that rebinds it to current trusted worker identity.

Adding `isolated-compute` advances the global worker authority policy schema to v3.
Existing pending worker snapshots from an older policy version fail closed and require
normal retry/reselection rather than silently inheriting new authority semantics.

## Non-goals

This slice does not add workspace reads/writes, package installation, public web or API
access, credentials, shell authority, browser/computer control, arbitrary executable
selection, or Python access to Zelo Core internals.

Python remains an exclusive non-developer task under the existing scheduler semantics;
this slice does not add a new concurrent non-developer scheduler.
