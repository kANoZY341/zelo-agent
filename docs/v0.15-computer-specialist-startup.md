# v0.15 — Operator-selected Computer Specialist

This adds a usable Computer Agent to **normal Core application startup**. It
reuses the existing Skill/Capability registries, AgentInstance API, Computer
permissions, Task admission/Runner, Space gateway and persistent backend.
It does not inject test services or create a second execution system.

Status: local candidate, not a v0.15 release or production deployment. Final
exact-source review, full CI and post-merge qualification remain required.

## Scope and identity

The fixed `computer_observer` Specialist can submit only `computer_run` Tasks
with the `computer_read` capability and existing `computer_observation` Skill.
Its Computer profile permits browser observation and file reads/lists, not
navigation, clicking, typing, writes, shell, delegation or Skill self-promotion.
It is eligible for the logical `workroom` Space only. That eligibility alone
creates **no** resource, intent, activation or effective file access.

The opt-in SHA-256 pins the **entire** selected Agent Registry, including the
unchanged Coding/Research templates. It is not a model-supplied AgentSpec.
Creating a Specialist leaves its persisted Computer permissions disabled.
One active `computer_observer` instance is permitted per Project; independent
Projects retain separate AgentInstance identities and Computers.

## Operator startup

First inspect the fixed selection without loading `.env`, opening a database,
starting a service or granting permissions:

```bash
.venv/bin/python -m scripts.preview_computer_observer
```

After independently reviewing that output, set
`ZELO_COMPUTER_OBSERVER_APPROVED_REGISTRY_SHA256` to its exact
`approved_registry_sha256` value in the intended private operator environment.
Configure the already-supported pinned Computer backend using
[v0.15 Computer infrastructure](v0.15-agent-computer-openbot-foundation.md).
Do not use example credentials or overwrite an existing environment file.
Then use the normal migrated Core startup from the README:

```bash
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Absent approval leaves the normal registry unchanged. Wrong/stale approval,
a missing configured backend or incompatible live Agent bindings refuses
startup. The opt-in does not automatically retire, migrate or rewrite existing
Agents. Same-registry restarts preserve persisted identity. Disabling the
opt-in requires explicitly retiring **all** live instances bound to that
registry, including baseline roles created while it was enabled; history stays
intact. Separate YouTube pilot/company opt-ins cannot be silently combined
with this approval; a future combined registry needs its own reviewed design.

Read-only internal-network Computers start **no outbound proxy listener** when
no named navigation endpoints are configured. Existing named-navigation
configuration and per-Agent authority checks remain separate and unchanged.

## Normal authenticated operator workflow

Use the existing operator API; every mutation requires the operator token.

1. Create a Project with `POST /projects`, then create its Specialist with
   `POST /agents` and `agent_id="computer_observer"` plus that Project ID.
2. Review `GET /agents/{id}/computer`, explicitly grant only the intended
   `enabled`, `browser` and `files` fields through
   `PATCH /agents/{id}/computer/permissions`, then `POST .../computer/start`.
3. Submit `POST /agents/{id}/tasks` with an ordinary Task body, for example:

```json
{"task":{"kind":"computer_run","payload":{"action":"files_list"}}}
```

Read status/results at `GET /tasks/{task_id}`. The normal background Core Runner
claims and executes the Task; no direct call to a test Runner is needed.
Browser snapshots and `files_read` use the same path. Computer-relative file
paths refer to that Agent's persistent Computer workspace, not host paths.

For Space files, the owner first provisions the private, canonical root under
`runtime/spaces/{project_id}/workroom/{resource_id}` with safe ownership/modes.
The existing Space APIs then register that resource, create an operation-specific
intent and confirm it. Bind the returned activation ID in the Task payload as
`space_activation_id`; use a canonical resource-relative path. A `list` grant
never grants `read`, and neither grants writes. Revocation through
`POST /agents/{id}/space-activations/{activation_id}/revoke` prevents new work.
This feature does not supply a general filesystem upload/provisioning API.

Owner takeover/handback remains `POST .../computer/take` and `POST .../computer/release`.
Takeover rejects new work/retries, fences queued work, and invalidates in-flight
permission identity. Retrying after handback uses the atomic identity correction
in PR #187. `POST .../computer/stop` does not delete persistent volumes.

## Qualification and limits

Tests exercise normal application startup and its HTTP/Runner/storage paths,
using a controlled backend for deterministic regression. A separate disposable
Zelo-host proof uses real loopback TCP HTTP, the unmodified application lifespan,
background Runner and pinned native OpenBot/Chromium backend. It exercises
Computer Tasks, actual Space list/read/revocation, owner control, container
replacement with persistent files, and a second Core startup retaining Agent,
Task-result and revocation state. All temporary proof-owned resources are removed.

These proofs do not activate a production service, finish general Space rights,
qualify interactive browser mutation, enable Media/REA, or close the full v0.15
release gate. See [the canonical closeout ledger](v0.15-release-closeout.md).
