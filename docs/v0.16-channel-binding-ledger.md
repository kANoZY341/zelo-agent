# v0.16 — Operator channel binding and unverified inbound ledger

## Authority boundary

This is a **non-connected persistence slice** built on PR #108's transport-neutral
text-envelope contracts. It does not claim a WhatsApp/email sender is
authenticated, that a message can be admitted into Mind, or that any outbound
delivery is authorized.

The operator-approved binding service accepts only an authenticated Ahmad
OperatorPrincipal from trusted Core code. It stores an immutable mapping from
opaque channel/account/sender/thread identity to an **existing** Zelo
conversation. No external route is added. Binding an opaque identity is an
operator selection, not proof that the holder owns the provider account.

The unverified observation ledger records only scoped message fingerprint,
opaque provider message key, message text SHA-256 and original UTC timestamp.
The original message body, phone number, email address, credentials, attachments
and reply payloads are not stored in the channel ledger. Mind is never called;
there is no task execution and there is no send/delivery state. A plain text
SHA-256 is a content fingerprint, NOT encryption: common short phrases could
be guessed from their digest. Keep the SQLite database private and never expose
observed digests to a provider or an untrusted user.

## Replay and integrity

The full scoped thread identity is domain-separated. A message ID is bound to
that thread, so the same provider message ID in different threads produces
different fingerprints. Retrying the exact same metadata is idempotent; changing
content digest or provider timestamp under an existing identity fails closed.
An observation for an unbound thread fails closed. A thread may not be silently
remapped to another conversation.

SQLite enforces foreign keys, unique identities, lowercase hex digests and
operator/authority constraints. UPDATE/DELETE triggers make both tables
append-only, including attempts at no-op updates. Core reconstructs and
checks the deterministic fingerprints on reads.

These checks do not prove webhook authenticity. A future provider adapter must
verify provider signatures, timestamps and replay windows before any
provider-authenticated admission; a trusted account-binding policy must
separately decide which sources may reach Mind.

## Non-goals

- No WhatsApp, email, voice or call connection.
- No provider secret, contact lookup, webhook or external API request.
- No conversation turn, Core task, scheduler wake, worker capability or delivery.
- No send approvals, outbox, delivery receipts or message deletion.
- No automatic provider verification, account revocation or remapping.
- No change to learned-skill authority or UI PR #61.

## Next milestones

1. Strong provider-specific authenticity and verified account binding.
2. Atomic verified-ingress ledger transition and existing MindService turn
   admission under the reserved channel idempotency namespace.
3. Explicit Ahmad-controlled lifecycle and revocation for channel accounts.
4. Separate approval-gated outbound intent, delivery status and retry policy.
5. Qualified voice-note, browser voice and calling transport gates.

Until those gates are completed, this store is historical unverified metadata
only; it must not be used to infer delivery, operator identity or execution
authority.
