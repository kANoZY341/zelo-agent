# v0.16 — WhatsApp raw webhook signature foundation

## Current qualification

This is an **offline, transport-inert** integrity check. The pure function
`verify_whatsapp_webhook_signature` accepts the exact raw webhook body,
Meta's `X-Hub-Signature-256` header value and a trusted server-configured
Meta App Secret. It computes HMAC-SHA256 over the *unmodified bytes* and
compares the 32-byte digest using constant-time comparison. A missing,
malformed, mismatched or legacy SHA-1 signature fails closed. The input
body limit is currently 1 MiB; this limit must be qualified against the
selected provider settings before enabling a real listener.

Meta's documented Cloud API pattern sends the SHA-256 digest in a header
of the form `sha256=<lowercase-hex-digest>`; it is not interchangeable
with the separate GET webhook setup verification token.

References:
- https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/webhooks/start/
- https://developers.facebook.com/docs/graph-api/webhooks/getting-started/

The trusted future adapter, not the webhook payload or an HTTP caller,
must select the App Secret. A missing or weak configured secret is a
server-side error and does **not** produce a successful verification.

## Authority and replay limits

**A valid HMAC proves only that the exact body was signed with the
configured App Secret.** It does not prove that the sender is Ahmad or
that any provider phone number/account has been approved. The signature
does not independently establish the message's freshness or eliminate
replayed deliveries. Never infer `provider_authenticated=True` from this
function alone, and never pass its result directly to Mind execution or
delivery. In a future verified adapter, independently require:

1. Explicit operator-controlled and revocable provider-account binding,
   including app secret identity and intended WhatsApp Business Account
   and phone-number scope.
2. Typed, bounded message/event parsing after signature verification;
   refuse unsupported attachments and status-only events as text turns.
3. Timestamp/replay-window and durable message-ID deduplication using
   verified provider facts.
4. Atomic Mind admission with the reserved `channel:` namespace only
   after those checks; still no tool/task escalation from provider text.
5. Independent outbound approval, delivery accounting, and credentials.

Email/browser transports must have their own verified ingress gates.
There is no webhook HTTP listener, app secret storage, account onboarding,
outbound send, voice/call adapter or runtime skill activation here.
The parked UI and the existing Media qualification budget are unchanged.

## Verification

- Valid byte-for-byte Meta HMACs accepted.
- Raw body edits, equivalent JSON reserialization, wrong secret,
  wrong/legacy header, empty/badly typed/oversized payload refused.
- Boundary body limit and absent/weak server secret checked.
- No new execution, account identity or transport authority objects.
- Ruff, formatting, diff check and exact-head full CI required before
  eventual merge.
