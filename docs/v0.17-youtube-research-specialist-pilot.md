# v0.17 pilot — operator-pinned YouTube Research Specialist

This bounded Core feature introduces the **first real opt-in domain Specialist**
without launching an automatic organization or external social-media integration.
The initial actor uses Zelo's existing Research Worker and TaskService to produce
read-only, source-grounded research notes. It is **not** the VP → Director →
Manager → Specialist team creation flow, which still needs separate hierarchy,
Campaign budgeting, durable activation authority, per-agent computer access
review and revocation.

## Default behavior and explicit activation

The trusted default Agent Registry is **unchanged** when the operator does
nothing. Existing Coding and Research AgentSpecs, their exact registry version,
their instances and their Task revalidation path stay unchanged. No new Agent,
Task, OrganizationAssignment, computer, scheduler or resource is created by
shipping this source code.

The operator may inspect the proposed exact spec/digest in either of two ways:

- Authenticated GET `/agent-factory/optional-specialists/youtube-research`
- Offline CLI `.venv/bin/python -m scripts.preview_youtube_research_optin`

The preview states the baseline registry SHA-256, full canonical AgentSpec
SHA-256, current enablement and bounded capabilities. It **does not enable**
anything. To opt in, the operator must deliberately set a single startup
configuration value equal to that exact pinned candidate digest:

`ZELO_YOUTUBE_RESEARCH_APPROVED_SPEC_SHA256=<exact 64-hex SHA-256 from preview>`

The value is a public exact-version *approval identity*, not a bearer token.
Do not accept a value from untrusted web/model output. An absent value means
disabled. An incorrect/old/malformed digest fails startup instead of silently
switching specs. Any later material change to the AgentSpec changes its digest
and requires a fresh deliberate operator change.

Since AgentInstance snapshots bind to Zelo's **entire registry version**, adding
one trusted AgentSpec changes the version of all Agent bindings. On first
enablement, startup refuses any active or paused AgentInstance still bound to
the prior/different registry version. A normal restart with the **same exact
approved registry** and existing active/paused matching instances is accepted.
When disabling, startup refuses any live AgentInstance bound to the expanded
registry, including Coding/Research agents created while it was enabled.
Thus neither changing the opt-in nor removing it can silently stale a live
Agent. Disabled startup retains previous treatment of unrelated historical
stale bindings. The precondition is checked under the serialized SQLite writer
lock. Retired instances remain terminal and cannot be reactivated. Operators
must deliberately retire or separately migrate incompatible instances before
switching. No hidden row rewriting or compatibility bypass occurs.

## Exactly what is granted

This single-Specialist pilot deliberately uses the **distinct**
`youtube_topic_researcher` registry identity. The pinned Harness
`youtube_content` team blueprint already reserves `youtube_research` for
its **Manager** role. Reusing that ID for a pilot Specialist would block
future team design/activation checks or force an incompatible Agent registry
migration. A source-pinned regression verifies that all four Harness role
IDs remain available while the pilot is enabled.

The new active trusted `youtube_topic_researcher` AgentSpec has:

- Role and organizational level: `youtube_topic_researcher`, `specialist`;
- One `research_run` Task kind routed through the existing configured
  `research` Worker with `research` capability requirement;
- `evidence_synthesis` and `research` capabilities;
- The existing reviewed `evidence_retrieval` procedure and Skill;
- An explicit three-tool **read-only workspace allowlist**:
  `list_workspace_files`, `read_workspace_file`, `repo_status`,
  plus existing `workspace_read` permission. This includes access to
  operator-selected Zelo workspaces, not arbitrary host paths; do not mistake
  the Specialist for a public-web-only isolation boundary.
- A distinct `agent/youtube_topic_researcher` memory namespace, but no
  automatically admitted new memory or skill-learning authority;
- One active instance **per active Project** (not a global instance limit).

All of: `developer_run`, `shell_run`, `computer_run`,
`browser_run`, publication, YouTube credentials/channel API, financial
transactions, learned-skill promotion, agent hiring/delegation and Space grants
remain disallowed. No permanent org chart or Manager reports are created.
Neither the `instructions` string nor title grants a new Tool. The existing
Skill Registry checks the trusted Skill-to-tool compatibility and the
AgentActivationEvaluator must accept the worker/task/capability surface
before startup can finish.

At **real Research Worker execution**, TaskService first revalidates the
immutable project-bound `AgentExecutionBinding`. The Runner forwards that
binding only for bound Research Tasks. ResearchRuntime intersects its fixed
read-only tool catalog with the bound AgentSpec allowed Tools and adds the
trusted AgentSpec objective, version and instructions to the model's system
prompt. Operator question text stays a separate user message; retrieved
evidence is still untrusted Tool output. Since model-generated JSON does not
have to honor the advertised output schema, ResearchRuntime also checks every
requested Tool against the bound AgentSpec allowlist **before tool lookup,
request events, validation or execution**. A simulated malicious model action
requesting another research Tool is denied before dispatch, with a negative
regression asserting no forbidden effect. Plain unbound Core Research retains
its previous generic prompt and tool behavior. End-to-end fixture tests inspect
both the actual `ModelRequest.system_prompt` and allowed tool schema.

## Manual use after operator activation

With the server running on the explicitly opted-in configuration and no
historical live agent conflicts, an authenticated operator can:

1. POST `/projects` with a normal Project name and summary.
2. POST `/agents` with JSON `{"agent_id":"youtube_topic_researcher","project_id":"<Project UUID>"}`.
3. POST `/agents/<AgentInstance UUID>/tasks` with
   `{"task":{"kind":"research_run","payload":{"query":"Compare three public astronomy video ideas"}}}`.
4. Inspect the Task, Attempt, evidence and bounded results using normal Core
   endpoints. Pause or retire the instance using the existing
   `/agents/<instance_id>/transition` lifecycle route; pause/retire invalidates
   Task claims via the existing execution identity gate.

This uses existing operator authentication, per-Project instance limits,
TaskService bounded time/worker selection and pause/revocation semantics.
Direct research tasks do **not** become a Campaign-budgeted hierarchy just
because a role has a Specialist label. Shared Campaign spending/approval
before multi-agent team work remains separately required.

## Validation and release gates

- Default unchanged registry and absent opt-in;
- Invalid/stale candidate digest and malformed settings rejected;
- Active and paused historical AgentInstances block opt-in, retired remain
  terminal and preserved;
- HTTP preview requires the owner bearer token and creates no records;
- Active runtime startup requires passing AgentActivationEvaluator and
  SkillRegistry compatibility;
- Explicit authenticated AgentInstance creation and per-Project quota;
- Exact Research Task binding, idempotency, pause/claim rejection and
  refusal of Developer tasks from a Research Specialist;
- Full Ruff, related regression suite, independent security review,
  exact-head CI, followed by post-merge main CI before release.

No live YouTube account, uploads, credentials or outside service must be
connected for this slice. Never silently activate the optional spec in the
test/user's production runtime as part of verification. Leave UI PR #61,
REA runtime and the already-exhausted Media native-reader qualification
budget untouched.
