# v0.16 — Operator-selected WhatsApp account metadata (inert)

## Purpose and scope

This self-contained Core-only persistence gate follows the merged v0.16
channel-text and append-only observation foundations. It **does not**
authenticate an external provider or authorize admission of messages into
Mind. It records the operator's choice of a previously HMAC-pseudonymized
WhatsApp Business Account **and receiving phone** tuple and the trusted
Core-managed identity of the Meta App Secret chosen for that account.

The `account_key` must be a domain-separated keyed pseudonym derived from the
parsed WABA ID and receiving phone number using the Core identity key.
`app_secret_identity` is a separate opaque, 64-hex identity of the trusted
server-managed Meta App Secret selection. The service **does not** compute,
retrieve, or store the secret itself. Its identity must come from trusted
Core configuration, not attacker-controlled webhook text. Both identifiers
are recorded without raw provider account/phone/sender IDs or message bodies.

## Durable behavior

The private `ChannelOperatorAccountStore` permits only a trusted
`OperatorPrincipal` to:

- `select`: append exactly one account-to-secret selection; exact duplicate
  retries return the existing frozen snapshot, but secret-identity conflicts
  fail closed;
- `revoke`: append a one-time irrevocable refusal for that account key;
  repeated revoke requests return without mutation;
- `get`: read immutable selected metadata and the latest **revoked or
  selected** state; access is operator-only.

Both SQLite tables reject UPDATE/DELETE through triggers, validate lowercase
hex identities, require the known operator identity, and prohibit
`provider_authenticated`, `mind_admission_authority`, or
`delivery_authority` becoming true. SQLite `BEGIN IMMEDIATE` serializes
competing selection and revocation requests.

Revocation is **final for that opaque account key**. This increment does
not support unrevoking, silently rotating a trusted provider secret, or
reusing a revoked key. Any future re-onboarding under a new identity must
have its own separately approved versioned registration protocol.

## Authority and limitations

This stores only an operator's *selection* — not cryptographic provider
authentication. A real adapter would still need to verify the Meta webhook
HMAC over exact raw bytes with the currently configured secret, parse
untrusted provider facts, compare WABA and receiving-phone identity against
this ledger, enforce replay/freshness controls, and revalidate revocation
immediately before any admitted Mind turn.

There are no HTTP routes, external listeners, Meta API tokens, credential
persistence, outbound sends, voice/call transports, Mind turns, runtime
skill loaders, or Worker/Tool privilege changes. The account selection does
not mutate or reclassify the existing unverified thread bindings or message
observations, and no agent can invoke its methods as a new tool.

The original four Media native-reader qualification attempts are preserved
as refusals; no fifth attempt is authorized. The UI PR #61 remains parked.

## Qualification

- One selected record for concurrent identical requests;
- conflicting secret selections fail closed;
- irreversible append-only revocation with idempotent retry;
- SQLite check and FK guards against direct tampering;
- no original provider account/phone data, messages or Meta secrets persisted;
- wrong/malformed input or non-operator access rejected;
- migrations preserve earlier append-only triggers and existing data;
- Ruff check, formatting, exact-head CI and final source review before merge.
