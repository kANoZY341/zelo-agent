## Trusted operator setup

Default configuration disables Browser Worker and has an empty browser-origin
registry. API endpoints do not automatically authorize document browsing. Only
trusted application assembly may configure canonical approved HTTPS origins,
verified bundle, exact local sha256 image, captured manifest, generated seccomp
profile and one persistent private admission directory shared across processes.

Provide a separate explicit operator preparation path for a reusable local image
and its content-verified receipt. Runtime never builds, pulls, chooses image tags
or removes that reusable image. Any serialized operator receipt is configuration,
not a signature or independent provenance claim. Validate its schema/bounds and
all contract identities; retain the stopped-image filesystem verification gate.
No model/task field may select receipts, images, paths, mounts, flags, Docker
contexts, profiles, runtime directories or policy. No system-service installation,
production database modification or live `.env` update is part of development.

## Task and persisted execution identity

- Introduce a narrow `browser_run` input: approved endpoint ID, strict relative
  document path, and bounded timeout only. No absolute URL, query, method, header,
  cookie, credentials, navigation, script, screenshot, clicks or downloads.
- Add typed BrowserExecutionSpec and result models. Bind exact endpoint registry/
  origin, worker selection, complete RendererContract digest, renderer/broker/
  resource identities and prepared image/artifact/profile identity into persisted
  task authority and action hashing. Task callers cannot author these bindings.
- Preserve original source origin/path/digest, full contract and broker policy
  digests, node count, truncation and `instruction_trust="none"` in bounded evidence.
  DOM text is not a CSS visibility or complete-page claim.
- Extend the next task migration and immutable database guards without weakening
  existing kinds, Agent execution bindings, campaign/delegation scope or approvals.
- On retry, select and bind fresh trusted configuration. At claim and again in
  Runner, revalidate persisted identity against current worker/configuration;
  drift fails closed before DNS, Docker or pipe work. Reuse API/Python patterns.
- Add a narrowly described worker authority/capability. Register it only when all
  explicit operator prerequisites validate. Do not add a default AgentSpec,
  department, Mind routing surface or broad browser authority in this slice.

## Lifecycle and availability

One canonical AdmissionController/ResourceOwner remains the sole cross-process
browser capacity boundary. Core concurrency counters cannot replace its lock or
crash marker. The complete renderer contract is admitted before DNS, fetch or
container creation. Every execution constructs a fresh one-shot renderer while
sharing the same trusted persistent admission directory.

Propagate cancellation and task deadlines through the composed job. Return or
persist successful evidence only after HTTP/DNS, container, local CLI children and
reader tasks have confirmed cleanup. Unknown cleanup remains fenced; task retry,
application restart, database state or TTL cannot silently clear the marker. Do
not infer ownership from stale PIDs or remove unrelated resources. Explicit
operator fence reconciliation requires its own design; do not invent it here.

Keep native Chromium sandboxing, private pipe/blank context, scripts disabled,
no-network/read-only/nonroot/cap-drop ALL/NNP and qualified cgroup/profile limits.
No privileged or no-sandbox fallback. Keep deterministic CI offline; Docker tests
remain explicit host opt-ins. Do not expose browser internals through task results.

## Implemented operator setup

The adapter is `app/browser_worker.py`; `configured_browser_runtime(Settings)` is
its real assembly path. Disabled configuration returns without opening a receipt,
scanning artifacts, creating an admission controller or constructing a renderer.
Enabled configuration fails startup unless every prerequisite validates. No new
runtime dependencies are required.

Preparation is an explicit operator command, **not run by this implementation
session**. After qualifying local source artifacts and supplying their trusted
manifest digest, use a NEW absolute destination under a trusted private parent:

```sh
python -m scripts.prepare_browser_worker \
  --allow-owned-image-preparation \
  --bundle /absolute/private/qualified-source \
  --expected-bundle-digest <trusted-64-hex-source-manifest-digest> \
  --destination /absolute/private/browser-prepared \
  --endpoint docs=https://docs.example.com
```

The command reuses `scripts.qualify_browser_renderer.prepare_candidate`: verifies
the source bundle, compiles the fixed bootstrap, builds with no network/no pull,
exports an unstarted exact-image container, and verifies actual archive payload
bytes/modes against the full expected inventory. It never extracts the archive.
Only a successfully verified reusable image is preserved by setup cleanup; owned
setup containers and unsuccessful images are eligible for that helper's labelled
cleanup. Setup failures are not runtime authorization and require operator review.
The command does not start Core or a browser, install services or activate a worker.

The resulting `verified-receipt.json` is a private 0600 regular file. It contains
`schema="zelo-browser-operator-v1"`, the complete serialized `RendererContract`
(profile bytes encoded as lowercase hex), `image_payload` mapping paths to
size/mode/SHA256, and the canonical `image_payload_digest`. The runtime loader
accepts at most 2 MiB, requires exact keys/types and all existing contract
invariants, rejects duplicates/nonfinite values/symlinks/unsafe file modes,
rescans the bundle and checks the full image inventory identity. **These runtime
structural checks are not image verification, signatures or independent
provenance**; the preceding stopped-image inspection is the operator evidence.
Same-UID operators, local filesystem ancestors and Docker daemon remain trusted.

Configure all five operator settings shown in `.env.example`: separate
`ZELO_BROWSER_WORKER_ENDPOINTS`, `ZELO_BROWSER_WORKER_RECEIPT`,
`ZELO_BROWSER_WORKER_BUNDLE`, `ZELO_BROWSER_WORKER_RUNTIME`, and
`ZELO_BROWSER_WORKER_ADMISSION`. All paths must be absolute/canonical; runtime and
admission directories must already be owned by this UID and mode 0700. The prepared
bundle is `browser-prepared/build/bundle`; the command creates `runtime` and
`admission` siblings. Use the same persistent admission path across processes and
restarts. Only after separate acceptance/host/release gates may the operator set
`ZELO_BROWSER_WORKER_ENABLED=true`. Do not enable it as part of this slice.

Full contract, origin registry/exact endpoint, worker selection, operator receipt,
canonical bundle/runtime/admission paths and adapter version are bound into the
persisted specification/action hash, alongside exact document path/timeout.
Retry binds fresh trusted identity. Claim and Runner reject drift before DNS or
Docker. The qualified Docker handle retains its immediate pre-start exact image,
container and profile checks under admission; no runtime preparation is added.

Migration 0029 preserves every prior task/attempt trigger, extending only the
Agent task-kind guard with `browser_run`, and adds browser specification immutability
within each action. Rebinding is allowed only on a terminal failed/cancelled/
interrupted action transitioning to pending with the next action version. Existing
Agent identity, project, campaign and delegation checks remain in effect. The
pre-existing SQL kind guard still excludes API/Python Agent-bound inserts; this
slice does not silently change that unrelated authority boundary.

Task deadline starts before Runner identity revalidation and clips the renderer's
broker/pipe deadline. ResourceOwner owns cancellation and cleanup; retained owners
are tracked through application shutdown. Unknown cleanup leaves the persistent
marker fenced and shutdown reports `browser_cleanup_unproven`. Busy admission owns
no resources. No marker reconciliation, TTL or stale-PID shortcut exists.

Offline Core tests use actual task migrations, registry/Runner and qualified
renderer/ResourceOwner with deterministic HTTP and container-handle fixtures.
Preparation tests simulate the setup helper; existing archive tests validate the
actual verifier algorithm. Neither proves a live image/container/browser. Parent
owns `scripts/qualify_browser_core_binding.py`, its host fixtures, controlled host
probes, clean full pytest, independent exact-head review and exact-head CI. See
[implementation handoff](reviews/browser-core-binding-implementation.md).
