# Zelo Core v0.14 — Hierarchy-aware bounded child creation

## Status

Sixth bounded implementation slice of v0.14 Agent Factory.

Merged prerequisites:

- registry foundation: PR #47;
- project-bound lifecycle: PR #48;
- bounded task delegation: PR #49;
- generic agent execution identity: PR #50;
- durable organizational hierarchy: PR #51.

## Goal

Allow authorized factory-managed executives/managers to create one trusted
permanent subordinate at the next organizational level while preserving all
existing Core task, Campaign, budget, delegation and audit boundaries.

Permanent organizational creation is intentionally stricter than temporary task
delegation.

## Authority requirement

A parent may create a permanent child only when its trusted AgentSpec has all of:

- `allow_subagents = true`;
- remaining `max_subagents` capacity;
- explicit `organization_hire` permission.

This prevents ordinary delegation authority from silently becoming hiring/
organization authority.

## Allowed hierarchy

Only the next permanent level can be created:

```text
VP       -> Director
Director -> Manager
Manager  -> Specialist
```

A Specialist cannot create a permanent organizational child.

The child AgentSpec must already exist in the trusted active registry and its
`organizational_level` must exactly match the required next level.

Model output cannot create or mutate AgentSpecs in this slice.

## Organization scope

The child must be placed inside the parent's existing reporting scope:

- VP creates a Director only in a department under the VP's division;
- Director creates a Manager only in a team under the Director's department;
- Manager creates a Specialist only in the Manager's own team.

Creation never changes the parent's reporting assignment.

## Project, Campaign and delegation

Parent and child remain in the same active Project.

Every creation also requires one active Campaign in that Project and an exact
reserved, unexpired Campaign budget reservation owned by the parent instance.

The permanent reporting assignment and the temporary task-delegation contract
remain separate records.

Task delegation still carries:

- bounded objective;
- allowed Core task kinds;
- required child capabilities;
- Campaign ownership;
- budget proof;
- inherited depth/max-depth.

A later delegation revocation does not erase the historical fact that the child
was created as an organizational subordinate.

## Atomic transaction

A successful factory child creation persists, in one database transaction:

1. child `AgentInstance`;
2. initial child lifecycle event;
3. child `OrganizationAssignment`;
4. initial bounded `AgentDelegation`;
5. immutable `AgentChildCreation` receipt.

If any hierarchy, registry, Project, Campaign, budget, capability, depth or
instance-limit check fails, none of those records is persisted.

## Idempotency

The request is fingerprinted over all material creation/delegation inputs.

Reusing the same parent + idempotency key with the same request returns the
existing receipt.

Reusing the key with a changed request fails closed.

## Persistence

Migration `0025_hierarchy_child_creation` adds
`agent_child_creations`.

The receipt binds:

- parent instance;
- parent reporting assignment;
- child instance;
- child reporting assignment;
- initial delegation;
- idempotency key;
- request fingerprint;
- creation timestamp.

Receipts are immutable and cannot be deleted.

The database relation guard requires all linked parent/child instances,
assignments and delegation to be active and mutually consistent when the receipt
is created.

## Non-goals

This slice does not:

- create new AgentSpecs from prompts or model output;
- allow hierarchy-level skipping;
- let Specialist Agents permanently hire reports;
- grant tool/worker authority based on title;
- create Zelo CEO or the human Managing Director;
- add new Core task kinds;
- automatically execute the child after creation;
- enable unrestricted recursive spawning;
- add automatic memory writes;
- bypass Campaign budgets, approvals, scheduler, promotion, merge or release.
