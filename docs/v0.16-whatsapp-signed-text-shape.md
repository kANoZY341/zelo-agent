# v0.16 — Strict, signed WhatsApp text shape (offline)

## Inputs and scope

`extract_signed_whatsapp_text_event` is a pure, network-disabled adapter
foundation stacked on the offline HMAC verifier. It accepts only a byte-for-byte
Meta `X-Hub-Signature-256` authenticated payload and extracts exactly one
inbound **text** event using the documented WhatsApp Business Account webhook
shape. It is not a webhook listener, bound provider account, Mind turn, Tool
action, provider message receiver or delivery mechanism.

Source shape: Meta WhatsApp Business Platform's Webhook Payload Reference,
including `object`, `entry[].id`, `changes[].field`, `value.metadata.
phone_number_id`, and `value.messages[]` with `from/id/timestamp/type/text`.

- https://www.postman.com/meta/whatsapp-business-platform/folder/vzaxn16/webhook-payload-reference
- https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/payload-examples

For the first narrowly reviewed slice, **exactly one entry, change and
message** is supported. If a payload contains multiple entry/change/message
records, unsupported media types, contradictory contacts, mismatched product
identifiers, malformed timestamps, simultaneous text-plus-media fields, or a
mixed message/status event, the complete extraction fails closed; it never
silently uses the first event.

Legitimate **status-only** signed payloads return `None`, never an inbound
text turn. In this version they do not update any delivery record; a future
outbound receipt service must have separate verified handling. Duplicate JSON
keys, malformed UTF-8, NaN/Infinity, null bytes, oversized UTF-8 text, invalid
IDs, unpaired Unicode surrogates and unknown message types are refused.

Raw provider IDs and message text exist only as ephemeral in-memory *untrusted
facts*. The parser has no network call, file write, database write, logging,
credentials store, account lookup, signature bypass flag or dispatch to Mind.
No automatic forwarding to any Worker, Tool or external provider occurs.

## Essential safety restrictions

- A valid signature establishes body integrity under one configured Meta App
  Secret. It does **not** establish that the claimed account or sender is
  Ahmad's authorized channel identity.
- The provider's Unix timestamp is recorded only as a claimed UTC fact. The
  bounded calendar check is not a live clock, freshness window or replay check.
- A separately qualified provider adapter must cross-check WABA ID and phone
  ID against operator-controlled, revocable verified account grants, with
  durable replay defense, before calling a new Mind admission gate.
- Reuse the existing `ChannelTextIngress` and private channel observation
  ledger only after explicit authenticating/binding transitions; do not
  reinterpret their false authority fields as granted permissions.
- No message content is stored by this slice. The sender, timestamps,
  contacts or text may never be used as instructions to execute Core tasks.
- Real webhook resource/availability limits and delivery acknowledgements
  require separate operator qualification. Preserve UI PR #61 and the Media
  native-reader refusal ledger.

## Tests

Require valid signed text, optional matching contacts, status-only refusal,
whole-body rejection of batches/media/mixed payloads, HMAC verification
before JSON parsing, duplicate/malformed JSON refusal, strict ID/timestamp/text
bounds and no execution/delivery authority. Ruff, format, diff, exact-head CI
and code review remain the merge gates.
