# v0.16 — Offline verified WhatsApp text to reply-only Mind admission

This is a Core-only integration seam. It is **not wired into the ASGI app** and
does not expose a webhook, register Meta credentials, deliver replies, accept
voice, or submit Core tasks. The latest published release remains v0.15.0.

A trusted caller supplies the server-held Meta App Secret and an independent
Core identity secret. The adapter verifies the HMAC on exact raw bytes and
projects the one-text-event payload to opaque account, sender, thread, and
message keys. The selected account's stored App Secret identity must equal
an HMAC-derived identity of the supplied secret, keyed by the Core identity
secret. The account must remain selected, and the exact sender/thread must
have an immutable Ahmad-approved binding to an existing conversation.
The signed provider timestamp must be no more than 24 hours old or 5 minutes
in the future according to the trusted Core clock. That window is a local
replay admission policy, not a provider delivery guarantee.

A preflight avoids model work for obvious refusals. Mind may generate a
reply outside the database write transaction. Its new synchronous admission
hook then repeats the account, revocation, secret, binding, freshness, and
replay checks **inside the same serialized SQLite transaction** as the
ConversationTurn insert. The hook inserts an append-only
`whatsapp_verified_ingress` record linked to that turn. A revoked account
during model generation therefore leaves neither a verified record nor a
turn. A generated Core task action is rejected before commit. Exact retries
return the existing reply; changed text, timestamp, secret identity, or
turn link for the same scoped provider message ID fail closed. A preexisting
unverified observation or a preexisting unlinked `channel:` turn cannot be
silently upgraded to verified admission. Both ledgers exclude the other's
message identity at insert time, so a later unverified observation cannot
break exact verified retry. The adapter's secret pair and derived identity
are immutable for its lifetime; a replacement requires a new adapter and
a separately selected account identity.

The verified ledger stores opaque identities, text SHA-256, provider UTC
timestamp, admission UTC timestamp, trusted secret identity, and the Mind
turn ID. The Mind turn itself stores the original conversation text and
reply under the existing Mind retention rules. No raw provider account,
phone, sender ID, App Secret, signature, or webhook body is stored in the
new ledger. A text SHA-256 can reveal low-entropy phrases to someone with
database access; keep the Core database private.

This does not establish that a sender owns Ahmad's WhatsApp account.
The operator's explicit sender/thread binding is the local decision to
accept that provider-asserted identity. Live provider provisioning and
credential rotation, production webhook protection, outbound approval and
delivery, operational retries, voice, and calling require separate review
and qualification. Identity-secret rotation changes opaque keys and cannot
silently rebind historical selections.

Verification must cover signed success, exact retry, account/secret/thread
refusals, freshness, replay edits, existing unverified records, forged
unlinked turns, revocation during model generation, reply-only enforcement,
append-only database guards, and affected Mind/channel regression tests.
