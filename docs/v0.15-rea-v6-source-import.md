## Standalone source-build qualification

qualification copy, not via the Core/Mind/Agent worker system:

1. npm ci --ignore-scripts --no-audit --no-fund installed 374 packages
   from the committed npm lockfile. All npm install lifecycle scripts were
   disabled, and no global REA installation or MCP client registration ran.
2. npm run build:unlocked succeeded using Node v22.23.2, compiling 1,223

3. The compiled source's own CLI ran in a disposable, unprivileged, offline
   Docker container with no network, read-only root and target mounts,
   dropped capabilities, no-new-privileges, 384 MiB/no swap, one CPU and
   a 64-process limit. It analyzed a harmless two-file JavaScript fixture.
4. The result reported REA provider rea-javascript-application version 1,

   analyze_javascript_application and Evidence ID
   ev_0f2c503826e337eeac41e4791b41654cdcf3dffc4991b48bc2629b192e4fa617.
   The target JavaScript was not executed.

This demonstrates a local build and one static Linux analysis. It is not
a qualification of every REA tool, arbitrary hostile inputs, a persistent
computer, native engines, runtime capture, or all transitive dependencies.

## Verifiable local source integrity

The standalone no-network verifier is:

    .venv/bin/python -m scripts.verify_rea_source_vendor

It validates the fixed manifest SHA-256, upstream tag/commit/root tree,
the exact 2,082 file inventory, Git blob hashes and executable modes,
license notices, no extra files/symlink escape and the five optional engine
gitlink identities. The fast Python regression tests run in normal Core CI.

Intentional modifications to vendored source require a versioned feature
branch, reviewed new manifest/pinning and independent qualification. Never
silently alter upstream copyright, run setup scripts during Core startup or
assume that a source file gives itself Core authorization.

Zelo-owned adapters continue to follow standard Ruff validation; the
pinned upstream source tree is excluded from automatic Ruff reformatting.
Git whitespace checks exempt this upstream tree to preserve its original
bytes rather than masking errors in Zelo-owned code.

## Source verifier adversarial correction

Independent static review found two issues in the initial offline verifier:
special filesystem entries could be ignored during the extra-file scan, and an
oversized replacement file could be read into memory before enforcing the
aggregate limit. Both have been corrected: verification now refuses all
unexpected FIFOs/sockets/devices/symlinks and opens regular files with a
bounded pre-read limit and a post-read identity/change check. Adversarial tests
prove the oversized-file and special-entry refusal paths. The upstream source
tree and its manifest remain byte-for-byte unchanged.

A follow-up source-inventory hardening pass also bounds the manifest read
before JSON parsing, and rejects untracked empty directories. As a result,
the verifier requires an exact regular-file AND directory inventory, aside
from the five explicitly recorded empty optional external-engine gitlink
roots. Two additional regression tests cover an oversized manifest and an
unlisted empty directory. Neither change modifies upstream REA source or
enables runtime REA execution.

## Complete REA 6.0.0 MCP source tool inventory (metadata only)

An actual isolated no-network Docker execution of REA's **locally built
6.0.0 source** initialized its MCP server at protocol 2025-11-25 and
listed **139 distinct tool names**. The previous REA 5.0.0 npm-backed
proof listed 133; do not assume those older tool contracts still apply.

The fixed name-only inventory is at
`integrations/rea/tool-catalog-v6.0.0.json`, pinned to this exact
source revision with a SHA-256 regression check. Its records explicitly

A tool name is **not** a grant, availability proof for an optional native

  `extract_firmware`, `inspect_firmware_regions`;

  `inspect_electron_page`, `capture_web_screenshot`;

## Second source-build proof — offline from Zelo's own vendor tree

To prove that the import itself is sufficient (rather than a separate
upstream checkout), the qualification was independently repeated from the
exact files in Zelo's own `third_party/rea/` subtree:

1. Copy that already-verified subtree into an ignored disposable build
   directory, leaving tracked source bytes and legal notices untouched.
2. Run `npm ci --offline --ignore-scripts --no-audit --no-fund`
   using a **previously populated**, local npm cache. This run installed
   all 374 required packages without any registry request or install hooks.
   An initial source acquisition had populated the cache earlier; complete
   source ownership must not be confused with ownership of all dependencies.
3. Run `npm run build:unlocked` inside the disposable copy. The
   built source produced 945 JavaScript files, with Node v22.23.2.
4. Run the locally built CLI inside a pinned, no-network, read-only,
   unprivileged Docker Node guest with fixed memory/CPU/PID limits
   against a two-file harmless JavaScript fixture. REA returned a
   valid static Evidence response (one parsed file, one finding):
   `ev_228223c43d08d2c121f8107a6ff99951dacce7d4beccf36ec9b1a126944ee012`.
5. Confirm the Zelo source worktree remains clean and remove the disposable
   Docker guest. No globally installed REA package, external MCP endpoint,
   client configuration, user target, network request or Zelo execution
   permission was involved in the offline build/proof.

The offline cache remains an *acquired third-party dependency closure* and
is NOT checked into Zelo as REA source. Future production execution requires
a sealed, pinned, reviewed build artifact and appropriate per-tool authority.

## Model-facing self-inspection boundary

Zelo's existing self-improvement RepositoryInspector verifies the *whole*
repository's clean Git status and binds the complete HEAD commit, while its
model-facing tracked-path inventory deliberately excludes the copied
third_party/rea/ subtree. Those files have separately pinned source
integrity and include upstream AGENTS.md and .npmrc that must not be
treated as Zelo's own trusted instructions or configuration. Without this
exclusion, the copied tree made git ls-files -z exceed the existing 64 KiB
bounded process-output limit and blocked self-improvement. The change
does not loosen that limit, weaken Git cleanliness checks, or hide changes
to vendor source from the HEAD identity. A synthetic large-vendor
fixture verifies the previous output-limit failure and that the bounded,
trusted inventory remains usable.
