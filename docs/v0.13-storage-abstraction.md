# v0.13 — Storage abstraction

## Purpose

This final v0.13 slice makes Zelo Core depend on a Zelo-owned storage contract
instead of a concrete SQLite class.

The goal is portability, not a backend migration:

```text
Core services
  -> SessionStore
  -> configured CoreStorage backend
  -> SQLite today
  -> Postgres/Supabase later
  -> optional vector capability later
```

SQLite remains the only enabled backend in v0.13.

## Contracts

`SessionStore` is the service-level contract. It exposes only:

- `transaction()` for authoritative writes;
- `read()` for bounded reads.

Project, memory, campaign, scheduler, Mind, task and performance services depend
on this contract rather than on SQLite-specific paths, engines, PRAGMAs or file
locks.

`CoreStorage` extends that contract with application-lifecycle responsibilities:

- schema verification;
- exclusive runner ownership;
- backend descriptor metadata;
- resource cleanup.

Application assembly selects the backend through `build_storage(settings)`.

## Current backend

The current adapter is still `Database`, the existing SQLite implementation.

Its behavior is intentionally unchanged:

- the database remains under the configured local runtime directory;
- files are created with private permissions;
- foreign keys remain enabled;
- WAL mode and the existing busy timeout remain enabled;
- authoritative writes still use `BEGIN IMMEDIATE`;
- the existing runner lock still prevents two Core runners from owning one local
  database;
- Alembic remains the schema migration mechanism.

The adapter declares the non-secret descriptor:

```text
schema = zelo-storage-backend-v1
backend = sqlite
relational = true
vector_search = false
```

## Configuration

`ZELO_STORAGE_BACKEND` is explicit but fail-closed. In v0.13 its only valid
value is:

```text
sqlite
```

Postgres, Supabase and vector backends are **not** silently accepted before an
implementation exists.

## Future backend requirements

A later relational backend must preserve the same Core semantics rather than
only matching method names. In particular it must provide:

- atomic authoritative transactions;
- concurrency behavior that protects task, approval, budget, lease and scheduler
  invariants;
- schema/version validation;
- a runner-ownership mechanism appropriate for that backend;
- bounded resource use and clean shutdown;
- no credential or connection-string leakage through public descriptors.

A Supabase implementation would be treated as a Postgres-compatible storage
adapter behind the Zelo-owned contract. Supabase does not become Zelo's
authority boundary.

## Vector storage boundary

This slice does not add embeddings, semantic retrieval or a vector database.

The current backend descriptor reports `vector_search = false`. A later vector
capability can be composed behind a Zelo-owned interface once the memory roadmap
actually requires it. Existing lexical memory retrieval remains authoritative
for the current milestone.

## Explicit non-goals

This slice does not:

- move or copy existing SQLite data;
- add a Postgres driver or Supabase SDK;
- add a vector database;
- change memory retrieval behavior;
- add automatic memory writes;
- change task, approval, scheduler, budget, merge or release authority;
- change the Workspace into a persistence authority;
- begin v0.14 Agent Factory work.

## Completion gate

The slice is complete when:

1. Core services depend on the storage session contract;
2. application assembly uses the storage backend factory;
3. SQLite behavior remains unchanged;
4. tests prove the contract can be satisfied without a concrete `Database`
   dependency;
5. configuration fails closed to the implemented backend;
6. full CI and independent review are clean.
