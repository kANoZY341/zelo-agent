# Zelo Core v0.14 — Agent lifecycle and project binding

## Status

Second implementation slice of v0.14 Agent Factory.

The registry foundation is merged through PR #47 at:

`8609ee583513f24d312785b7158a90d40a8458ef`

This slice persists project-bound agent instances without granting them generic
execution authority.

## Goal

Turn trusted `AgentSpec` templates into durable, inspectable Core-owned agent
instances whose identity and project ownership cannot silently change.

The core rule remains:

> Models think. Agents specialize. Workers work. Tools act. Zelo decides.

## Persisted agent instance

Creating an instance accepts only:

- trusted `agent_id`;
- existing `project_id`.

Core resolves the current active `AgentSpec` through the trusted Agent Factory
and persists:

- generated instance ID;
- stable agent ID;
- agent spec version;
- exact registry fingerprint;
- exact AgentSpec snapshot;
- owning project ID;
- lifecycle status;
- creation/update timestamps.

The caller cannot supply a spec snapshot, worker ID, implementation, model,
provider, executable, credential, tool grant, permission grant, or registry
fingerprint.

## Lifecycle

Instance lifecycle is:

`active -> paused -> active`
`active -> retired`
`paused -> retired`

`retired` is terminal.

Resume is fail-closed: the persisted AgentSpec snapshot and registry fingerprint
must still match the current trusted registry. A stale instance may still be
paused or retired so operators can safely shut it down, but it cannot return to
active service without an explicit future migration/rebinding mechanism.

The owning project must also be active before an instance can be created,
resumed, or used to assemble execution-ready memory context.

## Database invariants

Migration `0020_agent_instances` adds:

- `agent_instances`;
- `agent_instance_events`.

Database triggers enforce:

- immutable agent ID, spec version, registry fingerprint, project binding,
  spec snapshot and creation timestamp;
- valid lifecycle transitions;
- terminal retirement;
- no instance deletion;
- contiguous event sequences;
- exactly one initial `created` event;
- append-only lifecycle events.

The service transaction uses the existing serialized write boundary, so active
instance limits are checked and created atomically.

## Project binding and memory context

This slice adds a bounded read-only memory-context resolver for active,
current instances.

It combines only:

1. the owning Project memory scope;
2. the specialist Agent memory scope identified by stable `agent_id`.

It deliberately excludes:

- personal memory;
- other projects;
- other specialist agent scopes.

The resolver reuses the existing v0.13 bounded lexical retrieval and creates no
new memory records.

## API surface

Authenticated operator routes:

- `POST /agents`;
- `GET /agents`;
- `GET /agents/{instance_id}`;
- `POST /agents/{instance_id}/transition`;
- `GET /agents/{instance_id}/events`;
- `POST /agents/{instance_id}/memory-context`.

These routes manage identity/lifecycle and inspect bounded context only. They do
not execute specialist work.

## Non-goals

This slice does not add:

- a new task kind;
- generic Agent Factory task execution;
- parent-child delegation;
- subagent creation;
- recursive agent trees;
- manager runtime behavior;
- agent-to-agent messaging;
- dynamic/model-authored AgentSpec creation;
- automatic memory writes;
- new tools or worker authority;
- approval, budget, scheduler, promotion, merge or release bypasses.
