# v0.15 — Persistent Agent computer internal topology

## Goal

Qualify the network topology required before any Agent-visible browser mutation
action can be added.

This slice is stacked after the egress prerequisite in
docs/v0.15-computer-browser-mutation-egress-gate.md. It still does not add
navigate, click, type, key, scroll, workspace write or shell to computer_run.

## Canonical topology

    Zelo Core
       |
       +------------------------+
       |                        |
    loopback Supervisor      Core egress proxy
    127.0.0.1:4312          internal bridge gateway
       |                     172.30.x.1
       |                        |
       | Docker socket          | CONNECT only
       v                        v
    OpenBot supervisor      internal-only Docker network
       |                    no direct public egress
       | creates                |
       v                        |
    per-Agent computer <--------+
    private IP :4100
       |
       +-- persistent browser/profile
       +-- persistent workspace
       +-- per-Agent control credential
       +-- per-Agent proxy credential

The supervisor remains reachable by Zelo Core only through host loopback.
The Agent computer itself is not host-published in internal-network mode.

Core reaches the computer through the exact private IPv4 address Docker assigned
on the configured internal network. That address is accepted only when it is:

- canonical IPv4;
- inside the exact configured RFC1918 CIDR;
- not the network address;
- not the broadcast address;
- not the Core proxy/gateway address; and
- port 4100 exactly.

The internal CIDR and Core proxy host are configuration identity. Changing them
changes the OpenBot backend identity and invalidates pending bound Computer work.

## Egress credentials

The host-only master computer token is never placed in an Agent computer.

The pinned supervisor derives two independent child credentials:

    computer control:
    HMAC-SHA256(master, "zelo-computer:" + AgentInstance UUID)

    browser egress:
    HMAC-SHA256(master, "zelo-egress:" + AgentInstance UUID)

The egress proxy username is the AgentInstance UUID. The password is the derived
egress credential. Raw EGRESS_PROXY passthrough is rejected by the hardened
supervisor so a deployment cannot silently replace the Zelo-owned proxy route.

## Why the private-IP control path is required

A live qualification disproved an earlier assumption: on this host,
internal:true Docker networks do not publish the requested host port even when
HostConfig retains a PortBindings entry. NetworkSettings.Ports is null.

The host can reach a computer through its private address on the internal bridge.
Therefore the correct topology is private-IP Core control plus internal-only
browser networking, not a pretend loopback publication.

The pinned OpenBot supervisor adaptation now reports the private control URL for
the exact configured network. The Zelo adapter independently validates that URL;
the supervisor response alone is never trusted.

## Live qualification — 5 October 2026

A disposable real OpenBot computer was started on:

    network: zelo-topology-live-sandbox
    CIDR:    172.30.252.0/24
    gateway/Core proxy: 172.30.252.1:4392
    computer control:   172.30.252.3:4100
    allowlisted origin: https://example.com

Observed results:

- supervisor returned the private computer control address;
- Core accepted that address only under the exact CIDR contract;
- the Agent container did not contain the master computer token;
- the browser received an Agent-specific authenticated proxy configuration;
- direct curl to https://example.com from the same Agent container failed;
- real Chromium navigation to the allowlisted origin succeeded through the Core
  proxy with HTTP 200 and title Example Domain;
- Browser permission was revoked in Core while the computer remained alive;
- the next Chromium navigation failed with HTTP 502 because egress authority had
  been revoked;
- the computer then stopped normally; and
- the disposable .252 container, volumes, supervisor and networks were removed
  completely.

The direct OpenBot /navigate endpoint was called only by the qualification
harness. No Agent-executable navigation action is introduced by this slice.

## Pinned upstream adaptation

The deployment remains pinned to OpenBot commit:

    b6932d31a8d6e7896c15139dfc27a6c6911deb27

The fail-closed supervisor build patch now reviews and transforms exactly three
upstream source files:

- supervisor/src/environment.ts;
- supervisor/src/docker.ts; and
- supervisor/src/index.ts.

The build fails if any expected source contract drifts.

The adaptation:

- derives the child control token;
- derives the child egress token;
- injects the per-Agent browser proxy;
- refuses raw proxy passthrough;
- reports the computer address on the configured internal network;
- requires that address to exist before returning a network-mode computer; and
- binds list/ensure responses to the configured network.

## Non-goals

This slice does not grant:

- Agent-visible navigate;
- click/type/key/scroll;
- arbitrary URLs;
- workspace writes;
- shell execution;
- page credentials;
- host filesystem/browser/shell access; or
- direct public egress.

## Next gate

After the egress prerequisite and internal topology are merged and green, add
the first browser mutation action separately.

The initial action should be named-endpoint navigation, not arbitrary URL
navigation. The task should identify an operator-configured endpoint ID plus a
bounded path, bind the exact endpoint-registry/policy/permission/backend identity,
and revalidate immediately before and after execution. Click/type/key/scroll
remain later actions with their own policy and approval review.
