# v0.16 — Private WhatsApp send-response shape observation

This Core-only step follows the one-use possible send claim. It does not connect a Meta HTTP client, token, account registry, webhook, API route or Worker. Published v0.15.0 remains the latest release.

For one claimed reply intent, an Ahmad-only method compares a trusted raw recipient ID under the Core identity secret to the saved opaque recipient. It records only the first supplied response observation. A bounded strict parser recognizes an HTTP 200 JSON shape with one WhatsApp contact matching that recipient and one valid outgoing `wamid`. Duplicate keys, malformed JSON, mismatched recipients, ambiguous lists and contradictory error or failed-status fields produce `invalid_success_shape` with no outgoing message link. A non-200 status and a missing response retain separate conservative categories.

The append-only `whatsapp_send_responses` row stores HTTP status, the category, an optional keyed opaque outgoing message ID, UTC observation time and fixed false delivery and transport flags. It stores no raw recipient, wamid, body, token or credential. A duplicate or SQL mutation/replacement refuses. The underlying send attempt remains spent and cannot be automatically retried regardless of the observation category.

`success_shape` describes supplied bytes only. It is not proof of a real Meta exchange, provider acceptance or delivery. A future sender must bind a qualified account and credential, issue at most one request after the durable claim, and provide trustworthy response provenance. Signed status events and operator acceptance remain separate work. Live Meta transport and delivery are NOT RUN.
