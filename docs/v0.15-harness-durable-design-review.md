# v0.15 — Durable operator review of a Harness team **design**, not activation

This slice records the Managing Director's human design-review decision against
an exact, currently recomputed Project-bound Harness plan. It is the first
durable *review evidence* for a proposed specialist organization, not a team
activation token. The existing trusted AgentFactory and OrganizationService
remain the only appropriate basis for eventual real execution.

## Operator-only routes

- `POST /integration-candidates/community/teams/{template}/design-reviews` (201)
- `GET /integration-candidates/community/team-design-reviews/{review_id}`

The POST accepts a strict JSON `proposal` identical to the Project readiness
preview, the exact `expected_review_plan_sha256` obtained from that preview,
an opaque 8–64 character `idempotency_key`, and a `decision`:
`accepted_for_design_review` or `rejected_for_design_review`.

This endpoint is operator-authenticated with Core's configured owner bearer
token. It does not accept an actor identity in client JSON. It records the
existing principal, `ahmad`, in the row and receipt.

Within one serialized SQLite writer transaction, the service recomputes the
pinned Harness blueprint and full Project plan, including current Project
status/timestamp, globally reserved nonretired Agent role IDs, immutable
Agent Registry fingerprint and the exact proposed budgeting ceilings. Only
an exact SHA-256 match can be recorded; accepted design reviews require a
currently eligible plan. Explicit rejections may record otherwise denied
designs. A changed/stale plan or replay fails closed with 409.

## Exact persistence and replay

Migration `0042_harness_team_design_review` creates
`harness_team_design_reviews`, an append-only, irreversible SQLite audit
ledger with a unique idempotency key. The row contains bounded Project,
template, registry, blueprint and exact plan identifiers, its review reason,
the operator's design decision, a SHA-256 of the strict request, and a
SHA-256-bound historical receipt. The database disallows UPDATE and DELETE.
It also refuses `INSERT OR REPLACE` against existing primary or
idempotency keys, including when recursive SQLite triggers are off.

An exact retry returns the same historical receipt without writing a second
review. A changed request under a reused key is rejected. Even on an exact
retry, a stale or changed Project/Registry/role reservation is rejected before
the historical result is returned. GET returns a sealed *historical* review,
not an assertion that current Project or role eligibility is unchanged.
Direct storage corruption cannot pass the receipt's strict reconstruction.

## No executable grant

A stored `accepted_for_design_review` judgment is **not** an activation,
permission, financial expenditure or AgentFactory registry mutation. It does
not create Agents, OrganizationAssignments, Tasks, Approvals, Campaigns,
worker access, Skill registrations, per-agent computers or Space grants.
Receipt flags explicitly prohibit presenting the record as execution
authority. No Worker, Tool, Mind or automated scheduler path consumes these
rows. No new model instruction, provider credentials or external account
action is introduced.

Any later real team activation requires a **separate durable operator
activation decision**, trusted active AgentSpec registrations and activation
evaluation, atomic Project-scoped identity reservations, real runtime
resource-limit enforcement, explicit org hierarchy and Campaign budgets,
per-role permissions and revocation checks. This record alone must never
satisfy those gates. UI #61 remains parked. REA remains inactive; Media
native-reader refusal budget is untouched.
