# Zelo Core v0.15 — Generic Worker Registry foundation

## Status

Third bounded implementation slice of v0.15 Capability and skills ecosystem.

Merged foundations:

- Capability Registry: PR #55, merge
  `4dcc5bf03dfe761d64df49f848762a163158d8df`;
- Skill Registry: PR #56, merge
  `7e0936750967be79ec49ee5858a508935d7ad3e0`.

## Goal

Separate trusted worker **selection metadata** from the DeveloperWorker execution
interface so future Research, Browser, Computer, Python, API, Shell and Media
backends can share one Supervisor without creating parallel routing authority.

This slice generalizes types and storage only. It does not add a new worker or
change runtime execution.

## Scope

This slice:

- makes `RegisteredWorker` generic over its backend object;
- makes `WorkerRegistry` generic over its backend object;
- makes `Supervisor` generic over its backend object;
- keeps exact WorkerDescriptor, authority-profile, registry-version and routing
  policy semantics unchanged;
- keeps DeveloperRuntime explicitly typed as
  `WorkerRegistry[DeveloperWorker]`;
- proves Supervisor can select an opaque backend object without calling any
  DeveloperWorker method.

## Non-goals

This slice does not:

- register a Research, Browser, Computer, Python, API, Shell or Media worker;
- add a task kind, tool, capability or skill;
- change WorkerDescriptor fields or registry fingerprint schema;
- change worker priorities, capacity routing or exclusion behavior;
- change WorkerAuthority profiles or realized sandbox policy;
- add network, filesystem, subprocess or credential authority;
- unify DeveloperRuntime and ResearchRuntime execution semantics;
- change approval, budget, scheduler, promotion, merge or release authority;
- add database tables or migrations.

## Compatibility rule

The existing DeveloperRuntime remains explicit:

`WorkerRegistry[DeveloperWorker]`

Its workers still must satisfy the existing DeveloperWorker identity, binding,
preflight and run contracts at the execution boundary.

The generic WorkerRegistry itself only stores:

- trusted WorkerDescriptor;
- backend object;
- resolved WorkerAuthorityProfile.

Supervisor still routes exclusively from descriptor metadata and current
capacity. It never invokes the backend object while selecting.

## Why this comes before a Research Worker

Today the Coding/Developer path uses WorkerRegistry + Supervisor while the fixed
Research path is a separate ResearchRuntime.

Before introducing a replaceable Research Worker, Core needs one canonical
selection mechanism that is not typed specifically to DeveloperWorker.

This foundation creates that seam without altering ResearchRuntime or granting
new authority.

## Verification

Required gates:

1. PEP 695 generic typing passes Ruff;
2. opaque backend selection proves no DeveloperWorker call is required;
3. existing deterministic role/capability filtering remains unchanged;
4. priority, capacity and exclusion semantics remain unchanged;
5. registry version and authority snapshot semantics remain unchanged;
6. existing DeveloperRuntime remains explicitly DeveloperWorker-bound;
7. focused worker/capability/activation tests pass;
8. full pytest passes from a real clone with a trusted validation environment;
9. diff check and Ruff lint/format pass;
10. adversarial review and exact-head GitHub CI pass.

## Continuation

After this foundation merges, the next bounded slice may introduce a read-only
Research Worker adapter behind the same Supervisor.

That later slice must separately define:

- a research worker backend contract;
- trusted descriptor and capability identity;
- compatible skill metadata;
- workspace-read/no-network authority;
- bounded model/tool behavior;
- evidence, cancellation, retry and audit semantics.

Generic registration alone is never permission to execute.
