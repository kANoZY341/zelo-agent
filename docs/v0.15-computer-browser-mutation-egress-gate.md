# v0.15 — Persistent Computer Browser Mutation / Egress Gate

## Decision

Do not expose `navigate`, `click`, `type`, `key`, or `scroll` merely because
the read-only Computer Worker is qualified.

OpenBot's computer endpoint correctly validates that navigation uses HTTP(S), but
it deliberately does not own deployment policy. In the current host topology a
computer without an explicit Docker network uses Docker's normal outbound path.
That is acceptable for owner-controlled qualification, but it is not a sufficient
boundary for autonomous Agent browser mutation.

Browser mutation therefore starts with a separate egress authorization gate.

## Network shape

Target topology:

```text
                           Zelo host
                              |
               +--------------+--------------+
               |                             |
         Zelo Core                    OpenBot supervisor
               |                       Docker socket only
               |                             |
      Computer Egress Proxy                  |
               |                             |
               +---------- bridge gateway ---+
                              |
                  INTERNAL Docker network
                  (no direct internet route)
                              |
                    per-Agent computer
                    Chromium + workspace
```

The Agent computer joins a Docker network created with `internal: true`.
It must have no direct default path to the public internet.

The host-side egress proxy binds only to that internal bridge gateway. It is not
a public/LAN proxy.

The OpenBot supervisor remains loopback-published to Core. Agent-computer HTTP
control ports remain loopback-published even while the computers also join the
internal network.

## Why a proxy is required

URL syntax validation alone cannot stop:

- private or loopback targets;
- link-local/cloud metadata targets;
- DNS rebinding between policy check and Chromium connection;
- redirects that cause a private request before Core can inspect the final URL;
- page/script/WebRTC attempts to bypass application-level navigation policy.

The Docker internal network removes the direct egress path. The proxy becomes
the only network route available to Chromium.

## First mutation capability

The first mutation capability should be:

`computer_navigate`

Only HTTPS destinations are eligible.

Click/type/key/scroll remain disabled until navigation itself is independently
qualified.

## Trusted endpoint identity

Reuse Zelo's existing `ApiEndpointSpec` / public-address semantics rather than
inventing a second hostname parser.

A trusted computer-navigation endpoint has:

- endpoint id;
- canonical HTTPS origin;
- public hostname/IP only;
- no credentials in the origin;
- bounded port.

Each persistent Agent computer profile gains a canonical tuple of allowed
endpoint IDs. Task input selects an endpoint ID + relative path; it never supplies
an arbitrary authority-bearing URL.

The AgentSpec remains the upper bound. A model cannot add an endpoint to itself.

## Per-Agent proxy authentication

Every computer gets a derived proxy credential:

```text
username = AgentInstance UUID
password = HMAC-SHA256(COMPUTER_TOKEN, "zelo-egress:" + AgentInstance UUID)
```

The master token never enters the Agent computer.

OpenBot already supports Playwright proxy username/password. The hardened
supervisor will derive the per-Agent credential while constructing that
computer's environment.

## CONNECT policy

The proxy accepts only bounded HTTP CONNECT requests.

For every CONNECT:

1. parse and authenticate the AgentInstance UUID + derived token;
2. load current AgentInstance / trusted AgentSpec;
3. require active/current Agent identity;
4. require Core computer `enabled=true` and `browser=true`;
5. require Agent capability `computer_navigate`;
6. require the requested host:port to match an endpoint granted to that Agent;
7. resolve the hostname through Zelo's owned resolver;
8. require every result to pass `public_address`;
9. connect the proxy itself to the exact selected public IP;
10. tunnel bytes with bounded connection/time/resource budgets.

Because the proxy connects to the resolved IP itself, Chromium cannot perform a
second DNS resolution and rebind to a private address.

The browser still performs TLS through the CONNECT tunnel and validates the
destination certificate/SNI.

## Subresources

A page may load only origins explicitly granted to the same Agent.

Cross-origin CDNs/API hosts therefore need separate trusted endpoint grants.
This may make an unqualified site render incompletely, which is preferable to
silently widening network authority.

## Revocation

Navigation authority is not submit-time only.

Pending task execution must bind:

- Agent execution identity;
- Computer Worker selection;
- endpoint registry binding/version;
- per-Agent endpoint grant digest;
- Core Browser permission digest;
- egress policy version;
- OpenBot backend identity.

Claim revalidates all of them.

The proxy independently checks current Agent/Core state on every new CONNECT,
again after DNS resolution before opening the upstream socket, and before
forwarding each subsequent tunnel chunk. Revocation therefore blocks queued Zelo
tasks, new browser network connections, and further traffic on already-open
tunnels. An idle revoked tunnel may remain allocated until its bounded timeout,
but it cannot forward additional bytes.

## Human takeover

Owner Take Control does not bypass egress policy.

A human may drive the Agent's browser, but the browser remains on the same
internal network and behind the same Agent-scoped proxy. Human control changes
who may send input; it does not widen network reach.

## OpenBot adaptation

Continue pinning the exact reviewed OpenBot revision.

The Zelo supervisor hardening patch may additionally:

- keep loopback PortBindings even when `COMPUTER_NETWORK` is set;
- join computers to the internal network;
- derive per-Agent `EGRESS_PROXY_DEFAULT` credentials;
- refuse upstream source drift before the image builds.

Zelo Core's backend should prefer a returned loopback port over a container-name
URL so host-mode Core never needs Docker DNS.

## Qualification gates

Before `computer_navigate` becomes active, prove:

- internal network has no direct public route;
- direct IP/private/link-local/loopback/metadata attempts fail;
- DNS name resolving private fails;
- DNS rebinding cannot change the proxy-pinned destination;
- unauthorized Agent endpoint fails;
- stale AgentSpec fails;
- Browser permission revocation fails;
- proxy credential for Agent A cannot authorize Agent B;
- human Take Control does not bypass endpoint grants;
- loopback computer-control port remains host-only;
- cancellation closes tunnel resources;
- proxy failure fails closed with no direct fallback.

## Later browser actions

After navigation is qualified:

1. `scroll` (low mutation / no external side effect);
2. ref-bound `click` with risk classification + approval for side-effecting UI;
3. bounded `type` / `key` with secret separation;
4. only then richer browser workflows.

Workspace writes and shell remain separate authority phases.
