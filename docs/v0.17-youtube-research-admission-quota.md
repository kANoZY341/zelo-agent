# v0.17 — durable new-submission quota for the opt-in YouTube Research Specialist

This follow-on to the default-disabled single-Specialist pilot introduces a
small, concrete automatic-work guardrail **without creating a new budget service,
scheduler, approval authority, or database table**.

## Core authority and bounded scope

The limit is eight **new** `research_run` Task submissions over a rolling
24-hour UTC window for one **Project + `youtube_topic_researcher` AgentSpec identity**.
It counts Task creation records across all AgentInstance UUIDs in the same
Project, including earlier retired/replaced specialist instances. Cancelled,
failed and completed tasks still count. A replacement AgentInstance therefore
cannot erase the Project's recent Task history.

The limit applies ONLY to Tasks submitted through the trusted
`/agents/{instance_id}/tasks` path with a validated immutable Agent execution
binding and `spec.agent_id="youtube_topic_researcher"`. Existing unbound generic
Research, Coding and other AgentSpec operations retain their prior behavior.
The quota cannot authorize a new task, worker, tool or account on its own.

Enforcement occurs inside **TaskService.submit's existing serialized SQLite
writer** (BEGIN IMMEDIATE), after exact idempotency replay resolution and
the existing AgentSpec, AgentInstance, Project, Campaign and delegation
identity checks, but before the new Task is inserted. Two competing new
submissions for the eighth slot cannot both succeed. Excess attempts fail
with HTTP **429** / `youtube_research_new_task_quota_exhausted`.
No denial creates a Task or consumes an extra slot.

An identical idempotency-key retry returns the already-recorded Task
even when the quota is full. A reused key with a changed request still
fails under the existing TaskService idempotency and bound Agent identity
rules. The limit is derived directly from persisted Task creation
records (including Task agent_execution_spec and created_at), surviving Core
restarts. No mutable counter can be reset or overcommitted.

## Operator-only visibility

`GET /agents/{instance_id}/research-quota` is under Core's existing owner
bearer authentication. The view returns the bound Project, instance status,
UTC observed time and 24-hour window start, current counted submissions,
maximum of eight and remaining slots, plus explicit untrusted/authority
limitations. Other Agent types or missing AgentInstance IDs are refused.
It does not execute a Worker, reserve funds, call an external service,
change a Task or give Skills/Space/computer grants.

## What is NOT covered

This is a **new-Task submission cap**, NOT a financial budget, token-metered
quota, cost guarantee, attempt-level retry budget, or total usage accounting.
Existing Core `max_agent_steps`, `max_agent_tool_calls` and Worker timeouts
continue to bound each Task, but a particular accepted Task may still be
retried under Core's separate retry authority. Future Campaign budgeting
and cost evidence must enforce actual per-attempt/compute spending before
claiming monetary budget limits.

An operator can create another Project and separately admit a specialist
there. This is deliberate Project scoping, not a global customer/account
monthly expenditure limit. The Feature still has **no** YouTube channel
credentials, uploads, publication authority, external messaging, hiring,
auto-scheduling or computer/browser/shell ability. The main v0.17 full team
hierarchy, durable independent activation authorization, Campaign budgets
and multi-agent delegation remain unfinished.

## Verification and promotion

Focused tests assert exactly eight accepted unique submissions, 429 on ninth,
idempotent replay with full quota, rejection without Task/Audit writes,
concurrent eighth-slot competition, per-Project separation, generic Research
unaffected, retired/replaced instance cannot reset Project quota, all terminal
states count and rolling cutoff expiry, read-only authenticated quota endpoint,
and strict authority-free response fields.

The full Agent/Research/Task regression suite, independent exact-commit review,
exact-head GitHub CI and preceding post-merge main CI remain the release gates.
No production runtime is changed merely by storing or reviewing this branch;
UI #61, REA and Media native-reader restrictions stay untouched.
