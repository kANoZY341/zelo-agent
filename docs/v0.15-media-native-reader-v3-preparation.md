## One-process receipt capture candidate

The inert `ApprovalCapture` prototype generates an unpredictable 256-bit
challenge only after it holds the existing admission lock. Its trusted caller
must publish the challenge and exact four-attempt/source binding to the
Managing Director, supply the resulting comment ID in the same process, and
keep that process alive. There is no operator CLI or publication transport
yet. The capture fetches pinned GitHub resources, validates an unedited comment
created after challenge issuance, writes a private bounded receipt with file
and directory sync and readback, then re-fetches for drift and syncs a
separate exact recheck snapshot before returning the lease. A failed write or
changed comment fences the attempted invocation; a restarted process cannot
reuse its earlier challenge. Tests use only a disposable four-attempt fixture.

The receipt alone cannot establish whether an earlier grant or native run
survived a crash. Absence of its directory is not evidence of freshness. A
new decision still requires independent reconciliation of prior outcomes.
The prototype returns a held admission lease but never writes a v3 grant,
allocates a fifth attempt or calls Docker. It has not been connected to the
qualifier and cannot authorize a native run. The separate exact one-run
Managing Director decision, complete held-lock grant/run integration,
adversarial tests, independent review and exact-head CI remain required.
