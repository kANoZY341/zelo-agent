# Zelo Core v0.9 — Worker Authority and Multi-Worker Runtime

v0.9 turns the v0.8 worker-registry metadata into enforceable runtime policy and removes
the single-worker execution assumptions that would otherwise make a second production
worker unsafe.

## Mission

Zelo must be able to route developer work to multiple trusted workers while preserving the
same approval, source, validation, artifact and audit guarantees established in v0.8.

The v0.9 boundary is deliberately below MCP. External tool ecosystems come after worker
authority is enforceable.

## Authority policy

A worker descriptor's `authority` is no longer descriptive metadata.

Trusted application assembly resolves every descriptor authority tuple through a versioned
authority-policy registry. Unsupported authority fails closed at worker registration.

The selected worker approval snapshot binds:

- the full trusted worker descriptor;
- the content-derived worker-registry version;
- the routing-policy version;
- the resolved authority-profile name; and
- the content-derived authority-policy fingerprint.

The authority-policy fingerprint hashes the complete permission semantics of every trusted
profile. A change such as workspace write or network permission therefore invalidates old
approvals automatically, even if a developer forgets to manually bump a version label.

For v0.9 the only production authority profile is:

`workspace-write-no-network-v1`

It permits writes only inside the isolated developer checkout and denies worker-command
network access. The Codex adapter must derive its actual permission configuration from this
resolved profile rather than from a hard-coded workspace-write assumption.

## Concurrency policy

`max_concurrency` is a hard ceiling.

The task scheduler may claim developer work concurrently only while the selected worker has
capacity. Non-developer tasks remain exclusive with developer execution in v0.9.

The runner may host multiple concurrent developer executions, but capacity is keyed by
trusted `worker_id`. A worker with `max_concurrency=1` can never have two running tasks.

The runtime also enforces the same ceiling with process-wide filesystem slot locks so a
second Zelo process cannot bypass scheduler accounting. Scheduler capacity and runtime slot
capacity are independent fail-closed checks.

## Multi-worker construction

With an explicit registry, the runtime derives its primary/default worker from the
Supervisor's actual routing winner. A supplied compatibility worker must be that exact
winner or construction fails. This removes the v0.8 state where the public primary worker
could differ from the worker the Supervisor would really select.

Each future production worker must have an explicit trusted descriptor. The single Codex
default remains only for the implicit one-worker application assembly.

## Async safety

Trusted source-state and Git-state hashing used during developer execution must not block the
runner event loop. Bounded synchronous hashing is moved to worker threads while all existing
snapshot and boundary checks remain unchanged.

## Acceptance criteria

v0.9 is not a release candidate until all of the following are demonstrated:

1. unsupported authority fails at registry construction;
2. authority profile and policy version are persisted in the approval snapshot;
3. changing the authority policy/profile invalidates compatibility;
4. Codex execution derives filesystem/network permissions from the bound authority profile;
5. scheduler claims never exceed a worker's `max_concurrency`;
6. different eligible workers can run concurrently when each has capacity;
7. non-developer tasks remain exclusive while developer tasks are running;
8. cross-process worker slot locks enforce the same concurrency ceiling;
9. explicit registry construction cannot expose a primary worker different from the
   Supervisor routing winner;
10. trusted snapshot hashing is off the asyncio event loop;
11. all v0.8 approval/source/artifact/validation protections remain intact; and
12. Ruff, Ruff format and the complete pytest suite pass.
