# Media native Reader: proposed fifth-run admission

**Design candidate only.** The four refused attempts remain terminal. No fifth
proof, new grant, operator approval, Docker command, or qualifier admission is
created by this document. The native Reader remains required for the full
v0.15 release.

## Authority and one-run boundary

The existing v3 ledger preparation is historical evidence, not a runnable
permit. Its readable seal cannot prove that its writer returned successfully:
a failed sync followed by failed seal cleanup could leave an apparently valid
seal. The native qualifier must never treat `v3.validate()` or a file digest
alone as authority to create attempt five.

After independent review of the exact candidate code, the Managing Director
must issue a **separate, exact one-run decision** for the retained runtime and
reviewed source head/tree. A GitHub issue comment is a proposed additional
machine-checkable receipt, not proof of the human Managing Director's identity
by itself. The Managing Director confirmed in this conversation on 20 October
that the existing GitHub account `kANoZY341` is theirs; its API numeric ID is
`64309771`. The proposed gate must pin that ID, repository ID `1373657980`,
issue #166 ID `5806214593` and the approval schema. Login or repository-owner
role alone is insufficient. This identity confirmation is **not** authorization
for a fifth run. The separate exact one-run decision and its scope have not
been issued.

The proposed comment has a strict bounded schema: decision
`authorize-one-fifth-native-media-reader-proof`, absolute canonical runtime
root, four exact attempt names and proof digests, exact source head/tree, one
additional attempt, no network or runtime authority, and an expiry. It must
also include a fresh 256-bit random challenge generated inside that one
operator process after the lock is held. A restarted process must generate a
different challenge, so an earlier comment cannot be
replayed after an uncertain receipt write or crash. The command must accept no
caller-supplied challenge and must exit after a failed write rather than
reusing the live challenge. The Managing Director would post the exact comment
while that invocation remains alive. Admission must fetch the specific comment
from GitHub and check repository/issue/account IDs, a comment timestamp in
a later whole second than challenge issuance, edit timestamps, exact fields
and expiry. Fetch failure or
uncertainty refuses before Docker. Record the exact short approved body, its
digest, comment ID and API metadata in a private authorization receipt bound
to root, source and history. Sync the receipt file and directory **before**
creating a grant. If any receipt write/sync is uncertain, refuse without a
grant or attempt. A freshly created directory alone cannot prove consumption
across a failed parent-directory fsync and crash: its entry might disappear.
No automatic retry may infer fresh authority from absence of that directory.
The challenge prevents reuse of the old comment; it cannot establish whether
a receipt, grant or run survived a crash. A new decision needs explicit prior
outcome reconciliation, even when the directory is absent. The live process
challenge, its generation and one-shot state, the durable receipt, and
uncertain-result reconciliation must be designed, reviewed and tested together
before any run connection. The first local receipt-writer
candidate was discarded after independent review found this gap. The comment
is an operator decision, not a result or release approval.

Re-fetch the same comment under the held admission lock immediately before
grant mutation. Compare its exact body and metadata to the durable receipt and
check expiry against the current clock. If the comment changes, expires or
cannot be checked, refuse and retain the fenced receipt. Check it again before
attempt allocation; an intervening change consumes the grant without a run.
After attempt allocation, a later edit cannot undo a prior operation; retain
the checked snapshot for audit and report later drift without claiming the
original authorization still exists.

One reviewed operator invocation should perform approval verification,
read-only history/resource preflight, grant creation and the fifth synthetic
proof **in one process under one admission lock**. The discarded v3 writer and existing `AdmissionController.acquire()` each
locked `admission.lock`; nesting those implementations would deadlock. Add a
new approval-bound held-lock grant writer and an admission operation that
transitions the same held lock to its durable marker/lease without releasing
it. Test the transition and every failure point. Only the successful
return value from the live grant writer, while that invocation still owns the
lock, may flow into the fifth attempt path. A later process must never infer
this permission from a readable grant/seal. Grant and attempt records remain
append-only. This requires a new narrow qualifier path and tests; the current
qualifier is unchanged and still refuses four attempts before Docker.

If a grant write, sync, close, validation or cleanup is uncertain, the command
must refuse without creating attempt five. The grant directory remains as a
consumed/fenced continuation; it must not be removed and retried as fresh. A
crash after a successful grant but before attempt creation also consumes the
one-run decision. Once attempt five exists, all later invocations refuse even
if its proof failed. Any further decision would require a new reviewed design
and separate operator authorization, not a reset.

## Required adversarial qualification before connection

| Case | Required outcome |
| --- | --- |
| No comment, wrong pinned account/repository/issue, edited or expired comment, fetch failure | Refuse before Docker and before grant mutation. |
| Unconfirmed human-MD/account mapping or missing separate decision | Refuse before any grant mutation. |
| Authorization receipt write/sync uncertainty or comment drift on re-fetch | Refuse without a grant or attempt. Require independent reconciliation before any new invocation, even if a directory is absent after a crash. |
| Wrong root/head/tree, changed old proof or grant, live lease resources | Refuse without changing the four retained attempts. |
| Concurrent invocation or admission marker not empty | Exactly one contender proceeds; others refuse. Held-lock grant/marker transition has no unlocked gap. |
| Grant file/seal sync fails and cleanup also fails | No attempt five; no later `validate()`-only route can start it. |
| Crash after grant success but before attempt creation | Continuation consumed; explicit new decision needed. |
| Fifth attempt begins and fails at any stage | Retain refusal and cleanup evidence; never allocate a sixth. |
| Exact reviewed source, valid approval and clean preflight | At most one synthetic run; inspect full matrix/cgroup and cleanup receipts. |

A strict snapshot parser and a read-only `gh api` GET adapter exist in
`qualification/media_reader_run_approval_v3.py`. The fetcher reads the fixed
repository and issue plus an exact comment ID, binds a caller-provided expected
challenge and issuance time, validates a fresh clock after fetch and can
compare a second snapshot for drift. The future operator command must generate
that challenge internally; the parser does not establish its origin. It has no
automatic invocation and creates no receipt, grant or run permit. The confirmed
Managing Director account ID is pinned in the parser; that identity is not a
fifth-run decision.
The new `AdmissionController.acquire_after()` primitive runs a trusted
synchronous writer under the existing lock before writing the lease marker.
No v3 writer is connected to the qualifier. The standalone v3 command and
public `grant_once()` API refuse even with the fixed confirmation phrase and
matching source. An inert `ApprovalCapture` now exercises held-lock challenge generation,
fixed-resource fetch/re-fetch and a synced receipt in disposable tests. It has
no operator CLI, grant writer, attempt allocation or Docker path; a caller
callback must still convey the challenge and return a comment ID in that same
process. If it exits after an uncertain write, a new process requires a new
challenge and a reconciled prior outcome, even if its local directory is absent.
The production operator interface, bounded wait and resource preflight,
held-lock grant/run integration, operator approval, exact-head CI and separate
real native proof remain pending. A synthetic proof does not itself qualify
package provenance, decoding, Core runtime authority or the final release
audit. No release tag may be inferred from this design.
