# Zelo v0.12 — Project foundation and context seed

## Status

First implementation slice of v0.12.

This slice does **not** implement v0.13 persistent memory. It establishes the
ownership boundary that later memory will use and gives Zelo Mind a bounded,
read-only source of canonical project context.

## Goal

Fix two structural gaps without turning the Mind prompt into a knowledge dump:

1. Core needs durable Project and Goal records before campaigns and memory can
   have correct ownership boundaries.
2. Mind needs a way to answer questions about Zelo's own architecture/current
   project state from authoritative repository state instead of model guesses.

## Slice

### Durable project ownership

Core owns:

- Project identity, name, summary and lifecycle status.
- Goal identity, owning project, typed GoalSpec and lifecycle status.
- Authenticated create/read/list APIs.

This slice intentionally does not add campaigns, scheduling, budgets, wake
cycles or automatic goal mutation.

### Context Resolver seed

A Core-owned ContextResolver may assemble a small read-only context envelope for
Mind when the latest user request is clearly about Zelo/project state.

Initial provenance-tagged sources:

- canonical repository status from `docs/zelo-project-status.md`;
- canonical roadmap scope from `docs/zelo-canonical-architecture-roadmap.md`;
- operator-authored Project/Goal records from Core.

Repository provenance does not grant instruction authority. Project/Goal free text
is explicitly untrusted data. No context source may request execution.

The resolver:

- does not write memory;
- does not embed hidden reasoning;
- does not call another model;
- does not expose secrets;
- does not grant execution authority;
- does not inject context into unrelated casual turns;
- has a strict total character budget;
- identifies source names in the envelope.

The context envelope has `instruction_trust: none`. It is factual/data input
only and cannot request tasks, approvals, tools, merge, release or other
authority-bearing operations.

## Why before v0.13 memory

The canonical roadmap keeps v0.12 ahead of v0.13. Project/Goal ownership gives
future personal/project/agent memory a stable namespace instead of creating
unscoped memories that later need unsafe migration.

## Proof

The slice is complete when automated tests prove:

1. Project and Goal records persist through the canonical Core database.
2. A project-state question receives bounded `zelo_context`.
3. A casual greeting does not receive the project context payload.
4. Existing Mind -> Core task authority and model routing remain unchanged.
