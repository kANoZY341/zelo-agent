# REA 6.0 — opt-in, offline sealed-target static qualification candidate

This separate qualification-only implementation builds beyond the fixed harmless
two-file source-built REA MCP proof. It can prepare one explicitly selected,
**already sealed** text-only operator target for a no-network static REA MCP
probe. The implementation and fake-container tests do **not** prove a real
selected-target Docker invocation succeeded. Do not mark generalized REA target
analysis qualified until the separately authorized real, bounded native probe
returns independently verified evidence and cleanup receipts.

## Allowed operator-only workflow

This is a local trusted CLI, **not** an Agent Tool, Core Task, active Specialist,
HTTP route, app credential flow, or persistent execution approval.

1. Use `python -m scripts.admit_rea_target --allow-offline-target-admission`
   to select a single benign text-only folder from Zelo's fixed private inbox.
   Retain the resulting opaque `target-` snapshot identifier and SHA-256 receipt
   digest outside that folder.
2. Optionally use the previously reviewed `scripts.preflight_rea_target` to
   confirm the pinned source/catalog and target metadata.
3. Only when a *separate actual operator decision* authorizes a manual native
   REA proof, provision the exact prebuilt source-owned REA v6 runtime from the
   reviewed lock in the worktree's ignored
   `workspaces/rea-qualification/runtime-v6`. No managed installation, network
   fetch or silent auto-provisioning is implemented. The identical fixed-fixture
   runtime profile's hashes for Node, package-lock, entrypoint, node_modules and
   dist must match; the pinned local Node image ID must exist already.
4. Explicitly run from the dedicated repository root:

```sh
.venv/bin/python -m scripts.qualify_rea_verified_target \
  --allow-native-rea-target-probe \
  --snapshot-id target-<32-lowercase-hex> \
  --receipt-sha256 <64-lowercase-hex>
```

No flag means refusal **before** any source/runtime or target access. The
arguments cannot contain source paths, network destinations, arbitrary tool
names, OS commands or secrets. The runtime must be non-root and the qualification
folder must be private. A missing trusted build refuses; the process never
falls back to npm, remote MCP packages, general browser/network tooling or
host executables. Do **not** use real or sensitive user artifacts during
qualification; only approved benign operator-owned test data.

## Independent safety boundaries

`integrations/rea/offline-verified-target-v1.json` is a separately pinned policy
whose own SHA-256 is anchored in trusted Python. It explicitly limits this proof
to manually selected sealed snapshots, one static tool, at most 128 UTF-8 JS,
JSON, HTML, CSS or Map files, 512 KiB/file, 4 MiB overall, five path components
and 45 seconds. The original `static-mcp-v6-profile.json` and fixed tiny fixture
proof are **not** widened by reusing that runtime identity.

Immediately before staging, the receipt is independently verified through the
private, symlink-safe admission boundary. The qualifier creates one randomly
named private staging folder, copies content through nofollow descriptor-based
bounded reads, seals all copied files and directories to 0400/0500, reconstructs
the exact canonical receipt from those *copied bytes*, and compares its digest
to the originally retained receipt SHA-256. It also checks file counts/byte
limits, then verifies the original snapshot again. Any discrepancy refuses
before Docker. The local operator OS account/kernel/filesystem remain trusted;
owner/root adversarial concurrent writes are outside this bound.

Only a pinned local Node Docker image may start. The inherited, already reviewed
source-owned Docker contract uses `--network=none`, `--read-only`,
`--cap-drop=ALL`, `--security-opt=no-new-privileges`, non-root host UID/GID,
`--pids-limit=64`, `--memory=384m`, `--memory-swap=384m`, `--cpus=1`, private
16 MiB tmpfs, no image pulling, and read-only mounts for the pinned REA runtime
(`/rea`) and the content-verified staging tree (`/target`). There is no writable
host/workspace mount. Only `analyze_javascript_application` with fixed `/target`
directory input can be called via bounded newline-delimited MCP JSON-RPC.
No target JavaScript evaluation permission is granted or intended. A parser bug
in an untrusted analyzer could still exist despite Docker restrictions.

All MCP output is **untrusted data**. The existing REA receipt parser checks
tool/provider/protocol identities, target-in-guest path `/target`, evidence
schema and subject digest, bounded statistics/limitations and time/output
limits. Only the bounded summary is exposed locally. Nothing is admitted as a
Mind instruction, learned Skill, Agent memory, untrusted code patch or Core
Evidence object.

A random Docker ownership label and retained exact container ID must reconcile
before staging can be deleted. Unknown CID, daemon errors or interrupted
cleanup retain the private run folder and refuse; no unrelated container is
removed. An operator must resolve uncertain cleanup separately using the
exact run owner token; this code does not auto-grant Docker cleanup authority
to Agents. Normal successful cleanup unseals only the owned copied tree and
removes only that proof's scratch directory.

## Non-authorization / next gates

Even after a successful manual proof the result states `core_approval=false`,
`core_worker_registered=false`, `core_tool_grants=[]`, and
`core_task_created=false`. It proves at most **one local test invocation**, not
that arbitrary target programs are safe or that REA is now a Zelo Worker.
The draft Reverse Engineering Specialist, 139 observed tools, existing
WorkerAuthority/Task/approval registries and operator-target revocation ledger
remain unchanged. No Core route imports this qualification module or calls
Docker. UI PR #61 remains parked; the four exhausted Media proof attempts are
unrelated and untouched.

Future Core integration needs independently qualified real evidence, a specific
WorkerAuthority and Agent/Space permission, trusted target byte verification
at claim and at launch, durable operator approval/lease with revocation checks,
concurrency limits, explicit Evidence sanitization and abort/recovery logic.
Never use a manual receipt or unverified analysis plan as Core authorization.

## Canonical runtime alias verification, 8 October 2026

The existing source-owned runtime is exposed through an operator-owned local
`runtime-v6` symlink into its earlier offline source-build workspace. An initial
read-only **diagnostic** passed the unresolved symlink path directly to
`trusted_profile()` and consequently reported `rea_runtime_symlink_escape` for
its relative `node_modules/.bin` links. That check was misleading: the
production qualifier resolves `RUNTIME.resolve(strict=True)` **before**
calling `trusted_profile()` and before constructing Docker mounts. Retesting
with the actual canonical path passed the complete pinned source-owned REA
6.0.0 lock, module and dist digests, with network and Core Worker flags false.

This does NOT authorize a selected-target native Docker probe or remove the
symlink-escape guard: module links resolving outside the **canonical** runtime
root must still be refused. The candidate worktree itself does not bundle the
ignored local runtime or user-target snapshots; the operator must deliberately
provision/readily verify trusted local dependencies and approve any real manual
qualification separately. Never replace a failed canonical integrity check
with a bypass, and never confuse alias-relative path diagnostics with a real
canonical runtime escape.
