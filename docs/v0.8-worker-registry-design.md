# Zelo Core v0.8 — Supervisor and Worker Registry

v0.8 introduces a trusted process-local worker registry and deterministic supervisor for
developer work.

## Routing contract

Each `WorkerDescriptor` declares:

- a stable `worker_id`
- role and required capabilities
- implementation name
- enabled state
- routing priority
- `authority`
- `max_concurrency`

The supervisor selects only enabled workers whose role and capabilities satisfy the
request. Ties are resolved deterministically by descending priority and then ascending
`worker_id`.

The persisted `WorkerSelectionSnapshot` binds the selected descriptor, a content-derived
registry version, and the routing-policy version into the developer approval.

## v0.8 enforcement boundary

In v0.8, `authority` and `max_concurrency` are **declarative metadata only**.

They do not grant permissions and they do not increase concurrency. Concrete execution
authority remains enforced by the worker/runtime sandbox boundary, and the task engine
still serializes execution globally.

Before a second production worker such as Claude or Ox is registered:

1. descriptor authority must map to an enforced sandbox profile and unsupported authority
   must fail closed at registration;
2. `max_concurrency` must be enforced by the scheduler rather than treated as descriptive
   metadata;
3. each worker must receive an explicit trusted descriptor rather than relying on the
   single-worker `descriptor_for_worker()` default;
4. worker identity, registry contents, routing policy, validation environment, source HEAD,
   and execution artifact must remain independently revalidated at the appropriate approval
   and execution boundaries.

## Approval and execution

Expensive live developer revalidation happens when an operator approves a developer task.
Runner polling performs only cheap TTL/structural checks. Immediately before execution,
`DeveloperRuntime` performs definitive live checks again, including selected-worker
identity, sealed executable/code-mode-host binding, source state, and validation
environment identity.

This avoids performing executable probes or full validation-environment hashing in the
runner's high-frequency polling loop while preserving fail-closed execution.
