# v0.16 — Private one-use WhatsApp send-attempt claim

This Core-only gate follows the approved reply-intent ledger and outbound identity projection. It has no ASGI route, Meta credential, webhook listener, HTTP request, Worker or delivery status. Published v0.15.0 remains the latest release.

Ahmad may claim one possible send for one exactly approved verified reply. The claim rechecks current account selection and revocation, the immutable thread binding, saved reply-only Mind action and text, operator decision, current App Secret identity and all four trusted raw-to-opaque provider identities inside the same serialized SQLite transaction as the new attempt record. The returned raw provider IDs and reply text are ephemeral and redacted from the result representation.

The append-only `whatsapp_send_attempts` table is keyed by the reply intent and stores only opaque identity linkage, operator, UTC claim time, `send_outcome_unresolved`, `send_may_have_occurred=true`, `automatic_retry_allowed=false` and `transport_authority=false`. A second claim always refuses. Direct SQL cannot insert a rejected or revoked attempt or mutate/replace a recorded attempt. The isolated test database and WAL files are checked for raw provider IDs after a claim.

This conservative fence can remain unresolved even when no network request happened. A future sender must invoke this claim immediately before one qualified Meta request, never automatically retry a claimed intent, and append independently qualified provider response and status evidence. Live Meta account ownership, credential rotation, provider policy, external send, delivery, and operator acceptance remain NOT RUN. The claim alone grants no transport authority.
