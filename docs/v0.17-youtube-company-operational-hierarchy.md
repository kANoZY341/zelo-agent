# v0.17 — Real, explicitly opted-in YouTube company hierarchy

## What actually works

This optional Core feature registers **four active, trusted Zelo AgentSpecs**,
ready for *real* Project-bound instances and execution:

| Level | Registered Agent ID | Reports to | Read-only Task | Can permanently hire? |
| --- | --- | --- | --- | --- |
| VP | `youtube` | Zelo CEO | `research_run` | 1 Director |
| Director | `youtube_content` | VP | `research_run` | 1 Manager |
| Manager | `youtube_research` | Director | `research_run` | 1 Specialist |
| Specialist | `youtube_script_writer` | Manager | `research_run` | No |

These exact IDs and organizational levels are checked against the pinned
`youtube_content` *Harness draft*, but the source's **draft AgentSpecs are
never promoted, mutated or used as grant tokens**. The four active trusted
specifications, Research Worker and narrow Skills are authored and reviewed
in Zelo Core. The earlier standalone Research pilot instead uses
`youtube_topic_researcher`, deliberately avoiding the actual Manager ID.

All four Roles can create bounded **source-grounded research outputs** through
the existing Research Worker, but every Task—including a VP root Task—requires
an explicit active Project Campaign. Campaign ownership is enforced during
Task submission and again before Worker claim; an Org assignment alone cannot
run campaignless model work. This is not a token/money spending cap and does
not create or upload videos. Their
trusted objective and role-specific instructions are applied to real
`ModelRequest.system_prompt` only after normal Core claim-time identity
validation. Model-generated JSON does not bypass the Research Tool allowlist:
dispatch-time checks remain enforced. All roles have only
`list_workspace_files`, `read_workspace_file` and `repo_status`,
`workspace_read`, Research Worker, and the existing `evidence_retrieval`
Skill. No browser, computer, shell, API worker, channel credentials, external
account, publishing, Skill promotion or Space authority is granted.

The three executives additionally declare `organization_hire` and bounded
`max_subagents=1`, with a separate trusted active `organization` procedure
Skill. **The Skill itself grants no hiring permission.** All actual hiring
still requires a human-authenticated Core API call, active Project/Org state,
the next exact reporting level, and an exact live Campaign budget reservation.
There is no model-exposed creation Tool or hidden autonomy.

**The hierarchy is enforced in the execution authority, not merely in
the documentation or the user interface.** Generic POST `/agents` may create
only the root VP; it refuses direct creation of active company Director,
Manager or Specialist instances. A VP cannot submit Research without a
current active CEO-rooted Division assignment. Every descendant requires
an active, exact-level Organization assignment, a matching active parent
reporting assignment and an incoming live Campaign-backed Delegation. Core's
TaskService checks this again under its serialized transaction on submit,
retry and claim, **recursively to the CEO-rooted VP**: each of the at most
three active Delegations must share the exact Campaign, have an unexpired
owner-bound reserved resource proof, preserve the fixed depths **1 → 2 → 3**
and inherited `max_depth=3`, and retain the original level/unit and
registered parent-Agent identity. Revoking, expiring or replacing the
VP→Director Delegation with narrower authority immediately invalidates
Manager and Specialist Work claims, even when their own immediate parent
Delegations remain active. This cascade is checked before Worker dispatch,
not just in model instructions.

The company VP, Director and Manager are **not allowed to use Core's generic
AgentDelegationService** to grant authority to existing baseline Research or
other unrelated agents. They may create only their fixed next-level child
through the human-authenticated, budget-backed atomic
`AgentChildCreationService`. TaskService separately refuses any preexisting
or injected generic-child Delegation from a company executive, protecting
execution even if a legacy invalid record is present.

Child creation enforces the **exact trusted child role ID**, the strict
three-edge inherited depth ceiling, and the organizational level. A Director or Manager cannot hire after its own
parent Delegation was revoked, after its parent budget expired, or into a
different Campaign. The hiring guard additionally verifies its *entire*
ancestor Delegation chain under the same SQLite serialized writer.
Model-authored requests cannot skip `delegation_id`, move an Agent to a
different reporting unit, reset hierarchy depth, change Campaign ownership,
or dispatch after its assignment ends.

## Opt-in and registry/version safety

**Default Core behavior stays exactly unchanged**: absent the new startup
setting, the four active team roles are not registered, no team Skills are
added, and zero Projects/AgentInstances/Org assignments/Campaigns/Tasks are
created. The installed older standalone Research pilot retains its original
own opt-in setting and logic when company mode is disabled.

An operator can view the trusted immutable candidate (no mutation) via:

- Authenticated `GET /agent-factory/optional-teams/youtube-content`;
- Offline `.venv/bin/python -m scripts.preview_youtube_company_optin`.

The view includes the full *current* baseline+four-Agent registry digest and
the pinned upstream draft fingerprint. It is a proposal display, NOT an
activation token. After inspecting the source and operating safety, **only the
Managing Director** can deliberately configure the server for next boot:

`ZELO_YOUTUBE_COMPANY_APPROVED_REGISTRY_SHA256=<exact candidate registry digest>`

This 64-hex hash is an exact approved version identity, not an authentication
secret. An absent setting keeps the feature disabled. Stale/wrong/malformed
values abort startup. **It is mutually exclusive** with
`ZELO_YOUTUBE_RESEARCH_APPROVED_SPEC_SHA256` for the earlier standalone
specialist; no implicit pilot-to-company promotion is attempted.

All four company specs share one immutable whole-registry version with Core's
existing default Coding and Research specs. The enabling/restart gate checks
the currently non-retired AgentInstances under the SQLite serialized writer:

- Enabling a different registry refuses any existing active or paused
  AgentInstance of a different exact version.
- A normal restart with the same approved team and matching live identities
  succeeds.
- Removing the setting while any live instance still belongs to that team
  registry refuses startup instead of silently invalidating agent identities.
- Retired historical records stay terminal. No automatic migration/reassignment,
  resurrection or cleanup is performed.

The active `organization` Skill is added only for the explicitly selected
company registry. The normal Core `AgentActivationEvaluator`,
`SkillRegistry.validate_agents`, Tool/Worker/capability checks and per-Agent
persistent computer boundary all run before runtime startup completes. Source
integrity and startup approval are separate checks, not delegated to a model.

## Manual operator bootstrap (real persisted Core state)

After a reviewed company opt-in, the authenticated Managing Director can use
the **existing** Core endpoints/services (no duplicate project/agent factory):

1. Create a Project, Goal and Campaign for the YouTube company.
2. Under Organization, create the `Media` Division, a `YouTube`
   Department within it, and a `YouTube Research` Team under the Department.
3. POST `/agents` with `{"agent_id":"youtube","project_id":"<Project id>"}`,
   then assign this real VP instance to the Division. Core's existing
   `OrganizationService` verifies the VP reports to the Zelo CEO principal.
4. Set a Campaign `agent_steps` resource limit, and explicitly reserve
   two units for the current parent VP.
5. POST `/agents/<VP instance id>/children` with the exact Campaign and
   reservation IDs, Department ID, trusted child `youtube_content`, allowed
   task kinds `["research_run"]`, required capabilities `["research"]`,
   max depth 3, and unique idempotency key. Core atomically creates the
   Director Instance, Org assignment, and Campaign-bound Delegation.
6. Repeat with the Director as parent to create `youtube_research` Manager
   in the Team (a fresh reservation owned by that Director), then repeat
   with Manager as parent to create `youtube_script_writer` Specialist,
   again with a fresh owner-bound reservation and a depth no greater than 3.
7. POST `/agents/<Specialist instance id>/tasks` with a sourced
   `research_run` request, the exact Campaign ID and the live **incoming
   Delegation ID**. Core revalidates Project/AgentSpec/worker/parent Campaign
   reservation both on submission and on Worker claim. Inspect normal Task
   evidence/attempt records. Revoke a Delegation or pause/retire the active
   actor using existing Core APIs to fail closed on future claims.

This is already demonstrated by an actual **database-backed Core-service
end-to-end integration test** which instantiates all four roles with real
Division/Department/Team reporting assignments, three distinct
owner-bound Campaign reservations/delegations, idempotent creation receipts
and an actual Research Worker claim. A second test runs the specialist
through the real authenticated HTTP Task API and records the trusted
ModelRequest instructions and cited read-only result using a fixture model
provider—without an external account or a live model/API expense.

## Not yet automatic

This slice is the **operator-driven real company hierarchy**, *not* a
finished autonomous four-agent enterprise. Importantly:

- The Harness design-review decision is still historical design evidence,
  NEVER converted into an active AgentSpec permission by itself.
- No AI model can yet choose a budget, self-approve its hiring, automatically
  create Organizations or autonomously dispatch a full campaign.
- Existing Campaign budget reservations are bounded *proof of authority* for
  each Delegation; the resource is not yet measured LLM token/dollar spending.
- The separate single-Specialist task and Worker-attempt quotas remain scoped
  to `youtube_topic_researcher`; the company’s own execution is bounded by
  Campaign reservation expiry, existing task step/tool limits, manual approvals
  and parent identity/revocation checks. An independently reviewed real
  company per-attempt and cost budget is still needed.
- No permanent user-facing UI port yet; PR #61 is parked. REA remains
  inactive, and Media native-reader qualification attempts remain exhausted.

**Next gate:** actual operator-only atomic company bootstrap/approval and
measured shared Campaign resource accounting, followed by realistic local
model outcomes and failure recovery. None of these new authorities are
silently enabled by preview routes, imports, model text or design-review
receipts.
