# v0.15 — Explicit dual-approved delegated Space file execution

## Decision and intended acceptance

Issue #131 requires delegated Space execution. Current main already admits
one-hop delegated read/list Tasks with a child-owned Space confirmation and
rechecks delegation, Campaign budget and parent capability at file use.
This draft candidate additionally requires an independent current parent
confirmation for the same resource and operation. It extends the existing
owner -> Campaign budget -> Delegation -> Computer Task path rather than creating
another grant engine. Older queued delegated snapshots without a parent binding
fail closed after this change; an explicit new Task is required. This is not a
production permission or a completed v0.15 release.

Two alternatives were considered: implicitly inheriting a parent's Space grant,
or explicitly binding independent child and parent confirmations. Choose the
second. It preserves each Agent's authority, supports revocation by either side,
and never treats organizational membership as a grant. The initial qualified
path is one parent -> one child (depth=max_depth=1), read/list only, same Project
and the exact same immutable resource record. Nested delegation remains refused.

## Execution contract

A delegated Computer file Task must bind its child `space_activation_id` and
`parent_space_activation_id`. Core, not the request, captures the parent's current
Computer permission version. A v3 Computer execution snapshot binds these facts;
legacy v1/v2 requests cannot imply a parent grant. Nondelegated requests retain
their existing path and may not supply a parent confirmation.

Admission, retry, claim and the final serialized gateway check must verify exact
persisted Delegation, Campaign/Goal/Project and reserved unexpired budget;
current active parent and child identities; parent authority to delegate;
independent read/list confirmation for each; same immutable resource; each
Computer's file permission; both Core takeover barriers; and the claimed Task's
cancellation/attempt/payload identity. Revocation, pause, changed permission or
expired budget denies. Final checks repeat after bounded backend-control awaits,
under the same writer used for file access and audit. No remote call occurs
inside that writer. Content and arbitrary paths stay out of audit records.

## Normal startup and compatibility

Retain the existing single-observer registry and its digest unchanged. A separate
fixed Manager/observer registry may be selected explicitly by its complete
reviewed digest through the existing opt-in setting. No instance, delegation,
budget, Computer or Space confirmation is created by startup. Existing live
registry mismatches still refuse rather than migrate or rebind identities.
The operator creates the two Agents, their Computer grants, Campaign budget,
Delegation and separate Space confirmations through the normal authenticated APIs.

The new fields live in already-versioned JSON Task snapshots; no schema migration
or history rewriting is intended. Older source refuses unknown v3 snapshots,
which is safer than interpreting them as a weaker legacy authorization. Historical
Tasks/results and old single-observer configuration remain preserved.

## Operator preview and usage

Run `.venv/bin/python -m scripts.preview_space_read_team` to inspect the fixed
Manager/observer specifications and complete registry digest without loading
Settings, a database, credentials or a runtime. The existing single-observer
preview and approved digest are unchanged. Selecting the separate team uses
`ZELO_COMPUTER_OBSERVER_APPROVED_REGISTRY_SHA256`; never copy a digest from
an unreviewed model message. Normal startup must still reject incompatible
live registry bindings and cannot silently move existing Agents into this team.

The operator creates a Project, Goal and Campaign, then the fixed
`space_read_manager` and `computer_observer` AgentInstances. Explicitly enable
only each Computer's intended read permissions, start them and obtain required
fresh snapshots. Provision/register one resource in the Project; create and
confirm a separate operation-specific intent for EACH Agent. Reserve the
Campaign's `agent_steps` budget for the parent, then explicitly create its
one-level Delegation to the child (`max_depth=1`). A reservation is the existing
live delegation-budget proof, not a new per-read charging or accounting system.

Submit to `POST /agents/{child_instance_id}/tasks`:

```json
{
  "delegation_id": "REPLACE_WITH_EXACT_DELEGATION_UUID",
  "task": {
    "kind": "computer_run",
    "campaign_id": "REPLACE_WITH_BOUND_CAMPAIGN_UUID",
    "payload": {
      "action": "files_read",
      "path": "notes.txt",
      "space_activation_id": "REPLACE_WITH_CHILD_CONFIRMATION_UUID",
      "parent_space_activation_id": "REPLACE_WITH_PARENT_CONFIRMATION_UUID"
    }
  }
}
```

The `files_list` operation uses the same dual confirmation and its own `list`
rights; parent `list` does not imply `read`. No caller may supply the captured
parent Computer permission version or override the persisted parent identity.
Requests without separate parent evidence remain denied before resource lookup.

## Compatibility and qualification history

The initial three tests reproduced absent v3 input/execution. After adding the
binding, actual admission still refused until the use-point path was added.
The first combined execution check exposed a missing gateway in the test Runner;
that fixture was corrected. The next check exposed a production mistake reading
a nonexistent `Task.campaign_id`. A direct gateway regression reproduced it;
the correction reuses the established immutable CampaignTaskLink lookup.
A startup assertion incorrectly counted read-only Computer status inspection as
a hidden mutation; it now expects the two explicit `existing` lookups and still
forbids implicit starts or grants. The corrected initial group passed 30 tests.

Independent review found two concrete compatibility defects: default-null parent
input changed legacy request fingerprints, and null v3-only fields contaminated
v2 serialized snapshots. Two failing regressions reproduced both. Explicit
serialization now preserves the exact legacy representation and only emits the
parent fields for v3. The 32-test follow-up passed (3 warnings); simulated old
wire serialization is distinguished from running a previous deployed binary.
No database trigger or execution gate was weakened to repair those issues.

**Native qualification: NOT RUN.** The tool safety layer refused the write of
the new native two-Computer HTTP journey before creating its file. No native
Computer services were launched for this feature, and no alternate tool or
path was used to bypass that refusal. Existing nondelegated native receipts do
not qualify this delegated path. In-process Core tests use controlled Computer
backends and actual private Space files. This candidate must remain unmerged
and unactivated until required independent review, full CI and separately
permitted native qualification complete. No v0.15 release claim follows.

Native control responses are bounded observations, not an atomic lock across
two external Computers. Core-managed takeovers are revalidated after the awaits
under the same writer as the file use. Previously returned bytes cannot be
revoked retroactively; direct out-of-band backend changes retain the existing
backend-control limitations. These boundaries are not hidden by a PASS label.
