# v0.15 — Persistent Agent Computer / OpenBot foundation

## Goal

Reuse the mature per-agent computer lifecycle already exercised by
CopilotKit/OpenDots instead of rebuilding container, Chromium-profile, workspace
and supervisor plumbing from zero.

This is a **foundation slice** inside the existing v0.15 Computer Worker scope.
It does not reorder the roadmap and it does not grant any Agent new execution
authority.

## Reuse decision

Reviewed sources:

- CopilotKit/OpenDots at
  `c2569bb6a13a22e565cf3eb791c62267d06babb1`;
- the OpenBot revision pinned by that project:
  `b6932d31a8d6e7896c15139dfc27a6c6911deb27`.

Both are MIT licensed.

Zelo directly adapts the narrow OpenDots supervisor-deployment pattern:

- exact OpenBot source pin;
- supervisor-only Docker socket ownership;
- persistent per-agent computer volumes supplied by OpenBot;
- loopback-only supervisor for the initial host-run topology;
- fail-closed source patch when the pinned supervisor contract changes; and
- HMAC-derived child credentials so an Agent computer never receives the master
  computer token.

Zelo changes the child-token context to
`zelo-computer:<agent_instance_id>` and keeps Zelo Core authoritative.

## Zelo boundary

```text
AgentInstance
    |
    | exact trusted AgentSpec
    | computer intent
    v
Zelo Core / Agent Computer Adapter
    |
    | lifecycle only in this foundation
    | ensure / list / stop
    | exact identity validation
    v
Pinned OpenBot Supervisor
    |
    | creates/owns one computer
    v
Agent Computer
    +-- persistent browser profile
    +-- persistent workspace
    +-- later bounded browser/files/shell actions
```

The computer is an execution resource, not an authority principal.

## Current implementation

- `AgentSpec` can declare optional persistent-computer intent through
  `AgentComputerSpec`.
- New persistent-agent metadata is additive and does not change the historical
  v0.14 registry fingerprint when unused.
- Explicit Agent skill IDs are checked against the existing trusted Skill
  Registry and must fit the Agent's existing capability/task/tool upper bounds.
- `OpenBotComputerBackend` validates loopback supervisor configuration,
  derives per-AgentInstance credentials, bounds supervisor responses, validates
  exact container identity, and exposes only list/ensure/stop in this slice.
- `compose.agent-computers.yml` builds the exact pinned OpenBot computer image
  and hardened supervisor.
- Upstream MIT notices and provenance are retained under
  `deployment/agent-computers/`.

## Explicit non-goals

This slice does **not**:

- register a Computer Worker with Supervisor;
- create a `computer_run` task kind;
- expose browser/file/shell actions to Mind or Agents;
- add Computer Panel UI while the UI milestone is parked;
- grant Docker socket access to Zelo Core or Agent computers;
- expose the supervisor or computer ports publicly;
- fall back to the host shell/browser/files when the backend is unavailable;
- import CopilotKit Intelligence as Zelo's memory or skill authority;
- import OpenDots' Agent runtime, scheduler or permission system; or
- track OpenBot `main`/latest at runtime.

## Next gates

Before execution authority is enabled:

1. verify the pinned OpenBot build and supervisor source patch against the exact
   reviewed revision;
2. qualify persistent lifecycle and isolation on the Zelo host;
3. add Zelo-owned persisted per-AgentInstance computer permission state;
4. define typed bounded computer action/result contracts;
5. bind those contracts through Capability Registry, Skill Registry, Worker
   Registry/Supervisor and task execution identity;
6. prove revoke/cancel/takeover/handback behavior, including mandatory fresh
   browser snapshot after human control;
7. add Zelo audit records without secret values or unnecessary file contents;
8. only then expose Computer Panel actions through the future Control Desk UI.

The later Computer Panel may selectively adapt compatible OpenDots/OpenBot UI
patterns, but it remains a projection over Zelo Core state and authority.

## Skill learning relationship

v0.15 only binds trusted existing skills to AgentSpecs. The learning lifecycle
belongs to v0.18:

```text
evidence + outcomes
  -> candidate procedure
  -> bounded evaluation
  -> proposed skill
  -> approval/policy gate
  -> versioned Skill Registry publication
  -> measured use
  -> improve or roll back
```

Learning never grants new tools, Spaces, credentials, budgets or external-write
authority by itself.

## Reuse qualification beyond the backend

### Computer Panel

OpenDots' current `src/client/ComputerPanel.tsx` is largely plain React
(`useState`, `useEffect`, `fetch`-style API calls and local shared types).
It does not require CopilotKit UI components. Zelo Workspace is also React 19,
so a later focused port is technically practical.

Do **not** copy the component into the parked Zelo UI yet. Its current routes,
Dot types, permission model and action names are OpenDots-specific. Once Zelo
Core exposes real Agent Computer status/action/control contracts, port the useful
Browser/Files/Terminal/Activity tabs, polling lifecycle and Take Control /
Return Control interaction while replacing all authority and API bindings with
Zelo-owned ones. Preserve the OpenDots MIT attribution for materially adapted
UI code.

### Skill learning

OpenDots' automatic learning path is coupled to CopilotKit Intelligence Learning
containers and learned-skill delivery inside its agent runtime. Zelo should not
merge that runtime directly because Zelo's Skill Registry, memory, capability
bounds and promotion authority are already Core-owned.

Reuse the **lifecycle pattern**, not the provider ownership: conversation/task
evidence -> candidate skill -> evaluation -> proposal -> gated publication ->
versioned measured skill. Implement that natively in canonical v0.18, with a
future optional provider adapter only if it does not become the authority source.

### Space permissions

OpenDots' per-Dot Space grants confirm the product model, but Zelo already
persists full trusted AgentSpec snapshots into AgentInstances and binds instances
to projects. The new `space_permissions` field is therefore introduced as a
trusted Agent upper-bound now; v0.17 should bind it to Zelo's own project/document
authorization model rather than importing OpenDots' SQLite `dot_spaces` store.
