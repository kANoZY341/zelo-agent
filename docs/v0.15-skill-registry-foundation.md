# Zelo Core v0.15 — Skill Registry foundation

## Status

Second bounded implementation slice of v0.15 Capability and skills ecosystem.

The Capability Registry foundation is merged to `main` through PR #55 at
`4dcc5bf03dfe761d64df49f848762a163158d8df`.

## Goal

Create a trusted, versioned skill vocabulary on top of capability identities
without turning skills into execution authority.

A skill describes a compatible procedure surface. It does not run commands,
invoke tools, select workers, grant permissions, or bypass policy.

## Scope

This slice adds:

- immutable trusted `SkillSpec` definitions;
- immutable deterministic `SkillRegistry`;
- required capability identities;
- procedure identities;
- compatible Core task-kind and tool surfaces;
- draft/active/retired lifecycle;
- fail-closed validation against the Capability Registry;
- fail-closed validation against available task kinds and tools;
- validation that every active published AgentSpec procedure has a compatible
  active trusted skill;
- operator-authenticated read-only `GET /skills`.

## Non-goals

This slice does not add:

- skill execution;
- dynamic/model-authored skills;
- AgentSpec mutation from skills;
- new task kinds or tools;
- Browser, Computer, Python, API, Shell, Research or Media workers;
- external network, filesystem, subprocess or credential authority;
- MCP/plugin adapters;
- Ruflo/swarm execution;
- database migrations;
- new approvals, budgets, scheduler, promotion, merge or release authority.

## SkillSpec

A trusted skill binds:

- stable skill ID and version;
- human-readable description;
- one or more required capability IDs;
- one or more procedure IDs;
- zero or more compatible task kinds;
- zero or more compatible tools;
- lifecycle state.

All tuple fields are canonical, sorted and unique. Duplicate skill IDs fail
closed. The registry fingerprint covers all material definitions in canonical
order.

## Compatibility validation

An active skill is valid only when:

1. every required capability is active and valid for the `agent` subject;
2. every declared task kind exists in the current bounded Core task surface;
3. every declared tool exists in the current Tool Registry surface.

An active AgentSpec procedure is covered only when an active skill:

- declares that procedure;
- requires capabilities already held by the agent;
- uses only task kinds already allowed by the agent;
- uses only tools already allowed by the agent.

This is compatibility validation only. Passing it grants no new authority.

## Initial built-ins

The initial Skill Registry describes only procedures already used by the
published v0.14 default Coding and Research AgentSpecs:

- `core_implementation`
  - procedure: `implementation`
  - capabilities: `code_change`, `code_planning`
  - task: `developer_run`
- `core_review`
  - procedure: `review`
  - capability: `code_review`
  - task: `developer_run`
- `evidence_retrieval`
  - procedure: `evidence_retrieval`
  - capabilities: `evidence_synthesis`, `research`
  - task: `research_run`

All three are limited to the already-existing read-only workspace inspection
tool surface declared by their current AgentSpecs.

## Operator surface

Expose:

`GET /skills`

The endpoint requires operator authentication and returns only the immutable
registry snapshot and deterministic version.

There are no create, update, delete, run or execute skill endpoints.

## Authority boundary

The Skill Registry does not replace or widen:

- AgentSpec task/tool bounds;
- Capability Registry validation;
- Supervisor worker selection;
- WorkerAuthority;
- ToolPolicy;
- task validation and idempotency;
- approval gates;
- campaign budgets;
- audit/evidence;
- promotion, merge or release boundaries.

`SkillRegistry` intentionally has no `run()` or `execute()` method.

## Verification

Required gates:

1. deterministic registry version tests;
2. duplicate/canonicalization fail-closed tests;
3. capability subject/lifecycle validation;
4. unavailable task/tool rejection;
5. active-agent procedure coverage;
6. incompatible agent capability/task/tool boundary rejection;
7. operator-authenticated read-only API;
8. explicit proof that registry exposes no execution method;
9. diff check;
10. Ruff lint and format;
11. focused tests and full pytest;
12. adversarial review and exact-head GitHub CI.

## Continuation

After this slice merges, v0.15 can begin introducing new worker/tool surfaces one
bounded capability at a time.

Each new execution surface must separately define and verify:

- capability identity;
- skill/procedure compatibility;
- worker authority;
- tool policy;
- sandbox/network/filesystem/credential boundaries;
- approvals where required;
- deterministic evidence and audit;
- failure/retry/cancellation behavior.

A registry entry alone is never sufficient authority to execute.
