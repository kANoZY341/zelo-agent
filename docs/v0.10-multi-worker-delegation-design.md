# Zelo Core v0.10 — Multi-Worker Delegation

## Status

Architecture design for v0.10. Implementation must preserve the v0.9 worker-authority,
approval, isolation, validation, concurrency, recovery, and promotion boundaries.

v0.10 extends the existing architecture. It does not replace it.

> Models think. Workers work. Zelo decides.

## Mission

v0.10 proves that Zelo can delegate real coding work to more than one replaceable
developer worker while preserving a single Zelo-owned control plane.

The release must demonstrate that:

- Codex remains one worker, not the system itself;
- Claude Code can operate behind the same Zelo-owned worker contract;
- OpenCode can operate as a provider-neutral third worker, including a local-model lane;
- the architecture can accept Ox without another Developer Runtime redesign;
- Zelo selects workers from trusted descriptors using capability, role, routing policy,
  and bounded capacity;
- implementation and independent review can be delegated to different workers;
- approval-bound worker selection cannot silently change after approval; and
- v0.9 security and concurrency guarantees remain intact.

The v0.10 boundary is still the coding-worker layer. Agent Factory, specialist agents,
MCP ecosystems, persistent learning, Ruflo swarms, and business/trading/YouTube agents
remain future work.

## Existing v0.9 baseline

v0.9 already provides the pieces v0.10 must extend rather than rebuild:

- trusted `WorkerRegistry`;
- deterministic `Supervisor`;
- persisted `WorkerDescriptor` and `WorkerSelectionSnapshot`;
- versioned enforceable worker authority;
- approval compatibility bound to registry, routing, authority, sandbox, and worker
  identity;
- per-worker scheduler capacity;
- cross-process filesystem slot locks;
- concurrent developer execution;
- isolated standalone developer workspaces;
- trusted validation and post-worker review;
- promotion, merge, and release boundaries outside developer workers.

v0.10 must not weaken or bypass these boundaries.

## Architecture

```text
                              ZELO
                               |
                         Supervisor
                               |
                    trusted worker registry
                               |
                  capability / role selection
              /          |             |          \
             /           |             |           \
      Codex Worker  Claude Code Worker  OpenCode Worker  Ox Worker*
             \           |             |           /
              \          |             |          /
                    Developer Runtime
                           |
                 validation / review
                           |
                    Zelo-owned result

* OpenCode is a production target for v0.10 and should support a provider-neutral execution path.
* Ox may remain adapter-ready rather than production-enabled in the first v0.10
  implementation if its external interface is not stable enough to bind safely.
```

Workers remain execution harnesses. They do not become Zelo agents, supervisors, routing
authorities, promotion authorities, or owners of approvals.

## Worker-neutral contracts

The current worker contract must become genuinely implementation-neutral.

`DeveloperRuntime` must depend only on the common worker protocol and trusted routing
metadata. It must not branch on vendor names such as `codex`, `claude`, `opencode`, or `ox`.

Worker-specific executable, authentication, configuration, capability-probe, and sealed
artifact details belong behind each adapter.

A common persisted worker identity must contain only fields required across worker
implementations. Adapter-specific identity material must be represented through a bounded,
canonical, content-derived adapter identity/fingerprint rather than Codex-specific fields in
the shared contract.

The approval must still bind the exact worker identity that will execute.

## Trusted worker descriptors

Each production worker is registered explicitly by trusted application assembly.

A descriptor continues to bind at least:

- `worker_id`;
- role;
- capabilities;
- authority;
- implementation;
- enabled state;
- priority; and
- `max_concurrency`.

Worker IDs are stable Zelo identities. Implementation names describe the adapter and may not
be used as implicit authority.

Example developer registrations:

```text
worker_id=codex_core
role=developer
implementation=codex
capabilities=[python_development, repository_refactor, testing, zelo_core_development]

worker_id=claude_core
role=developer
implementation=claude_code
capabilities=[python_development, repository_refactor, testing, zelo_core_development]
```

## Capability-aware routing

A developer request must declare the trusted capability set required for the job. Callers do
not select arbitrary executables or permission sets.

The Supervisor selects only workers that are:

1. enabled;
2. registered for the required role;
3. capable of every required capability;
4. compatible with the required authority; and
5. eligible under the routing policy.

The routing policy remains deterministic for the same trusted registry and capacity state.

v0.10 may use priority and worker ID as deterministic tie-breakers after eligibility and
capacity considerations. The exact policy must be versioned and approval-bound.

No model may directly override the worker selection.

## Capacity-aware delegation

`max_concurrency` remains a hard ceiling enforced independently by the scheduler and
filesystem slot locks.

v0.10 adds selection across multiple eligible worker IDs. A worker without available
capacity may be skipped in favor of another eligible worker with capacity when the request
has not yet been approved.

Capacity is routing input, not permission to mutate an existing approval.

Once an approval snapshot is created, the selected worker is frozen. If that worker later
has no capacity, the task waits or follows the existing bounded deferral behavior. Zelo must
not silently switch the approved task to a different worker.

Rerouting to another worker requires a new selection snapshot and a fresh approval.

## Developer and reviewer roles

v0.10 introduces explicit worker-role separation for independent review.

At minimum:

```text
role=developer
role=reviewer
```

A developer worker may modify only its isolated candidate workspace under its approved
authority.

A reviewer worker receives a read-only review boundary. The production reviewer authority
must not permit mutation of the candidate workspace.

Target reviewer authority:

```text
workspace-read-no-network-v1
```

The exact realized filesystem/network policy must be content-fingerprinted using the same
fail-closed authority machinery established in v0.9.

When independent review is required, the reviewer selection must exclude the exact worker
instance that produced the candidate. A worker must not independently review its own work.

Implementation and review may use the same vendor through distinct trusted worker identities
only if the release policy explicitly permits that configuration. The preferred v0.10 proof
uses different implementations.

Examples:

```text
Claude Code -> implementation
Codex       -> independent read-only review
```

or:

```text
Codex       -> implementation
Claude Code -> independent read-only review
```

## Reviewer output

Reviewer execution must produce a bounded structured result owned by Zelo.

The reviewer may report findings, severity, affected paths, and a concise explanation, but it
must not modify files, approve promotion by itself, merge, push, tag, or release.

Reviewer output is evidence for Zelo and the human approval process. It is not an authority
decision.

## Claude Code adapter

The first new production adapter is `ClaudeCodeWorker`.

It must implement the same Zelo-owned worker protocol as Codex and provide:

- canonical implementation identity;
- trusted executable identity and digest;
- bounded configuration identity;
- authentication location identity without persisting credential contents;
- preflight/capability verification;
- approval-bound bind/unbind lifecycle;
- isolated execution;
- explicit environment allowlist;
- bounded stdout/stderr/events;
- timeout and process-group cleanup;
- fail-closed unsupported-version behavior; and
- no direct commit, push, PR, merge, tag, release, or promotion authority.

Any Claude-specific command-line flags, config files, environment variables, authentication,
or capability probes remain inside the Claude adapter.

Zelo must never pass its GitHub credentials or promotion credentials into the worker sandbox.

## Codex adapter

Codex remains supported through the existing adapter and existing v0.9 sandbox guarantees.

Refactoring the shared contract must not weaken:

- sealed executable/artifact handling;
- Bubblewrap isolation;
- authentication read restrictions;
- command network denial;
- trusted validation;
- boundary verification;
- cancellation cleanup; or
- approval compatibility.

## OpenCode adapter

The third production adapter is `OpenCodeWorker`.

It must satisfy the same Zelo-owned worker contract and security boundary as other workers while keeping provider choice inside the adapter. The initial supported mode should include a local-model lane so Zelo can execute lower-cost or free coding work without changing orchestration logic.

OpenCode-specific provider configuration, model selection, executable/config identity, environment variables, and authentication remain adapter-owned. Zelo binds only the canonical adapter identity/fingerprint and approved worker descriptor.

The OpenCode adapter must not gain extra authority merely because it can talk to multiple providers. Provider selection must never bypass Zelo's role, capability, approval, sandbox, validation, or promotion boundaries.

For v0.10, OpenCode shell access is deliberately narrow. The worker may use only approval-bound, read-only Git inspection commands under Zelo's trusted Git configuration. Arbitrary shell execution, repository-controlled Git programs, web tools, external-directory access, subagents, skills, promotion commands, and credential-bearing commands remain denied. Tests and linting continue to run through Zelo's trusted no-network validation boundary rather than through the model-facing worker namespace.

The OpenCode v2 execution transport is a Zelo-managed authenticated local HTTP server. Zelo starts the sealed OpenCode executable with `serve` inside the existing Bubblewrap worker sandbox, binds it only to `127.0.0.1` on an ephemeral port, generates a fresh per-run Basic-auth password, verifies `/api/info`, creates an approval-bound session, submits the prompt through the session API, waits through the bounded session endpoint, reads structured messages, interrupts the session on completion or failure, and then reaps the complete process group. The adapter does not use `opencode run`, `--standalone`, or the removed `--pure` flag.

Project OpenCode configuration is disabled for worker execution. The trusted inline configuration disables automatic compaction for bounded Zelo jobs, disables plugins, skills, commands, formatter, snapshots, and MCP servers, and binds the model/provider plus permission policy into the adapter identity. The initial production provider boundary remains localhost Ollama only; adding a credential-bearing remote provider requires a separate explicit credential-location and authority design rather than silently widening this adapter.

A practical v0.10 target is:

```text
opencode_local
role=developer
implementation=opencode
capabilities=[python_development, testing, documentation, repository_refactor]
```

The exact model/provider may be configured by trusted application assembly and must participate in the adapter identity/fingerprint when it can materially change execution behavior.

## Ox adapter readiness

The shared contract and registry must allow an `OxWorker` to be added without changing
`DeveloperRuntime`, task persistence, approval semantics, or routing architecture.

If Ox is production-enabled in v0.10, it must satisfy the same adapter requirements as Codex
and Claude Code. Otherwise v0.10 must include tests proving a fourth conforming adapter identity
can be registered and selected without vendor-specific runtime routing logic.

## Approval invariants

The approved worker selection must bind:

- exact worker descriptor;
- registry version;
- routing-policy version;
- requested role;
- requested capabilities;
- authority profile;
- authority-policy fingerprint;
- adapter identity/fingerprint;
- sandbox version;
- validation identity;
- source/base SHA; and
- effective execution limits.

Any material change invalidates compatibility.

An approved worker may not be replaced by another eligible worker without a new approval.

## Audit events

v0.10 should record bounded, non-secret events sufficient to reconstruct delegation decisions.

Expected event families include:

```text
worker_selected
worker_capacity_claimed
worker_capacity_released
reviewer_selected
review_started
review_completed
review_failed
```

Selection events should include safe metadata such as worker ID, implementation, role,
required capabilities, routing-policy version, and registry version.

Do not persist credentials, prompts beyond existing approved task payload rules, hidden model
reasoning, raw authentication material, or unrestricted worker logs.

## Parallel delegation

v0.10 must demonstrate real worker-specific parallelism.

For example:

```text
Task A -> codex_core  ------ running
Task B -> claude_core ------ running
```

Both may execute concurrently when their independent capacities allow it.

The existing v0.9 rule that non-developer work remains exclusive may remain unchanged unless a
separate architecture decision explicitly changes it. v0.10 does not need to widen that
boundary.

## Failure and recovery

All new worker and reviewer paths must preserve current fail-closed behavior.

Required properties include:

- no terminal failure solely because another eligible worker is temporarily at capacity;
- no silent rerouting of an already approved task;
- no capacity leak after timeout, cancellation, bind failure, unbind failure, or process
  recovery;
- no success result after a boundary-verification failure;
- interrupted work remains explicit and recoverable through existing task semantics; and
- reviewer failure cannot mutate or invalidate the candidate through side effects.

## Migration policy

Persisted schema changes must be additive, atomic, tested from the current released migration
head, and preserve rollback/failure behavior expected by the existing migration suite.

Do not rewrite released migrations.

If role/capability/selection data already lives entirely inside existing frozen JSON task
specifications, avoid adding a migration solely for convenience.

## Implementation sequence

The implementation should proceed in this order:

1. refactor the shared worker identity/contract to remove Codex-specific assumptions;
2. preserve Codex behavior behind the refactored contract;
3. extend trusted routing to explicit required capabilities and multi-worker capacity-aware
   pre-approval selection;
4. add explicit reviewer role and read-only reviewer authority;
5. add `ClaudeCodeWorker` behind the common contract;
6. add `OpenCodeWorker` behind the common contract, including a trusted local-model configuration path;
7. add independent reviewer execution/result handling;
8. prove parallel delegation across Codex, Claude Code, and OpenCode where capacity allows;
9. prove implementation/reviewer separation;
10. add Ox adapter or fourth-adapter conformance proof;
11. run the complete regression, security, migration, and adversarial review process.

Each step must keep the repository testable. Do not combine all architectural changes into one
unreviewable rewrite.

## Acceptance criteria

v0.10 is not release-ready until all of the following are demonstrated:

1. Codex still executes through the common worker interface with no v0.9 security regression.
2. Claude Code executes a real Zelo developer task through a production adapter.
3. OpenCode executes a real Zelo developer task through a production adapter, with at least one trusted local/provider-neutral configuration path.
4. `DeveloperRuntime` contains no vendor-specific Codex/Claude/OpenCode/Ox routing branches.
5. shared persisted worker identity is implementation-neutral.
6. required role and capabilities participate in trusted selection and approval binding.
7. at least three eligible production workers can be registered simultaneously.
8. selection is deterministic for the same trusted state.
9. pre-approval routing can choose another eligible worker when one is at capacity.
10. post-approval capacity contention never silently changes the selected worker.
11. rerouting to another worker requires a fresh approval.
12. per-worker scheduler and filesystem capacity ceilings remain enforced.
13. Codex, Claude Code, and OpenCode can execute separate developer tasks concurrently when capacity allows.
14. reviewer selection uses an explicit reviewer role.
15. reviewer execution is read-only and network-denied under a content-fingerprinted authority
    profile.
16. an independent-review workflow cannot select the exact producing worker instance.
17. reviewer output is structured, bounded, auditable, and cannot promote or modify code.
18. implementation by one worker and review by another is demonstrated end-to-end.
19. a fourth conforming worker can be added without changing Developer Runtime architecture.
20. timeout, cancellation, recovery, and audit tests cover both developer and reviewer paths.
21. released migrations remain unchanged and migration tests pass.
22. Ruff check, Ruff format check, `git diff --check`, and the complete pytest suite pass.
23. an independent adversarial review finds no unresolved release blocker.

## Release proof

The target v0.10 proof is:

```text
Developer task A
Zelo -> Codex -> isolated implementation -> trusted validation -> success

Developer task B
Zelo -> Claude Code -> isolated implementation -> trusted validation -> success

Developer task C
Zelo -> OpenCode -> isolated implementation -> trusted validation -> success

Parallel proof
Codex task + Claude task + OpenCode task can execute concurrently within independent worker capacities

Independent review proof
Claude Code -> implementation
Zelo        -> selects separate reviewer
Codex       -> read-only review
Zelo        -> persists structured review result
```

The inverse implementation/reviewer pairing should also be covered where supported.

This proves the worker layer is genuinely replaceable and gives v1.0 a stable foundation for
the later Coding Agent and Agent Factory.
