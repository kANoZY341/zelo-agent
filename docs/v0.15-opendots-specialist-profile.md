# OpenDots Specialist Dot profile — Core-only read-only projection

The operator-only endpoint `GET /agents/{instance_id}/specialist-profile`
uses an immutable, version-pinned `AgentSpec` saved by the existing
`AgentInstanceService`, the trusted `AgentFactory` registry and the Core
`SkillRegistry`. It does not load OpenDots' runtime or call OpenBot, a model,
a Worker, a Skill promoter, a filesystem path or an external provider.

The response shows the registered instructions and their origin, the exact
memory namespace and configured learning policy, per-Skill catalog eligibility,
declared Spaces and tools, plus the active/paused/retired and project state.
Every skill retains lifecycle, version, registry provenance, compatibility and
an explicit denial reason when absent/incompatible/inactive. Its compatibility
is **not** execution approval. A stale AgentSpec or retired registry entry
never becomes trusted just because it was once persisted: on a registry
mismatch the profile redacts instructions and all declarations.

The typed view deliberately reports **zero effective Space access and zero
verified Worker/Tool grants**. Declared tools still require a separately
validated Task/Worker claim and Tool Gateway checks. Declared Spaces are not
usable until the separate, per-resource enforcement and revocation gates in
issue #131 pass. `skill_learning=propose` is not autonomous publication; it
uses the existing governed learning pipeline. The status flags explicitly
mark no upstream Dot runtime and no operation or permission mutation.

The endpoint only supports GET and existing operator authentication. It does
not replace existing `GET /agents/{instance_id}/learned-skills` or Computer
Panel status. The cyberpunk UI and interactive OpenDots React Computer Panel
remain parked with UI PR #61. This is an inspection-oriented intermediate
step, not full Specialist lifecycle activation.
