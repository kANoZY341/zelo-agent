# v0.15 — RepositoryInspector linked worktree qualification

**Issue:** #124, reported on 8 October 2026. The existing
`RepositoryInspector.inspect()` refused clean linked Git worktrees because it
required `<source>/.git` to be a directory, whereas a genuine Git worktree
has a small `.git` **file** referring to its registered administrative
directory.

## Minimal fix and security checks

A normal clone still needs a real, owner-controlled `.git` directory. The
inspector now also accepts a linked worktree only when:

- `.git` is an actual owner-controlled, non-symlinked, single-linked,
  non-group-writable small regular file; its `gitdir:` pointer has a canonical
  absolute path and no traversal or control characters
- the destination is an owner-controlled, non-aliased admin directory immediately
  below the registered common Git directory's `worktrees/<identity>` path
- the admin directory's reciprocal `gitdir` file names **this exact**
  configured source root's `.git` file, and `commondir` is the standard
  `../..` pointer to the checked common directory
- sanitized `git rev-parse` reports the exact configured top-level, absolute
  admin directory, absolute common Git directory, and a real working tree

Git commands continue using the established bounded, noninteractive process
wrapper, timeouts and maximum-output bounds. The entire repo metadata identity
and clean Git status/HEAD are rechecked after source file inspection to reject
changes while inspecting.

Inspected source files retain the existing descriptor-relative, no-symlink,
bounded file policy and REA vendored data exclusion. No Git metadata content,
review evidence, runtime files, secrets, authorization tokens or untrusted
model instructions are admitted to the inspection result. This change does
**not** authorize the Developer Worker to execute inside linked worktrees:
the original approval, validation, reviewer and developer-sandbox gates still
apply independently. It also does not authorize self-merges, releases,
deployments or automatic skill promotion.

## Qualification evidence

The regression suite reproduces the original failure before the code fix: a
valid registered worktree refuses inspection and a dirty registered worktree
refuses before Git clean-status evaluation. It also exercises unrelated
forged `.git` pointers, copied pointers without reciprocal registration and
symlinked Git metadata; none are accepted. After the fix all affected focused
inspector tests pass. Normal clones, dirty repos, tracked credential exclusions,
bounded source sampling and inspection fingerprints stay unchanged.

For complete self-improvement Task tests in a separate isolated development
worktree, first provision a **local, trusted `.venv`** in that checkout (the
Developer validation contract hashes `ROOT/.venv`). A missing/invalid
checkout-local validation environment is a different refusal, not the original
linked-worktree inspection defect.
