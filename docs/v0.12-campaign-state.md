# Zelo v0.12 — Campaign ownership and operational state

## Status

Second implementation slice of v0.12, after the Project/Goal + Context Resolver seed.

## Goal

Turn isolated Core tasks into durable work owned by a Goal through a Campaign,
without introducing the later scheduler or v0.13 memory early.

The ownership chain becomes:

```text
Project
  -> Goal
     -> Campaign
        -> Core Task
           -> dependency edges
        -> Campaign events
        -> Campaign checkpoints
```

## Campaign boundary

A Campaign is Core-owned durable operational state. It belongs to exactly one
Goal and is not a UI-only grouping.

This slice adds:

- durable Campaign records;
- optional Campaign ownership on existing Core tasks through a dedicated link;
- immutable dependency edges between tasks in the same Campaign;
- runner gating: a task is not claimable until all dependencies have succeeded;
- append-only ordered Campaign events;
- immutable versioned Campaign checkpoints.

Task payloads, approvals, worker selection, execution, validation, promotion,
merge and release authority remain owned by the existing Core task system.

## Dependency rules

Dependencies are deliberately bounded:

- a task may have at most 32 dependencies;
- duplicate dependencies are rejected;
- dependencies require Campaign ownership;
- every dependency must already exist and belong to the same Campaign;
- a task cannot depend on itself;
- new tasks can only reference already-created tasks, making cycles impossible
  through the public submission contract;
- the runner treats blocked tasks as non-claimable until every dependency has
  reached `succeeded`.

Failure/cancellation propagation is intentionally deferred to the later
cancellation/recovery slice.

## StateStore seed

Campaign events and checkpoints establish the first operational StateStore
boundary.

Events record meaningful Campaign lifecycle facts such as Campaign creation,
task attachment, task completion and checkpoint creation. Checkpoints are
bounded JSON snapshots with monotonically increasing versions.

This is operational state, not persistent memory. It must not contain hidden
reasoning.

## Not in this slice

- scheduler;
- leases;
- shared budget accounting;
- autonomous Mind wake cycles;
- failure/cancellation propagation;
- Research specialist;
- workspace Campaign UI;
- v0.13 personal/project/agent memory.

## Proof

The slice is complete when tests prove:

1. Campaigns persist under active Goals.
2. Campaign events are ordered and durable.
3. Checkpoints are versioned and size-bounded.
4. Campaign-owned tasks expose their ownership and dependency IDs.
5. A dependent task cannot be claimed before its prerequisite succeeds.
6. Cross-Campaign dependency edges are rejected.
7. Existing non-Campaign task behavior remains compatible.
