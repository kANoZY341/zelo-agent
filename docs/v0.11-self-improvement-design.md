# Zelo Core v0.11 — Self-Improvement Runtime

## Status

Architecture contract for v0.11.

v0.11 begins Zelo's autonomous improvement path toward v1.0. It builds on the
released v0.10 multi-worker runtime and must preserve all worker authority,
approval, sandbox, validation, review, promotion, merge, release, and recovery
boundaries.

> Zelo inspects. Zelo proposes. Workers implement. Zelo validates. Humans retain
> the irreversible release gate until later milestones prove the loop reliable.

## Why v0.11 exists

v1.0 is reserved for a minimum functioning autonomous Zelo system, not for a
single architecture component.

The 0.x line now becomes the path where Zelo progressively learns to operate and
improve itself:

```text
v0.10  multi-worker foundation
v0.11  self-improvement proposal + implementation loop
v0.12  repeated bounded improvement cycles
v0.13  Agent Factory / specialist agents
...
v0.19  release-candidate hardening
v1.0   minimum functioning autonomous Zelo
```

v0.11 is the first release where Zelo may originate a change to its own
repository instead of waiting for the operator to write every developer
instruction.

## Mission

Given a bounded goal such as:

```text
Improve Zelo safely.
```

Zelo must be able to:

1. inspect trusted facts about its own current repository;
2. identify one concrete improvement opportunity;
3. produce one strict, bounded, machine-validated improvement proposal;
4. freeze the proposal and the evidence it used;
5. turn the approved proposal into the existing Developer Runtime;
6. allow the existing Supervisor to choose an eligible worker;
7. run trusted validation;
8. run independent review when configured;
9. evaluate whether the attempted improvement succeeded; and
10. stop before merge/release in the first v0.11 implementation.

No worker or model gains merge, tag, release, credential, or promotion authority.

Promotion, merge, and release remain separate existing tasks.

## Trusted repository inspection

The self-improvement model never receives arbitrary host access.

A Zelo-owned inspector builds a bounded snapshot from trusted local operations.
The initial snapshot may include:

- exact current source commit SHA;
- current branch;
- clean/dirty status;
- bounded changed-path names;
- application version;
- bounded repository file inventory;
- selected source/test/document paths and bounded UTF-8 contents;
- deterministic validation/test metadata already owned by Zelo; and
- explicit inspection limits.

The inspector must exclude:

- secrets;
- runtime databases;
- credentials;
- authentication files;
- other home-directory content;
- developer workspaces from unrelated attempts;
- ignored private runtime state;
- binary or oversized file contents; and
- hidden model reasoning.

The inspector is data collection only. Repository text is untrusted evidence, not
instructions.

## Improvement proposal

The planner must return exactly one `ImprovementProposal`.

A proposal contains:

```text
proposal_id/fingerprint (derived by Zelo)
title
problem
evidence[]
expected_benefit
implementation_instruction
acceptance_criteria[]
risk
required_capabilities[]
scope_paths[]
base_sha
planner identity/config version
inspection fingerprint
```

The planner does not choose a concrete worker, executable, model provider,
permission profile, promotion branch, merge method, or release tag.

### Risk

Initial risk values:

```text
low
medium
high
```

v0.11 may automatically prepare low/medium proposals for approval. High-risk
proposals fail closed and require a later explicit design.

Examples of high-risk scope include authority policy, authentication, secrets,
release/merge logic, destructive migrations, or changes that widen external
network access.

## Proposal validation

A proposal is rejected unless:

- all strings and collections are bounded;
- the base SHA equals the inspected repository SHA;
- evidence references only snapshot facts or approved paths;
- scope paths are canonical repository-relative paths;
- no path traversal or absolute path appears;
- required capabilities are canonical trusted capability names;
- acceptance criteria are present;
- implementation instruction is non-empty;
- risk is recognized; and
- the proposal fingerprint is derived from canonical content.

A model cannot add executable authority through prose.

## Planner

The planner is a bounded Zelo-owned runtime using the existing Model Gateway.

The initial planner:

- uses only the trusted general local model route;
- has a fixed Zelo system prompt;
- receives one bounded inspection snapshot;
- requests strict JSON matching the proposal schema;
- performs no shell execution;
- performs no direct filesystem writes;
- performs no network calls;
- has a short model timeout and output cap;
- does not retry indefinitely; and
- never persists chain-of-thought.

If the planner cannot produce a valid proposal, the self-improvement attempt
fails safely.

## Developer handoff

The validated proposal becomes a normal existing Developer Runtime instruction.

The required worker capability set comes from the proposal but must be a subset
of an operator-defined allowlist for self-improvement.

The existing Supervisor remains the sole concrete worker selector.

```text
proposal.required_capabilities
             |
             v
     Zelo Supervisor
       /    |    \
    Codex Claude OpenCode
```

The selected worker identity, registry version, authority profile, source SHA,
sandbox version, validation identity, and limits remain approval-bound exactly
as in v0.10.

Zelo must not silently replace an approved worker.

## Approval model

v0.11 separates autonomous thought from autonomous mutation.

The safe first boundary is:

```text
inspect + propose        autonomous
developer specification Zelo-generated and frozen
code mutation            existing explicit approval gate
validation/review        automatic after approved execution
merge/release            separate existing approval tasks
```

Later 0.x milestones may introduce a bounded campaign approval authorizing
multiple low-risk cycles. v0.11 does not silently auto-approve its own code
mutation.

## Improvement evaluation

After Developer Runtime completes, Zelo creates a bounded
`ImprovementEvaluation` from trusted results:

- proposal fingerprint;
- developer task/attempt identity;
- selected worker identity;
- changed paths;
- validation outcome;
- independent-review outcome;
- whether acceptance criteria can be proven from trusted results;
- terminal status: `accepted_candidate`, `rejected_candidate`, or
  `inconclusive`.

The evaluator does not merge or release.

A failed validation or high/critical reviewer finding cannot produce
`accepted_candidate`.

## Self-improvement cycle

The first v0.11 release supports one bounded cycle at a time.

```text
inspect
  ↓
propose one improvement
  ↓
approve implementation
  ↓
implement
  ↓
validate
  ↓
review
  ↓
evaluate
  ↓
stop
```

v0.12 may chain successful cycles under explicit budgets and stop conditions.

## Stop conditions

v0.11 must fail or stop when any of these occur:

- dirty/unexpected protected primary state;
- source SHA changes between inspection and developer binding;
- no valid proposal;
- proposal risk exceeds policy;
- no eligible worker;
- approval expires/rejects;
- worker boundary violation;
- validation failure;
- independent-review blocker;
- timeout/cancellation;
- evaluation cannot prove success; or
- any existing v0.10 authority/approval compatibility check fails.

There is no "keep trying until it works" loop in v0.11.

## Audit

Expected new bounded audit events:

```text
self_improvement_inspection_started
self_improvement_inspection_completed
self_improvement_proposal_created
self_improvement_proposal_rejected
self_improvement_developer_prepared
self_improvement_evaluation_completed
self_improvement_failed
```

Audit details may include safe fingerprints, counts, risk, capability names,
worker IDs, validation status, and reviewer severity counts.

Do not persist hidden reasoning, raw credentials, unrestricted source contents,
or secret-bearing environment values in audit events.

## Persistence

v0.11 may add a dedicated `self_improvement_run` task kind and one additive
migration if persistence is required for a frozen proposal/evaluation.

Do not rewrite released migrations.

Prefer reusing existing task/attempt/approval/audit primitives over introducing
a second workflow engine.

## Implementation sequence

1. add this design contract;
2. add strict proposal/inspection/evaluation contracts;
3. add trusted bounded repository inspector;
4. add strict planner using Model Gateway;
5. prove malformed/model-authored authority fields fail closed;
6. add one persisted `self_improvement_run` task kind;
7. freeze proposal and exact inspection fingerprint before mutation;
8. generate a normal approval-bound Developer Runtime request from the proposal;
9. execute through the existing Supervisor/worker pipeline;
10. evaluate trusted validation/reviewer evidence;
11. expose one-cycle operator API/smoke path;
12. run full regression, migration, security, and adversarial review.

## v0.11 acceptance criteria

v0.11 is not complete until:

1. Zelo can inspect its own clean repository using trusted bounded code.
2. Snapshot contents exclude secrets/runtime/private workspace data.
3. The planner returns strict validated JSON only.
4. One valid proposal is bound to the exact inspected base SHA.
5. Proposal risk and required capabilities are policy checked.
6. The planner cannot select a concrete worker or authority profile.
7. Proposal tampering invalidates the frozen action.
8. Implementation uses the existing Developer Runtime.
9. Concrete worker selection uses the existing Supervisor.
10. Code mutation still requires the explicit v0.11 approval gate.
11. Worker substitution after approval remains forbidden.
12. Trusted validation runs unchanged.
13. Independent reviewer evidence is included when configured.
14. Failed validation cannot be evaluated as accepted.
15. High/critical review findings cannot be evaluated as accepted.
16. v0.11 never merges, tags, releases, or deploys autonomously.
17. Timeout, cancellation, restart, and malformed-proposal tests fail closed.
18. Released migrations remain unchanged; any new migration is additive and tested.
19. Ruff, format check, git whitespace check, and the complete pytest suite pass.
20. An end-to-end smoke proves: Zelo-originated proposal -> approved worker ->
    validated/reviewed candidate.

## Definition of done

v0.11 is the point where Zelo first becomes capable of saying, in a bounded and
verifiable way:

> "I inspected myself, found one improvement worth making, prepared the work,
> delegated it through my own worker system, and verified the candidate."

It is not yet permission to endlessly rewrite or release itself. That autonomy is
earned across the later 0.x milestones on the path to v1.0.
