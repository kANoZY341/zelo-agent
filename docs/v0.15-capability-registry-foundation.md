# Zelo Core v0.15 — Capability Registry foundation

## Status

First implementation slice of v0.15 Capability and skills ecosystem.

v0.14.0 is published from
`3b87bbe4dc9956fbb8b11108faa911c4b23de5c9` with tag `v0.14.0`.

## Goal

Create one Zelo-owned, versioned vocabulary for capability identities before
adding Browser, Computer, Python, API, Shell, Research, Media, skill, MCP/plugin,
or swarm execution surfaces.

The core rule remains:

> Capabilities describe what a trusted actor can satisfy. They do not grant authority.

Actual execution authority remains in Core tasks, AgentSpec task/tool bounds,
WorkerAuthority, ToolPolicy, approvals, budgets, sandboxing and audit.

## Scope

This slice adds:

- immutable trusted `CapabilitySpec` definitions;
- an immutable `CapabilityRegistry`;
- deterministic content-derived registry versioning;
- explicit capability subjects: `agent` and/or `worker`;
- lifecycle state: `draft`, `active`, or `retired`;
- fail-closed validation of AgentSpec capability declarations;
- fail-closed validation of AgentSpec WorkerRequirement capabilities;
- fail-closed validation of configured WorkerDescriptor capabilities;
- capability-registry identity bound into Agent Factory activation evidence;
- an authenticated read-only registry snapshot for operator inspection;
- built-in definitions only for capabilities that v0.14 already uses.

## Non-goals

This slice does not add:

- new task kinds;
- new workers or tools;
- browser, computer, Python, shell, API, research or media execution;
- skill execution or a Skill Registry;
- MCP/plugin or Ruflo adapters;
- database tables or migrations;
- model-authored capability definitions;
- dynamic capability registration;
- new network, filesystem, subprocess or credential authority;
- new approvals, scheduler authority, merge authority or release authority.

## CapabilitySpec

A capability definition is trusted configuration, never model output.

It binds:

- stable capability ID and version;
- human-readable description;
- one or more valid subjects (`agent`, `worker`);
- lifecycle state.

Subject compatibility is descriptive validation only. A capability marked for
a worker does not authorize a worker process, command, tool or credential.

## Registry behavior

The registry is immutable after trusted application assembly. Its SHA-256
fingerprint covers every material definition in canonical order.

Duplicate capability IDs fail closed. Capability subject lists must be canonical
(sorted and unique).

Validation distinguishes:

- capability not registered;
- capability not active;
- capability subject mismatch.

These conditions never silently remove a requested capability.

## Existing built-ins

The first registry describes only current trusted v0.14 vocabulary:

- `code_change` — agent;
- `code_planning` — agent;
- `code_review` — agent and worker;
- `evidence_synthesis` — agent;
- `research` — agent;
- `zelo_core_development` — worker.

A later v0.15 slice may version a definition when a new trusted worker actually
provides that capability. For example, a future Research Worker may extend the
`research` subject surface only when that worker exists and is separately
authority-bounded.

## Activation integration

Agent Factory activation evaluation gains deterministic checks for:

- AgentSpec capability definitions;
- WorkerRequirement capability definitions and worker subject compatibility.

The activation surface digest and report bind the exact Capability Registry
version. The current activation evidence contract is
`zelo-agent-activation-policy-v4`. v1 remains the historical v0.14 policy and
v2 is the first v0.15 Capability Registry integration. v3 additionally binds
persistent Computer Agents to an explicit computer profile, the
`computer_read` capability, and an enabled read-only Computer Worker before
`computer_run` may activate. v4 separately requires explicit trusted browser
endpoint grants and an enabled `computer_navigate` Worker before an Agent
declaring navigation authority may activate. Changing capability definitions or
this execution surface therefore changes activation evidence.

Configured WorkerDescriptors are also validated against the trusted registry at
application assembly. Unknown, inactive, or subject-incompatible worker
capabilities fail startup rather than entering Supervisor routing.

The Capability Registry does not select workers. Supervisor remains the worker
selection authority.

## Operator surface

Expose a read-only authenticated snapshot:

`GET /capabilities`

The response includes:

- registry schema/version;
- canonical capability definitions.

There is no create/update/delete capability endpoint in this slice.

## Verification

Required gates:

1. deterministic registry version tests;
2. duplicate/canonicalization tests;
3. unknown/inactive/subject-mismatch fail-closed tests;
4. current Coding and Research AgentSpecs validate;
5. configured worker capabilities validate;
6. activation evidence binds capability registry version;
7. operator endpoint requires authentication;
8. no new authority is created by capability metadata;
9. diff check;
10. Ruff lint and format;
11. full pytest;
12. adversarial review and exact-head GitHub CI.

## Next slice

After this foundation is merged, add the trusted Skill Registry on top of
capability identities. Skills may bind procedures, required capabilities, task
kinds and tools, but must remain non-authoritative metadata until execution is
separately introduced and policy-bound.
