# Zelo Core v0.14 — Agent registry foundation

## Status

First implementation slice of v0.14 Agent Factory.

## Architecture note — 1 October 2026

This document records the original first-slice implementation. Its flat
DepartmentSpec manager/producer shape is now transitional.

The canonical organizational model is defined by
`docs/zelo-organizational-authority-model.md`:

```text
Human Managing Director
  -> Zelo Group CEO
    -> VP
      -> Director
        -> Manager
          -> Specialist Agent
```

Future v0.14 slices evolve departments into organizational containers and keep
durable reporting relationships separate from temporary task delegation. The
historical registry records remain valid evidence of the implementation state
that created them.

v0.13.0 is published from
`adc43d856a29fdcacdba80a273566aefaa0b98f0`. This slice starts from that
release and does not change task execution authority.

## Goal

Establish Zelo-owned, versioned identities for specialist agents and departments
before any generic specialist execution or subagent creation is enabled.

The core rule remains:

> Models think. Agents specialize. Workers work. Tools act. Zelo decides.

## Scope

This slice adds:

- frozen versioned `AgentSpec` records;
- frozen versioned `DepartmentSpec` records;
- deterministic registry fingerprints;
- explicit lifecycle state: `draft`, `active`, or `retired`;
- manager/producer department assignments;
- canonical agent memory namespaces;
- worker-neutral delegation requirements;
- agent-level task, tool, permission and procedure upper bounds;
- review requirements and bounded lifecycle limits;
- fail-closed activation validation against trusted task/tool surfaces;
- exact registry bindings for later persisted execution snapshots;
- built-in Coding and Research templates that describe the already-existing
  specialist surfaces without replacing them.

## Non-goals

This slice does not add:

- a new task kind;
- database tables or migrations;
- model-authored agent definitions;
- dynamic agent creation;
- persisted agent instances;
- parent/child execution;
- recursive subagents;
- autonomous agent-to-agent messaging;
- new tools or worker authority;
- browser, shell, API or computer workers;
- automatic memory writes;
- new approval, merge or release authority.

## AgentSpec

An `AgentSpec` is trusted configuration, not runtime model output.

It binds:

- stable agent ID and version;
- specialist role and objective;
- capabilities;
- allowed Core task kinds;
- allowed Zelo tools;
- declared permissions and procedures;
- canonical `agent/<agent_id>` memory namespace;
- optional worker-neutral role/capability requirements;
- review requirement;
- lifecycle state;
- bounded active-instance count;
- explicit subagent authority and limit.

A spec never names Codex, Claude Code, OpenCode, model providers, executables,
credentials or GitHub tokens.

## DepartmentSpec

A department binds a stable department ID to:

- objective;
- optional manager agent;
- one or more producer agents;
- lifecycle state.

An omitted manager means Zelo directly supervises the department. This prevents
inventing a manager agent before one has an explicit trusted spec.

All referenced agents must exist in the same registry. An active department
cannot activate while an assigned manager or producer is inactive.

## Registry and activation

The registry is immutable after trusted application assembly. Its SHA-256
fingerprint covers every material agent and department field in canonical order.

Changing an agent version, lifecycle, authority declaration or department
assignment changes the registry fingerprint.

Activation is separate from registration. For every active agent, application
assembly verifies that declared task kinds and tools exist in the trusted Core
surfaces. Missing references fail startup rather than silently reducing or
widening authority.

The first built-ins are:

- `coding` under the `engineering` department;
- `research` under the `research` department.

Both remain backed by their existing v0.12 runtimes. Agent Factory does not route
tasks through them yet.

## Reuse from the parked experiment

The parked `feat/v1.0-agent-factory` branch is intentionally not merged. It
diverged from the v0.10 baseline and predates the v0.11-v0.13 authority, memory,
scheduler and storage work.

This slice reuses only compatible ideas:

- immutable trusted specs;
- canonical identifiers;
- content-derived registry versions;
- worker-neutral delegation requirements;
- exact snapshot matching;
- fail-closed disabled/unknown identities.

The v0.14 implementation is new code on the released v0.13 architecture.

## Next slices

After this foundation is merged:

1. persisted agent instances and lifecycle transitions;
2. project binding and project-scoped memory assembly;
3. bounded parent-child delegation contracts;
4. Coding/Research execution through the generic agent identity layer;
5. organizational role/unit/reporting-assignment contracts;
6. hierarchy-aware bounded subagent creation under explicit budgets and depth limits;
7. activation/evaluation gates before executive and specialist templates.

No later slice may bypass Core tasks, ToolPolicy, Worker Supervisor, approvals,
budgets, audit or release boundaries.
