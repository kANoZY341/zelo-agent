# v0.15 — Governed Agent skill learning

## Status

Proposal persistence, bounded Agent task submission, and operator review are
implemented as an inert Core-record slice. This document defines the first
governed learning lifecycle for persistent factory-managed Agents. Proposals
remain outside live Skill Registry activation.

The existing foundations remain authoritative:

- `AgentSpec.skill_learning` is `disabled | propose`;
- `SkillRegistry` is immutable trusted Core configuration;
- `SkillSpec` describes compatibility and never executes anything;
- Agent capabilities, task kinds, tools, Spaces, permissions, approvals and
  budgets remain authoritative outside the skill layer;
- normal Zelo review/promotion controls own repository/config changes.

## Goal

Give each persistent Agent a bounded way to learn reusable procedures from its own
validated outcomes while preserving the permanent rule:

> Learning may improve procedure knowledge. Learning never grants authority.

An Agent with `skill_learning="propose"` may produce a candidate learned
procedure. It may not:

- mutate its AgentSpec;
- mutate the live Skill Registry;
- activate a skill;
- add a capability;
- add a task kind;
- add a tool;
- widen a Space/data grant;
- widen computer/browser/network access;
- change approval or budget policy;
- write secrets into learned content; or
- promote its own proposal.

Agents with `skill_learning="disabled"` cannot create learning proposals.

## Why a separate procedure artifact is required

The current `SkillSpec` intentionally contains compatibility metadata:

- skill ID/version;
- description;
- required capabilities;
- procedure IDs;
- compatible task kinds;
- compatible tools;
- lifecycle.

It does not contain the actual learned procedure text.

Do not overload `SkillSpec` with mutable model-authored content. Introduce a
separate versioned procedure artifact whose content can be reviewed independently
from authority metadata.

Proposed trusted contract:

```text
SkillProcedureRevision
  schema_version
  procedure_id
  version
  title
  instructions
  preconditions
  verification_steps
  failure_conditions
  source_skill_id
  source_skill_version
  prior_revision_sha256?
  content_sha256
```

The revision digest covers canonical content and the optional prior-revision
identity. The proposal owns evidence references; separate review/promotion records
own lifecycle. A trusted resolver must supply the current prior revision (or
confirm none exists) before the pure builder accepts a lineage claim.

The exact fields may be refined during implementation, but the separation is
mandatory:

```text
SkillSpec                 -> compatibility / authority-neutral metadata
SkillProcedureRevision    -> bounded procedural knowledge
AgentSpec                 -> actual Agent authority envelope
```

A procedure revision cannot alter the capability/task/tool/Space envelope.

## Evidence-backed learning proposal

Learning begins from retained, bounded evidence rather than hidden reasoning.

Proposed contract:

```text
SkillLearningProposal
  proposal_id = deterministic UUIDv5 of proposal_fingerprint
  agent_instance_id = canonical UUID
  agent_id
  agent_registry_version
  skill_registry_version
  source_skill_id?
  source_skill_version?
  target_procedure_id
  proposed_revision
  evidence_refs[]
  proposal_fingerprint
  status
```

Initial statuses:

```text
proposed -> reviewed -> accepted
                    \-> rejected
accepted -> promoted | superseded
```

The current review endpoint records the review and terminal decision in one
transaction, retaining both `reviewed` and `accepted`/`rejected` in append-only
history. Only the authenticated human operator Ahmad may decide; the existing
single configured operator credential maps internally to Ahmad's principal.
Request bodies cannot name a reviewer. Acceptance requires every review check in
the canonical contract to pass. Rejection may record failed checks and rationale.

This decision means “accepted for trusted promotion review” only. It never
activates a procedure or changes registries.

"Accepted" means the proposal passed Zelo review. It does **not** mean that it is
active in the live Skill Registry.

## Permitted evidence

A proposal may reference only retained facts already owned by Zelo, for example:

- completed task ID and attempt ID;
- exact AgentInstance / AgentSpec identity;
- exact worker/backend identity;
- permission/policy/config fingerprints;
- validation outcome;
- bounded result/artifact hashes;
- promotion/review result identifiers;
- fixed audit-event identifiers;
- explicit operator feedback.

Do not persist:

- hidden model reasoning or chain-of-thought;
- raw credentials, tokens or cookies;
- unbounded transcripts;
- arbitrary environment dumps;
- private data unrelated to the learned procedure.

Each evidence reference must be immutable or content-addressed and re-verifiable.
The same evidence kind/source ID cannot appear with conflicting hashes. The pure
builder accepts only a trusted Core evidence resolver that supplies the retained
content digest, owner/visibility and terminal accepted state. A fixture resolver
can prove this contract offline; only a later Core store integration can establish
that the records are genuine. Missing, stale, mutated or unauthorized evidence
invalidates the proposal.

## Proposal authority rules

A proposal builder receives a trusted current AgentInstance snapshot, AgentSpec
binding, Skill Registry snapshot, prior-revision resolver and evidence resolver.
The pure contract does not fetch those records itself. A later Core integration
must load them from authoritative stores and revalidate them on review/promotion.
It must fail closed unless all of the following hold:

1. the AgentSpec is active;
2. `skill_learning == "propose"`;
3. the AgentInstance is active and still bound to that exact AgentSpec/registry;
4. every evidence item belongs to or is explicitly visible to that Agent;
5. all source attempts are terminal and accepted for the claimed outcome;
6. the candidate procedure stays within the Agent's current capability set;
7. candidate task kinds are a subset of `allowed_task_kinds`;
8. candidate tools are a subset of `allowed_tools`;
9. candidate Space/data references stay within existing grants;
10. no proposal field encodes a credential or new external authority.

A skill proposal may reduce authority requirements, but never widen them.

## New skill versus revision

Two proposal types are allowed conceptually:

### Procedure revision

Improve an existing procedure already supported by an active compatible
`SkillSpec`.

This is the preferred initial path. A revision with no prior trusted record must
start at version 1. Later revisions must bind an available trusted prior revision;
if no prior resolver can supply it, Core refuses the proposal.

The proposal binds:

- exact source SkillSpec ID/version;
- exact prior procedure revision, if one exists;
- exact evidence;
- new content hash.

### New skill candidate

A new skill ID may be proposed only when the Agent already possesses every
capability/task/tool/Space requirement the candidate declares.

The proposal remains a draft candidate. It cannot add itself to AgentSpec and
cannot activate itself.

Initial implementation should support **procedure revisions first**. New learned
SkillSpec creation is a later gate after revision promotion is proven.

## Review model

Learning and review must be separate roles.

The Agent that proposes a procedure cannot be the sole authority that accepts it.
Review should bind:

- proposal fingerprint;
- exact evidence set;
- current Agent Registry version;
- current Skill Registry version;
- source skill/procedure identity;
- candidate procedure content hash;
- current authority envelope;
- validation result.

Review checks at minimum:

- evidence genuinely supports the proposed change;
- instructions do not contain hidden tool escalation;
- procedure does not ask for capabilities/tools/Spaces absent from current grants;
- failure/verification steps are explicit;
- no secret/private unrelated material is retained;
- proposed procedure is deterministic/bounded enough for its intended use;
- stale source/evidence invalidates the review.

Review output is an immutable review record, not a mutation command.

## Promotion and activation

v0.15 must reuse Zelo's existing promotion philosophy:

```text
proposal
  -> immutable review
  -> explicit accepted candidate
  -> trusted promotion/config change
  -> normal repository/CI/review gates
  -> active procedure only after exact promoted identity is installed
```

For built-in repository-backed skills, promotion should flow through the normal
Developer/Review/Promotion path rather than giving an Agent a new write channel.

The inert candidate adapter serializes only a freshly revalidated, explicitly
accepted proposal after an explicit Ahmad operator request. Its versioned,
content-addressed artifact path is
`skills/procedures/<source_skill_id>/<procedure_id>/v<version>-<content_sha256>.json`
under an operator-selected candidate staging root. JSON uses canonical sorted-key
serialization; the revision's `content_sha256` binds semantic content and a
separate SHA-256 binds the exact artifact bytes for the normal promotion manifest.
Creation is immutable: identical retries deduplicate, conflicting bytes fail
closed, and path traversal or symlinked descendants are refused.

This adapter only writes a reviewable candidate artifact. It does not create a
Developer task or call Review/Promotion. Ahmad must explicitly hand the artifact
to the existing Developer/Review/Promotion path, where the normal repository,
CI, and approval gates remain in force. No live handoff or activation occurs
automatically. The candidate directory is not read by the active Skill Registry.
The trusted store currently has no authoritative promoted-revision resolver, so
later revisions remain fail-closed until that authority source is separately
defined; version 1 is the only eligible initial candidate.

A successful proposal therefore cannot immediately change:

- `default_skill_registry()`;
- `default_agent_registry()`;
- a running Agent's `skill_ids`;
- task routing;
- tool policy;
- worker authority;
- browser/computer permissions.

Activation requires a separately trusted configuration/repository change and
normal exact-head validation.

## Per-Agent learned-skill view

OpenDots-inspired "learned skills" should appear on the persistent Agent package
as a projection of governed records, not a writable folder that grants authority.

Conceptually:

```text
Agent
  instructions
  memory
  installed skills
  learned skill proposals/revisions
  Space permissions
  tool permissions
  optional persistent computer
```

The Agent-facing learned view may show:

- proposed revisions;
- review status;
- accepted but not yet promoted candidates;
- active promoted revision identity;
- evidence summary.

It must not expose hidden reasoning or mutable authority state.

## Read-only per-Agent learned-skill projection

After the governed proposal/review slice merges, Core may expose a read-only
projection of those records as part of the persistent Agent package. The first
projection is operator-authenticated at
`GET /agents/{instance_id}/learned-skills` and remains non-authoritative.

It exposes only bounded metadata:

- proposal ID/fingerprint;
- source Skill/procedure identity and proposed version/content hash;
- bounded title;
- review status/fingerprint;
- a `current` flag derived from fresh Agent/Skill/evidence revalidation;
- evidence count, evidence kinds and a fingerprint over the frozen evidence refs;
- promotion status; and
- explicit absence/presence of a trusted active promoted revision resolver.

It deliberately omits procedure instructions, verification/failure steps,
evidence source IDs, candidate artifact paths and any hidden reasoning. Accepted
records are reported as `not_promoted` until a future trusted promotion resolver
can prove an installed revision. Pending/rejected records are `not_eligible`.
Without that resolver, `active_revision_sha256` is null and runtime authority is
false.

Historical governed records remain visible for paused/retired Agents. If retained
evidence or Agent/Skill identity becomes stale, the projection reports
`current=false` without modifying append-only proposal/review history.

This view is informational only. It is not injected into Agent runtime context in
this slice and cannot activate, promote, share or execute a learned procedure.

## Persistence

Learning proposals are durable Core records, not model memory.

Initial persistence should use a dedicated bounded record/table rather than
embedding mutable proposal content into AgentSpec or SkillSpec.

Required identity should include:

- canonical proposal UUID (deterministically derived from its separate fingerprint);
- canonical AgentInstance UUID;
- Agent ID/spec version/registry version;
- Skill Registry version;
- source skill/procedure identity;
- canonical proposed revision content hash and prior-revision hash, if any;
- canonical proposal fingerprint over the ordered evidence refs and all frozen identities;
- status;
- created/updated timestamps;
- review/promotion reference IDs where applicable.

Proposal content and evidence metadata must have hard size/count limits.

No automatic migration of an accepted proposal into the trusted registries.

## Idempotency and deduplication

Canonical proposal fingerprint should cover the material proposal and evidence.
Equivalent proposals for the same Agent/source/evidence should be discoverable
rather than endlessly duplicated.

A retry must never create a different accepted identity for the same frozen
proposal.

If Agent/Skill Registry identity changes before review or promotion, the proposal
becomes stale and requires explicit regeneration/review.

## Audit events

Proposed fixed events:

- `skill_learning_proposed`
- `skill_learning_reviewed`
- `skill_learning_accepted`
- `skill_learning_rejected`
- `skill_learning_stale`
- `skill_learning_promotion_requested`
- `skill_learning_promoted`
- `skill_learning_superseded`

Audit details contain IDs, versions, hashes, status and fixed diagnostics only.

## Initial operator/API surface

First implementation should be intentionally narrow:

- operator-authenticated list proposals;
- operator-authenticated read one proposal/review;
- no Agent endpoint for approval;
- no generic edit endpoint;
- no direct activate endpoint;
- no runtime skill upload.

A `skill_learning_proposal_run` task is submitted through the existing
`/agents/{instance_id}/tasks` route. Core derives the Agent identity from the trusted
execution binding, requires `skill_learning="propose"`, and rejects delegation; the
proposal task does not expand the Agent's ordinary task-kind allowlist. The worker
revalidates the current Agent, project, policy and successful owned evidence when it
persists the proposal. Its bounded payload accepts one revision and 1–16 evidence
references, has a 10-second task timeout, and returns proposal metadata only. Review
remains operator-authenticated, and accepted proposals do not activate runtime skills.

Review decisions are currently available only to Ahmad through the authenticated operator
API described above.

## Failure behavior

Fail closed on:

- disabled learning policy;
- stale AgentSpec/Skill Registry identity;
- evidence mismatch;
- evidence outside Agent scope;
- non-terminal or failed source attempts presented as success;
- missing validation;
- authority/tool/task/Space widening;
- invalid or oversized procedure content;
- duplicate/noncanonical IDs;
- proposal mutation after review;
- promotion identity drift;
- review/promotion replay against another Agent or skill.

A failed proposal never modifies the existing active procedure.

## Initial implementation order

1. Frozen `SkillProcedureRevision`, evidence-ref and proposal contracts.
2. Canonical fingerprints, revision lineage and authority-envelope subset validator.
3. Pure proposal builder from trusted fixture instance/evidence/prior-revision resolvers.
4. Persistence migration and append-only proposal status history, with resolvers
   backed by authoritative Core records rather than caller-provided data.
   The read-only `CoreSkillLearningRecords` resolver is an early part of this step:
   it accepts only a successful, terminal, Agent-bound `research_run` attempt with
   matching task result, binding, current Agent/project identity and audit events.
   It derives a digest from the retained result and execution facts. Unsupported
   evidence kinds (review and feedback) default-deny. The dedicated proposal table
   stores validated, size-bounded candidates; retries with an identical fingerprint
   return the same record. Proposal and review records are append-only. Review
   revalidates current Agent/project/registry identity and evidence, then binds the
   decision to the exact evidence, candidate digest and current authority envelope.
   Only the authenticated Ahmad operator may accept or reject; stale proposals and
   acceptance with any failed review check are refused. Tests migrate isolated
   databases only.
5. Operator-authenticated proposal list/read and review-decision API.
6. Exact Agent/Skill Registry staleness checks are enforced during review.
7. Separate immutable review record, append-only status history and review tests.
8. Promotion adapter that emits a repository/config candidate only; no live
   registry mutation.
9. Bounded proposal task routed through the existing Agent execution and Core Runner,
   with direct-only policy binding and database-level task-kind guards.
10. End-to-end fixtures prove successful idempotent submission, disabled-policy denial,
    unbound/delegated denial, post-claim Agent revocation, and stale-evidence denial.
11. Full CI and adversarial review. Acceptance and promotion remain separate operator
    decisions; accepted proposals do not activate runtime skills.

## Acceptance criteria

The first governed learning slice is acceptable only when tests prove:

- `disabled` Agents cannot propose;
- `propose` Agents can create only bounded proposals;
- every proposal is bound to exact Agent/Skill Registry identities;
- evidence is content-bound and re-verifiable;
- learned content cannot widen capability/task/tool/Space authority;
- proposal and review are immutable;
- the proposing Agent cannot self-approve or self-activate;
- accepted proposal does not mutate the live registries;
- stale evidence/registry identity fails closed;
- no hidden reasoning or credentials enter learned records;
- promotion reuses trusted Zelo review/promotion boundaries;
- existing tasks/workers/tools behave identically when no learned revision is
  active.

## Non-goals for the first slice

- autonomous skill activation;
- model-authored capabilities;
- arbitrary code/package installation;
- new browser/computer/shell/network authority;
- cross-Agent skill sharing without explicit promotion;
- UI redesign;
- replacing the existing Skill Registry;
- using learning as a substitute for memory;
- self-modifying Core code without normal Developer/Promotion gates.

## Relationship to v0.15

This design is an independent Core slice and does not change the active Media or
Agent-computer qualification gates.

It implements the previously canonical OpenDots-inspired requirement that each
persistent Agent can have governed learned skills while preserving Zelo Core as
the authority boundary.
