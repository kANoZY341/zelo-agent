# v0.12 — Bounded autonomous continuation

This increment extends the existing Campaign scheduler without creating a second
execution or authority system.

## Goal

Allow one operator-created Campaign schedule to continue multi-step work after a
Core task reaches a terminal state, while preserving the existing Campaign lease,
Mind-wake budget, idempotency, task ownership and approval boundaries.

## Modes

Schedules remain `cadence` by default. Existing one-shot and fixed-interval
behavior is unchanged.

A schedule may opt into `continuation` mode. Continuation schedules:

- are still created by the authenticated operator;
- require more than one bounded logical wake and therefore retain `max_runs`;
- use `run_at` for the first wake;
- after a successful wake that creates a Core task, become immediately eligible
  when that exact task reaches `succeeded`, `failed`, `cancelled` or
  `interrupted`, even if the ordinary interval timestamp is still in the future;
- retain the configured interval as a recovery wake when the linked task is still
  non-terminal, missing, or the successful Mind turn created no Core task;
- retain fixed-interval retry behavior after a failed Mind wake;
- never grant merge, release, approval or policy authority.

The existing `task_finished` Campaign event remains the durable completion fact.
The scheduler derives continuation readiness from authoritative Core task state
rather than introducing a second callback bus or worker-to-scheduler authority path.

## Why this is bounded

Continuation cannot invent a schedule, escape its Campaign, exceed its configured
Mind-wake budget, exceed `max_runs`, bypass the Campaign-wide wake lease, or gain
new task authority. Each continuation wake still passes through the same durable
scheduler and Mind -> Core contract.

## Completion rule

The current Mind contract exposes only `reply` and `core_task`; it has no
explicit `complete` or `wait` disposition. A plain reply therefore is not
treated as proof that the Campaign goal is complete.

For this v0.12 slice:

1. A wake that creates a Core task may accelerate the next wake when that exact
   task reaches a terminal state.
2. A wake that creates no Core task falls back to the configured interval.
3. The schedule completes only when its configured `max_runs` bound is reached
   or the operator cancels it. Campaign state and the existing authority controls
   can also prevent further execution.

This gives Zelo a bounded goal -> task -> result -> next-decision loop without
guessing completion from conversational text or turning ordinary recurring
schedules into autonomous loops.
