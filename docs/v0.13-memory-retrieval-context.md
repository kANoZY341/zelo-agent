# v0.13 — Bounded memory retrieval and context

## Purpose

This second v0.13 slice makes the immutable MemoryRecord foundation useful to
Zelo Mind without giving stored memory execution authority or introducing
semantic/vector infrastructure early.

The design is intentionally conservative:

```text
user query
  -> explicit scope policy
  -> active-memory candidate set
  -> deterministic bounded lexical ranking
  -> bounded snippets with provenance
  -> untrusted zelo_context
  -> Mind reply / routing only
```

Memory remains data. It is never an instruction source.

## Retrieval contract

`POST /memories/retrieve` accepts:

- a bounded query;
- one or more explicit `personal`, `project`, or `agent` scopes;
- a bounded result limit.

The service:

- validates every scope through the existing MemoryService boundary;
- considers only non-expired records that have not been corrected or superseded;
- prefilters ASCII queries by the required number of content-substring overlaps before
  the candidate cap, then scans at most 2,048 such active candidates. This can
  recover older relevant records past newer unrelated records. Python still
  checks exact tokens before returning a hit, so substring-only candidates do
  not become false memories;
- scans at most 256 recent active candidates for non-ASCII queries because
  SQLite's lower() does not implement Python's Unicode casefold. Such searches
  retain the original behavior; neither bounded route promises exhaustive recall;
- extracts at most 32 meaningful query terms;
- ranks by deterministic token overlap with a phrase bonus;
- requires two matched terms for multi-term queries (one for single-term queries)
  to reduce generic-overlap contamination;
- returns at most 20 hits;
- returns at most 1,200 characters of content per hit, centered near the first
  matching term when a record is longer;
- exposes the retrieval method as `bounded_lexical_v1`.

The full immutable record remains available through `GET /memories/{id}`.

No model participates in retrieval ranking. There are no embeddings, vector
stores, external calls, hidden query expansion, or learned ranking in this slice.

## Scope policy for Talk-to-Zelo

The explicit retrieval API can query personal, project and agent scopes.

Automatic Mind context is stricter. A conversation does not yet have a durable
project or agent binding, so automatic retrieval is **personal scope only**.
This prevents text similarity from leaking one project's or agent's memory into
an unrelated conversation.

A later slice may add explicit conversation/project bindings. Until then:

```text
Mind automatic context -> personal memory only
operator retrieval API -> explicitly requested scopes
```

## Context assembly

Relevant personal hits are added as a `core.memories.personal` source inside
the existing `zelo_context` envelope.

The source preserves:

- memory ID;
- scope;
- kind;
- provenance;
- creation time;
- matched terms;
- deterministic score;
- bounded content;
- whether content was truncated.

The memory source has its own 2,200-character budget and the complete context
envelope still has the existing 6,000-character hard budget. Memory payloads are
reduced while preserving valid JSON rather than cutting serialized structures
mid-token.

## Authority boundary

All assembled context remains:

```text
instruction_trust: none
```

Mind may use the data to answer or decide which allowlisted Core task route is
appropriate. The context is deliberately excluded from the second-stage Core
task construction prompt. Stored memory therefore cannot become an executable
instruction merely by containing imperative text.

This slice does not:

- write memory automatically from conversation;
- infer project/agent scope from text similarity;
- let memory bypass approvals or task validation;
- add embeddings/vector search;
- add retention automation;
- create agents;
- change merge, release, scheduling or execution authority.

## Next slice

After this retrieval/context path is verified, v0.13 moves to baseline evaluation
cases and contamination-boundary tests before performance/cost evidence and
storage abstraction.
